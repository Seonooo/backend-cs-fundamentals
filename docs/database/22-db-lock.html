DB 락과 동시성 제어

05편에서 "서버가 여러 대면 JVM 락은 소용없으니 모두가 함께 보는 곳에서 막아야 한다"고 했고, 21편에서 MVCC만으로는 갱신 손실을 못 막는다고 했습니다. 이 편이 그 답입니다. 재고·쿠폰·잔액처럼 정확해야 하는 값을 DB 레벨에서 지키는 세 가지 방법을 비교합니다.

1DB는 수정하는 행에 락을 건다

  • UPDATE, DELETE, SELECT … FOR UPDATE는 대상 행에 배타 락을 겁니다(정확히 어디에 걸리는지는 3절). 같은 행을 수정하려는 다른 트랜잭션은 기다립니다.
  • 일반 SELECT는 MVCC 스냅샷을 읽으므로 락을 걸지도, 기다리지도 않습니다 (21편).
  • 락은 커밋이나 롤백할 때까지 유지됩니다. 트랜잭션이 길면 락도 오래 잡힙니다 (20편).

2세 가지 방법

① 원자적 UPDATE — 계산을 DB에 맡긴다

✓ 조건부 UPDATE 한 줄
UPDATE stock SET qty = qty - 1 WHERE product_id = ? AND qty > 0;
-- 영향받은 행 수가 1이면 성공, 0이면 품절

읽기와 쓰기가 한 문장 안에서 일어나므로 끼어들 틈이 없습니다. 조건이 단순하면 가장 먼저 고려할 방법입니다.

② 비관적 락 vs ③ 낙관적 락

로직이 복잡해서 "읽고 → 판단하고 → 쓰기"가 필요할 때는 두 가지 전략이 있습니다. 충돌이 자주 난다고 보고 미리 잠글지, 드물다고 보고 나중에 확인할지의 차이입니다.

① 원자적 UPDATE② 비관적 락③ 낙관적 락
방식조건부 UPDATE 한 문장SELECT … FOR UPDATE버전 컬럼 비교
JPA@Modifying @Query@Lock(PESSIMISTIC_WRITE)@Version
충돌 시0행 반환 → 실패 처리기다림예외 → 재시도
잘 맞는 곳수량 증감처럼 단순한 계산충돌이 잦고 로직이 복잡충돌이 드묾 (게시글 수정, 설정 변경)
주의복잡한 규칙은 표현 어려움락 대기·데드락 (06편)충돌이 잦으면 재시도 폭증

3InnoDB의 락은 인덱스에 걸린다

MySQL InnoDB는 행을 찾기 위해 훑은 인덱스 레코드에 락을 겁니다. 그래서 FOR UPDATE의 WHERE 조건에 인덱스가 없으면, 조건에 맞는 행을 찾으려고 훑은 수많은 행이 함께 잠깁니다.

4실무 예시

설계 이유

선착순 쿠폰 100장, 무엇을 고를까

상황선택
남은 수량만 줄이면 됨① 원자적 UPDATE — 가장 단순하고 빠름
1인 1장 확인, 등급별 조건 등 로직이 복잡② 비관적 락 — 충돌이 매우 잦은 상황이라 낙관적 락은 재시도 폭증
순간 요청이 DB가 감당 못 할 만큼 몰림DB 앞단에서 제어: Redis 원자 연산(DECR)으로 선착순 판정 후 DB 기록, 또는 대기열

"1인 1장" 같은 중복 방지는 락보다 유니크 제약(member_id, coupon_id)이 더 확실합니다. 동시에 두 요청이 와도 DB가 하나만 받아 줍니다 (12편 멱등 키와 같은 원리).

좋은 패턴

JPA로 쓰는 법

② 비관적 락
@Lock(LockModeType.PESSIMISTIC_WRITE)
@Query("select s from Stock s where s.productId = :id")
Stock findForUpdate(Long id);
③ 낙관적 락
@Entity
public class Article {
  @Id Long id;
  @Version Long version;   // 수정 시 자동 비교·증가
  String content;
}
// 충돌 시 ObjectOptimisticLockingFailureException
// → 사용자에게 "다른 사람이 먼저 수정" 안내 or 재시도

락 대기 시간 주의: MySQL의 기본 락 대기 시간(innodb_lock_wait_timeout)은 50초로 길어서, 따로 줄이지 않으면 요청이 50초 동안 커넥션을 쥐고 기다릴 수 있습니다. JPA의 jakarta.persistence.lock.timeout 힌트는 MySQL + Hibernate 6에서 0(NOWAIT)과 -2(SKIP LOCKED)만 SQL에 반영되고 3000 같은 값은 무시됩니다. MySQL에서는 세션의 innodb_lock_wait_timeout을 낮추거나 NOWAIT/SKIP LOCKED를 쓰고, PostgreSQL 등 다른 DB에서는 힌트가 동작하는지 확인합니다.

설계 이유

Redis 분산 락은 언제 쓰나

DB 행으로 표현되지 않는 자원(외부 API 호출을 한 번만, 배치 작업을 한 서버에서만)을 여러 서버에서 보호하거나, DB 락 경합이 너무 커서 앞단에서 걸러야 할 때 씁니다. 단, 락에 만료 시간이 있어서 작업이 만료보다 오래 걸리면 락이 풀린 채 작업이 겹칠 수 있습니다. 정확성이 최우선인 데이터는 최종적으로 DB 제약·원자적 UPDATE로 한 번 더 지키는 것이 안전합니다.

5설명해보기

답을 열기 전에 먼저 소리 내어 설명해 보세요.

비관적 락과 낙관적 락의 차이와 각각 어울리는 상황은?
비관적 락은 읽을 때부터 SELECT FOR UPDATE로 행을 잠가 다른 트랜잭션을 기다리게 하므로, 충돌이 잦고 로직이 복잡할 때 맞습니다. 낙관적 락은 잠그지 않고 진행한 뒤 수정 시점에 버전을 비교해 충돌을 감지하고 재시도하므로, 충돌이 드물 때 동시성이 좋습니다.
선착순 100명 쿠폰 발급에서 낙관적 락이 좋지 않은 이유는?
동시에 수많은 요청이 같은 행을 수정하려 해 충돌이 거의 매번 일어나므로, 대부분의 요청이 실패하고 재시도하며 부하가 폭증합니다. 단순 수량 차감이면 조건부 원자적 UPDATE, 로직이 복잡하면 비관적 락이 낫습니다.
SELECT FOR UPDATE의 WHERE 조건에 인덱스가 없으면 어떤 문제가 생기나요?
InnoDB는 행을 찾으며 훑은 인덱스 레코드에 락을 걸기 때문에, 인덱스가 없으면 테이블을 훑으며 지나간 많은 행이 잠깁니다. 무관한 행을 수정하려는 트랜잭션까지 기다리게 되고 데드락 가능성도 커집니다.
