인덱스

03편에서 디스크는 메모리보다 수천 배 느리다고 했습니다. 인덱스는 디스크에서 읽어야 하는 페이지 수를 줄이기 위한 정렬된 자료구조입니다. 트리 구현을 외울 필요는 없고, "정렬되어 있다"는 성질 하나로 어떤 쿼리가 빠르고 어떤 쿼리가 인덱스를 못 타는지 설명할 수 있으면 됩니다.

1. 인덱스가 없으면 전부 읽는다2. B+트리: 정렬되어 있고, 얕다3. InnoDB: 테이블 자체가 PK 순으로 정렬되어 있다4. 복합 인덱스는 왼쪽 컬럼부터 쓴다5. 인덱스가 있어도 못 타는 경우6. 실무 예시7. 설명해보기

1인덱스가 없으면 전부 읽는다

두꺼운 책에서 "트랜잭션"이라는 단어를 찾을 때, 색인이 없으면 첫 쪽부터 끝까지 넘겨야 합니다. 색인이 있으면 가나다순으로 정리된 목록에서 바로 쪽 번호를 찾습니다. DB도 똑같습니다.

인덱스 없음 · 풀 스캔
SELECT * FROM member WHERE email = 'kim@a.com';
-- 100만 행을 처음부터 끝까지 확인
email 인덱스 있음
CREATE INDEX idx_member_email ON member(email);
-- 정렬된 트리에서 몇 단계만 내려가면 끝

2B+트리: 정렬되어 있고, 얕다

MySQL(InnoDB)과 PostgreSQL의 기본 인덱스는 B+트리입니다. 알아야 할 성질은 셋뿐입니다. ① 값이 정렬되어 있다 ② 한 노드에 수백 개의 키가 들어가 트리가 얕다(수백만 행도 보통 3~4단계) ③ 맨 아래 칸(리프)끼리 옆으로 연결되어 있어 범위 검색이 쉽다.

3InnoDB: 테이블 자체가 PK 순으로 정렬되어 있다

MySQL InnoDB에서는 테이블 데이터 자체가 PK 순서의 B+트리로 저장됩니다(클러스터드 인덱스). 우리가 추가로 만드는 인덱스(보조 인덱스)의 리프에는 행 전체가 아니라 PK 값이 들어 있습니다. 그래서 보조 인덱스로 찾으면 보통 두 번 찾습니다.

4복합 인덱스는 왼쪽 컬럼부터 쓴다

여러 컬럼으로 만든 인덱스는 첫 번째 컬럼으로 먼저 정렬하고, 같은 값 안에서 두 번째 컬럼으로 정렬합니다. 전화번호부가 "성 → 이름" 순으로 정렬된 것과 같습니다. 성을 모르면 이름만으로는 빨리 찾을 수 없습니다.

복합 인덱스 순서 정하는 요령 — ① 같다(=) 조건 컬럼을 앞에 ② 범위(>, BETWEEN)나 정렬(ORDER BY) 컬럼을 뒤에. 범위 조건 뒤에 오는 컬럼은 인덱스로 좁히는 데 거의 쓰이지 않습니다.

5인덱스가 있어도 못 타는 경우

공통점은 하나입니다. 인덱스에 정렬된 값과 조건의 모양이 달라지면 정렬을 이용할 수 없습니다.

패턴✕ 못 탐✓ 고친 모양
컬럼에 함수·연산WHERE DATE(created_at) = '2026-09-01'WHERE created_at >= '2026-09-01' AND created_at < '2026-09-02'
타입이 달라 변환WHERE phone = 01012345678 (phone은 문자열)WHERE phone = '01012345678'
앞쪽 와일드카드WHERE name LIKE '%수'LIKE '김%'는 가능, 부분 검색은 전문 검색 엔진
선두 컬럼 없음(user_id, created_at)에 created_at만조건 추가 또는 별도 인덱스
대부분의 행이 해당WHERE status = 'ACTIVE' (95%가 ACTIVE)DB가 일부러 풀 스캔을 고름 (그게 더 빠름)

6실무 예시

실수 예시

"오늘 주문" 조회가 갑자기 느려졌다

데이터가 적을 땐 괜찮던 일별 통계 쿼리가, 주문 테이블이 수천만 건이 되자 수십 초가 걸립니다. created_at에 인덱스가 있는데도요.

✕ 컬럼을 가공해서 비교
WHERE DATE(created_at) = :today
-- 모든 행의 created_at에 DATE()를 적용해 봐야 함
✓ 컬럼은 그대로, 범위로
WHERE created_at >= :today
  AND created_at <  :tomorrow
-- 정렬된 인덱스에서 한 구간만 읽음

JPA 메서드 이름 쿼리도 결국 SQL로 나갑니다. 날짜 비교를 Between이나 GreaterThanEqual + LessThan으로 표현하면 됩니다.

좋은 패턴

"내 주문 최신순" 목록을 위한 복합 인덱스

✓ 조건(=) → 정렬 순서로
SELECT id, status, total_price, created_at
FROM orders
WHERE member_id = ?
ORDER BY created_at DESC
LIMIT 20;

CREATE INDEX idx_orders_member_created ON orders (member_id, created_at);
-- member_id 덩어리 안에서 created_at이 이미 정렬 → 별도 정렬 없이 20개만 읽고 끝

인덱스가 (created_at) 하나뿐이면 전체 주문을 최신순으로 훑으며 내 주문을 골라야 하고, (member_id) 하나뿐이면 내 주문 전체를 모아서 다시 정렬해야 합니다. 19편의 실행 계획으로 차이를 확인할 수 있습니다.

실수 예시

느린 쿼리마다 인덱스를 추가했다

인덱스는 공짜가 아닙니다. 행을 INSERT·UPDATE·DELETE할 때마다 모든 인덱스도 함께 갱신해야 하고, 디스크와 메모리(버퍼 풀)도 차지합니다. 인덱스가 10개인 테이블은 쓰기가 눈에 띄게 느려집니다.

해결: 비슷한 인덱스를 하나의 복합 인덱스로 합치고((a)와 (a, b)가 있으면 (a)는 대개 불필요), 사용되지 않는 인덱스는 지웁니다.

지금은 넘어가도 되는 것 · B+트리 노드 분할·병합 구현, 페이지 내부 구조, 해시·GIN·GiST 등 다른 인덱스 종류, 인덱스 통계 수집 방식

7설명해보기

답을 열기 전에 먼저 소리 내어 설명해 보세요.

인덱스가 조회를 빠르게 하는 원리는?
인덱스는 컬럼 값을 정렬된 B+트리로 저장합니다. 트리가 얕아서 몇 번의 페이지 읽기만으로 원하는 값에 도달하고, 리프가 옆으로 연결되어 범위 검색과 정렬된 순서 읽기도 빠릅니다. 결국 디스크에서 읽는 페이지 수를 크게 줄입니다.
(user_id, created_at) 인덱스가 있을 때 WHERE created_at > ? 만으로는 왜 효율이 낮나요?
인덱스가 user_id로 먼저 정렬되고 그 안에서 created_at으로 정렬되어 있어, created_at 조건에 맞는 값들이 user_id마다 흩어져 있습니다. 선두 컬럼 조건 없이는 한 구간으로 좁힐 수 없어 사실상 전체를 훑어야 합니다.
WHERE DATE(created_at) = ? 가 인덱스를 못 타는 이유와 해결책은?
인덱스에는 created_at 원래 값이 정렬되어 있는데, 조건은 가공된 값(DATE 결과)과 비교하므로 정렬을 이용할 수 없습니다. 컬럼은 그대로 두고 created_at >= 오늘 AND created_at < 내일처럼 범위 조건으로 바꿉니다.
인덱스를 많이 만들면 생기는 단점은?
쓰기 작업마다 모든 인덱스를 함께 갱신해야 해서 INSERT·UPDATE·DELETE가 느려지고, 저장 공간과 메모리를 더 차지합니다. 비슷한 인덱스가 많으면 옵티마이저의 선택도 복잡해집니다.
