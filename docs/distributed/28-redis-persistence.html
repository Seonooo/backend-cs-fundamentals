Redis 영속성과 메모리

27편에서 Redis가 빠른 이유는 데이터를 메모리에 두기 때문이라고 했습니다. 그 대가도 메모리에서 나옵니다. 꺼지면 사라지고, 가득 차면 무언가를 지워야 합니다. 이 편은 Redis가 죽거나 메모리가 찼을 때 무슨 일이 생기는지, 그리고 그 결과가 "캐시로 쓰느냐, 원본으로 쓰느냐"에 따라 어떻게 달라지는지 봅니다.

1메모리는 꺼지면 사라진다: RDB와 AOF

Redis의 데이터는 메모리에 있으므로, 프로세스가 죽거나 서버가 재부팅되면 그대로 사라집니다. 이를 막기 위해 디스크에 남기는 방법이 두 가지 있습니다. 이렇게 데이터를 디스크에 남겨 재시작 후에도 되살리는 것을 영속성(persistence)이라고 합니다.

방식무엇을 남기나죽으면 잃는 범위대가
RDB (스냅샷)정해진 주기마다 메모리 전체를 사진 찍듯 파일로 저장마지막 스냅샷 이후의 쓰기 전부 (주기가 5분이면 최대 5분)저장할 때 메모리가 순간적으로 더 필요함(아래)
AOF (명령 기록)쓰기 명령을 받을 때마다 파일 끝에 덧붙임기본 설정(appendfsync everysec)에서 최대 약 1초디스크 쓰기가 계속 생기고, 파일이 커져서 주기적으로 다시 정리함

RDB 스냅샷은 Redis가 자기 자신을 복제한 자식 프로세스(fork)를 만들어, 자식이 그 순간의 메모리를 파일로 쓰는 방식입니다. 부모는 그동안 계속 명령을 받습니다. 부모와 자식은 처음에 메모리를 공유하다가, 저장 중에 바뀐 부분만 따로 복사합니다. 그래서 저장하는 동안 쓰기가 많으면 추가 메모리가 필요하고, 쓰기가 아주 많으면 거의 두 배까지 늘 수 있습니다. 서버 메모리를 Redis에 전부 내주지 않고 여유를 남겨 두는 이유입니다.

핵심 — 영속성을 켜도 "잃을 수 있는 범위"가 줄어들 뿐, 0이 되지는 않습니다. RDB는 분 단위, AOF 기본 설정은 1초 단위입니다. 1초도 잃으면 안 되는 데이터라면 Redis 하나에 맡기지 않고 DB를 원본으로 둡니다.

2캐시냐 원본이냐에 따라 설정이 다르다

영속성과 다음 절의 메모리 설정을 정하는 기준은 하나입니다. "이 데이터를 잃으면 다시 만들 수 있는가?"

용도잃으면영속성메모리가 차면
캐시 (26편)DB에서 다시 읽어 채우면 됨꺼도 됨 (켜 두면 재시작 후 빈 캐시를 피할 수 있음, 4절)오래 안 쓴 것부터 지워도 됨
세션 (14편)사용자가 로그아웃됨보통 켬함부로 지우면 안 됨
카운터·선착순 수량 (22편)숫자가 틀어짐켬, 그래도 최종 기록은 DB에지우면 안 됨
분산 락 (30편)락이 사라져 두 명이 동시에 진입켜도 완전하지 않음 (30편)지우면 안 됨

그래서 캐시와 원본 데이터를 같은 Redis에 섞으면 설정이 서로 부딪칩니다. 캐시에 맞춰 "아무 키나 지워도 됨"으로 두면 세션이 지워지고, 세션에 맞춰 "지우지 않음"으로 두면 캐시가 메모리를 다 채웠을 때 세션 쓰기까지 실패합니다. 규모가 커지면 용도별로 Redis를 나누는 것이 일반적입니다.

3메모리가 차면 무엇을 지울지 정해야 한다

Redis가 쓸 메모리 상한은 maxmemory로 정합니다. 상한에 닿았을 때 어떻게 할지는 maxmemory-policy(eviction 정책)로 정합니다. eviction은 "자리를 만들기 위해 기존 키를 내보내는 것"입니다.

정책지우는 대상맞는 용도
noeviction아무것도 지우지 않음. 메모리를 더 쓰는 쓰기 명령이 에러로 실패지우면 안 되는 원본 데이터
allkeys-lru모든 키 중 오래 안 쓴 것부터순수 캐시
allkeys-lfu모든 키 중 덜 자주 쓴 것부터일부 키만 계속 인기 있는 캐시
volatile-lru / volatile-lfu / volatile-ttlTTL이 걸린 키 중에서만 고름캐시(TTL 있음)와 원본(TTL 없음)이 섞인 경우

직접 설치한 Redis의 기본값은 noeviction이고, 64비트 환경에서 maxmemory 기본값은 0(상한 없음)입니다. 상한 없이 두면 Redis가 서버 메모리를 다 쓸 때까지 늘어나다가 운영체제에 의해 강제 종료될 수 있으므로, 상한은 꼭 정합니다. 관리형 서비스는 기본값이 다를 수 있으니 파라미터 설정을 먼저 확인합니다.

volatile 계열 정책은 TTL이 걸린 키가 하나도 없으면 지울 것이 없어서 noeviction처럼 동작합니다. "캐시에 TTL을 빠뜨린 키"가 쌓이면 이 상황이 됩니다(실무 예시).

4재시작 직후 빈 캐시가 DB를 덮친다

영속성 없이 캐시로만 쓰던 Redis가 재시작되면, 캐시는 비어 있습니다. 그 순간부터 모든 조회가 캐시 미스가 되어 DB로 갑니다. 26편의 캐시 스탬피드가 키 하나가 아니라 캐시 전체에서 한꺼번에 일어나는 셈입니다.

대책내용
영속성으로 되살리기캐시용이라도 RDB를 켜 두면 재시작 후 대부분의 데이터가 돌아옴
레플리카로 넘기기한 대가 죽어도 복제본이 이어받아 캐시가 비지 않음 (29편)
미리 채우기 (warm-up)트래픽을 받기 전에 자주 쓰는 키를 채워 둠
DB 쪽 방어같은 키를 동시에 한 번만 로딩(26편), DB 커넥션 풀 상한(23편)으로 DB가 무너지는 것을 막음

5실무 예시

실수 예시

캐시 저장이 실패하면서 API가 500을 냈다

Redis를 직접 설치하면서 maxmemory만 정하고 정책은 기본값(noeviction)으로 두었습니다. 캐시가 상한까지 차자 새 캐시를 넣는 쓰기가 OOM command not allowed when used memory > 'maxmemory'. 에러로 실패했고, 그 예외가 그대로 올라가 조회 API가 500을 냈습니다.

  • 캐시 전용 Redis라면 정책을 allkeys-lru(또는 lfu)로 바꿉니다.
  • 캐시는 "없어도 되는 것"이므로, 캐시 읽기·쓰기 실패는 로그만 남기고 DB 결과로 응답하게 만듭니다. 스프링 캐시 추상화에서는 CacheErrorHandler로 처리합니다. 기본 핸들러는 예외를 그대로 다시 던지므로, 로그만 남기는 핸들러를 직접 등록해야 합니다.
실수 예시

volatile-lru인데도 메모리가 꽉 찼다

세션을 보호하려고 정책을 volatile-lru로 두었습니다. 그런데 한 기능이 캐시를 저장하면서 TTL을 빠뜨렸습니다. TTL 없는 키는 정책상 지울 대상이 아니므로 계속 쌓였고, 지울 수 있는 키가 바닥나자 쓰기가 실패하기 시작했습니다.

해결: 캐시 저장 코드에서 TTL을 필수로 만듭니다(스프링 캐시라면 RedisCacheConfiguration.entryTtl로 기본 TTL 지정). 캐시와 세션을 다른 Redis로 나누면 이런 간섭 자체가 사라집니다.

장애 대응

Redis 재시작 뒤 DB CPU가 100%가 됐다

메모리 설정을 바꾸려고 캐시 Redis를 재시작했습니다. 캐시용이라 영속성을 꺼 두었기 때문에 모든 데이터가 사라졌고, 4절 그림처럼 조회가 한꺼번에 DB로 몰렸습니다. DB가 느려지자 커넥션 풀 대기가 늘고, 캐시와 무관한 API까지 타임아웃이 났습니다.

해결: 캐시 Redis도 재시작이 필요한 작업은 트래픽이 적은 시간에, 레플리카로 먼저 넘긴 뒤 진행합니다(29편). 자주 쓰는 키는 미리 채우고, 같은 키의 동시 로딩을 하나로 합칩니다(26편).

운영 설정

maxmemory를 서버 메모리와 똑같이 잡지 않는 이유

서버 메모리가 16GB라고 maxmemory를 16GB로 잡으면, RDB 스냅샷 중 늘어나는 메모리(1절)와 연결마다 쓰는 버퍼, 운영체제 몫이 들어갈 자리가 없습니다. 그 결과 스냅샷 도중 운영체제가 Redis를 강제 종료하기도 합니다. 서버 메모리의 일부만 상한으로 주고 여유를 남기며, 여유가 얼마나 필요한지는 쓰기 양과 스냅샷 여부에 따라 모니터링하며 정합니다.

지금은 넘어가도 되는 것 · RDB·AOF 파일 형식, AOF 재작성(rewrite) 과정과 여러 파일로 나눠 저장하는 방식, LRU·LFU를 근사하는 샘플링 방식, 만료된 키를 지우는 시점(읽을 때·주기적 청소), 메모리 단편화

6설명해보기

답을 열기 전에 먼저 소리 내어 설명해 보세요.

RDB와 AOF는 Redis가 죽었을 때 각각 무엇을 잃나요?
RDB는 주기적으로 찍는 스냅샷이라 마지막 스냅샷 이후의 쓰기를 모두 잃습니다. AOF는 쓰기 명령을 계속 파일에 덧붙이고, 기본 설정에서 1초마다 디스크에 반영하므로 최대 약 1초 분량을 잃습니다. 둘 다 잃는 범위를 줄일 뿐 0으로 만들지는 못합니다.
maxmemory-policy가 noeviction일 때 메모리가 가득 차면 어떻게 되나요?
키를 지우지 않고, 메모리를 더 써야 하는 쓰기 명령을 에러로 거부합니다. 읽기는 계속 됩니다. 캐시 용도라면 쓰기 실패가 곧 애플리케이션 예외가 되므로 allkeys-lru 같은 정책을 쓰고, 캐시 실패를 무시하고 DB로 응답하도록 처리합니다.
캐시와 세션을 한 Redis에 두면 eviction 정책에서 어떤 문제가 생기나요?
캐시에 맞춰 모든 키를 지울 수 있게 하면 세션이 지워져 사용자가 로그아웃되고, 세션에 맞춰 지우지 않게 하면 캐시가 메모리를 채웠을 때 세션 쓰기까지 실패합니다. volatile 정책으로 TTL 있는 키만 지우게 할 수 있지만 TTL을 빠뜨리면 무너지므로, 용도별로 Redis를 나누는 것이 안전합니다.
캐시 적중률이 95%인 서비스에서 캐시 Redis가 비면 DB에는 어떤 일이 생기나요?
평소 DB로 가던 요청은 전체의 5%였는데, 캐시가 비면 100%가 DB로 가서 DB가 받는 요청이 20배가 됩니다. DB가 느려지면 커넥션 풀 대기와 타임아웃으로 번집니다. 영속성·레플리카로 캐시가 비지 않게 하거나, 미리 채우기와 동시 로딩 합치기로 충격을 줄입니다.
