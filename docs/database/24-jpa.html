JPA와 DB 기본기

JPA는 SQL을 감춰 주지만, 결국 DB로 나가는 것은 SQL입니다. JPA를 쓰면서 생기는 성능 문제는 대부분 "SQL이 몇 번, 어떤 모양으로 나가는가"를 놓쳐서 생깁니다. 이 편은 앞에서 배운 캐시(03)·트랜잭션(20)·인덱스(18)·메모리(02)가 JPA 안에서 어떻게 나타나는지 봅니다.

1영속성 컨텍스트: 트랜잭션 범위의 1차 캐시

JPA는 트랜잭션 동안 조회한 엔티티를 영속성 컨텍스트에 보관합니다. 같은 엔티티를 다시 찾으면 DB에 가지 않고, 엔티티의 필드를 바꾸면 커밋 때 알아서 UPDATE를 만들어 냅니다(변경 감지).

이 캐시는 한 트랜잭션 안에서만 유효합니다(OSIV가 켜져 있으면 요청이 끝날 때까지로 늘어납니다, 23편). 요청 간 공유되는 캐시가 아니므로 성능 캐시로 기대하면 안 됩니다. 그런 캐시는 26편에서 다룹니다.

2N+1 문제: 쿼리 한 번이 101번이 된다

주문 100건을 조회하고, 화면에 주문자 이름을 보여 주려고 order.getMember().getName()을 호출합니다. 연관 엔티티가 지연 로딩이면, 주문마다 회원을 따로 조회합니다. 회원이 모두 다르면 최대 100번이 더 나갑니다. 같은 회원은 1절의 영속성 컨텍스트에서 꺼내 쓰므로 한 번만 조회됩니다. 이름은 JPA에서 유명해졌지만, 목록을 가져온 뒤 반복문 안에서 하나씩 조회하는 코드라면 어디서든 생기는 문제입니다.

✕ SQL 로그
select * from orders limit 100;                -- 1번
select * from member where id = 3;             -- 주문 1의 회원
select * from member where id = 8;             -- 주문 2의 회원
…                                              -- 회원이 모두 다르면 → 총 101번
해결방법특징
fetch joinselect o from Order o join fetch o.member쿼리 1번. 컬렉션(1:N)과 페이징을 함께 쓰면 문제 (아래 예시)
@EntityGraph@EntityGraph(attributePaths = "member")fetch join을 어노테이션으로
배치 크기spring.jpa.properties.hibernate.default_batch_fetch_size: 100지연 로딩을 IN 절로 묶음. 페이징과도 잘 맞음 → 전역 기본값으로 많이 설정

3실무 예시

실수 예시

컬렉션 fetch join + 페이징 = 전부 메모리로

주문 목록을 주문 상품(1:N)과 함께 fetch join하고 Pageable로 20건만 요청했습니다. 조인 결과는 주문 × 상품 수만큼 행이 늘어나기 때문에 DB에서 정확히 20건을 자를 수 없고, Hibernate는 전체를 메모리로 가져와 자릅니다.

로그에 찍히는 경고 (Hibernate 6 · 5버전은 HHH000104)
WARN HHH90003004: firstResult/maxResults specified with collection fetch; applying in memory

주문이 100만 건이면 100만 건을 힙에 올립니다 (02편 OOM). 해결: 컬렉션은 fetch join하지 말고 배치 크기로 가져오고, 1:1·N:1 관계만 fetch join합니다.

실수 예시

벌크 UPDATE 후 옛 값이 보인다

21편에서 쓴 원자적 UPDATE(@Modifying @Query)는 영속성 컨텍스트를 거치지 않고 DB를 직접 바꿉니다. 같은 트랜잭션에서 그 엔티티를 이미 조회해 둔 상태라면, 1번 그림의 캐시에 남아 있는 옛 값이 계속 보입니다. 26편에서 볼 캐시 불일치의 가장 작은 버전입니다.

✓ 벌크 연산 후 캐시 비우기
@Modifying(clearAutomatically = true)
@Query("update Point p set p.balance = p.balance - :amt where p.id = :id and p.balance >= :amt")
int use(Long id, int amt);
실수 예시

대량 INSERT가 한 건씩 나간다

1만 건을 saveAll로 저장하는데 INSERT가 1만 번 따로 나갑니다. PK 생성 전략이 GenerationType.IDENTITY(MySQL auto_increment)이면, JPA는 INSERT를 실행해야 PK를 알 수 있어서 Hibernate의 배치 INSERT가 꺼집니다.

해결: 대량 적재는 JdbcTemplate.batchUpdate로 직접 배치 INSERT를 하거나(MySQL은 rewriteBatchedStatements=true), 시퀀스 등 다른 PK 전략을 검토합니다. 처리 중에는 영속성 컨텍스트에 엔티티가 쌓이지 않도록 일정 건수마다 flush()·clear()합니다 (02편 메모리).

좋은 패턴

엔티티 대신 DTO로 응답한다

엔티티를 컨트롤러에서 그대로 JSON으로 반환하면 문제가 한꺼번에 생깁니다. 직렬화하면서 지연 로딩이 줄줄이 일어나 N+1이 되고(그래서 OSIV가 필요해지고, 23편), 양방향 관계면 무한 재귀(02편 StackOverflowError), 내부 필드가 API 스펙이 되어 버립니다.

✓ 트랜잭션 안에서 필요한 것만 DTO로
@Transactional(readOnly = true)
public List<OrderSummary> myOrders(Long memberId) {
    return orderRepo.findWithMemberByMemberId(memberId).stream()   // fetch join or 배치 크기
        .map(o -> new OrderSummary(o.getId(), o.getMember().getName(), o.getTotal()))
        .toList();
}
지금은 넘어가도 되는 것 · Hibernate 내부 구현, 모든 연관관계 매핑 옵션과 cascade 조합, 2차 캐시 설정, 상속 매핑 전략 비교

4설명해보기

답을 열기 전에 먼저 소리 내어 설명해 보세요.

N+1 문제가 무엇이고, 해결 방법 두 가지는?
목록을 한 번 조회한 뒤, 각 항목의 지연 로딩 연관 엔티티를 접근할 때마다 추가 쿼리가 나가 총 1+N번의 쿼리가 실행되는 문제입니다. fetch join(또는 EntityGraph)으로 한 번에 가져오거나, 배치 크기를 설정해 IN 절로 묶어 조회합니다.
영속성 컨텍스트의 1차 캐시와 변경 감지를 설명해 보세요.
트랜잭션 동안 조회한 엔티티를 보관해 같은 엔티티를 다시 찾으면 SQL 없이 반환하는 것이 1차 캐시입니다. 조회 시점의 스냅샷을 함께 저장해 두고, 커밋 시 현재 상태와 비교해 바뀐 필드에 대한 UPDATE를 자동으로 만드는 것이 변경 감지입니다.
컬렉션 fetch join과 페이징을 함께 쓰면 안 되는 이유는?
1:N 조인은 결과 행이 부모 × 자식 수만큼 늘어나 DB에서 부모 기준으로 정확히 자를 수 없습니다. 그래서 Hibernate가 전체 결과를 메모리로 가져와 페이징하므로 데이터가 많으면 메모리 부족이 됩니다. 컬렉션은 배치 크기로 가져옵니다.
IDENTITY 전략에서 대량 INSERT가 느린 이유는?
IDENTITY는 DB가 INSERT할 때 PK를 만들기 때문에, JPA가 엔티티를 영속화하려면 INSERT를 즉시 실행해 PK를 받아야 합니다. 그래서 여러 INSERT를 모아 보내는 Hibernate 배치 INSERT가 동작하지 않습니다.
