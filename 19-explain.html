실행 계획 읽기

18편에서 "이 쿼리는 인덱스를 탈 것이다"라고 추측했다면, 실행 계획은 그 추측을 DB에게 직접 물어보는 도구입니다. 모든 칸을 알 필요는 없습니다. MySQL 기준으로 네 칸만 읽으면 대부분의 느린 쿼리 원인이 보입니다.

1. EXPLAIN: 쿼리 앞에 붙이기만 하면 된다2. type 등급: 오른쪽으로 갈수록 많이 읽는다3. EXPLAIN ANALYZE: 예상 말고 실제4. 실무 예시5. 설명해보기

1EXPLAIN: 쿼리 앞에 붙이기만 하면 된다

mysql> EXPLAIN SELECT * FROM orders WHERE member_id = 7 ORDER BY created_at DESC LIMIT 20;
+----+-------+------+---------------------+---------+------+----------------+
| id | table | type | key                 | ...     | rows | Extra          |
+----+-------+------+---------------------+---------+------+----------------+
|  1 | orders| ref  | idx_orders_member   | ...     |  830 | Using filesort |
+----+-------+------+---------------------+---------+------+----------------+
칸읽는 법위 결과 해석
type테이블을 어떻게 읽는가 (아래 등급표)ref: 인덱스로 같은 값 찾기 · 괜찮음
key실제로 고른 인덱스 (NULL이면 인덱스 안 씀)member_id 인덱스 사용
rows읽을 것으로 예상하는 행 수 (추정치)830행 읽음 → 20개 반환
Extra추가 작업 (정렬, 임시 테이블, 커버링 등)830행을 따로 정렬해야 함

2type 등급: 오른쪽으로 갈수록 많이 읽는다

Extra에서 자주 보는 값

값뜻판단
Using index인덱스만 읽고 끝남 (커버링 인덱스, 18편)좋음
Using where읽은 행을 조건으로 한 번 더 거름보통 · rows가 크면 확인
Using filesort결과를 따로 정렬함 (인덱스 순서를 못 씀)rows가 크면 주의
Using temporary임시 테이블을 만듦 (GROUP BY, DISTINCT 등)rows가 크면 주의
읽는 순서 — ① key가 NULL인가? (인덱스를 안 씀) ② type이 ALL·index인가? ③ rows가 반환 건수에 비해 너무 큰가? ④ Extra에 filesort·temporary가 있는가? 네 가지 중 하나라도 걸리면 18편의 인덱스·쿼리 모양을 다시 봅니다.

3EXPLAIN ANALYZE: 예상 말고 실제

EXPLAIN의 rows는 통계에 기반한 추정치입니다. MySQL 8.0.18+의 EXPLAIN ANALYZE는 쿼리를 실제로 실행하고 단계별 실제 시간과 행 수를 보여 줍니다. 추정과 실제가 크게 다르면 통계가 오래됐을 수 있습니다(ANALYZE TABLE로 갱신).

EXPLAIN ANALYZE 결과 일부 (읽는 법만)
-> Limit: 20 row(s)  (actual time=0.12..0.35 rows=20 loops=1)
    -> Index lookup on orders using idx_orders_member_created (member_id=7) (reverse)
       (cost=… rows=830) (actual … rows=20)   ← 830행 예상했지만 20행만 읽고 멈춤

주의: 실제로 실행하므로 UPDATE·DELETE에 쓰면 안 되고, 운영 DB에서 무거운 쿼리에 쓸 때도 조심합니다.

18편의 "내 주문 최신순" 쿼리입니다. 인덱스를 바꾸기 전과 후를 비교합니다.

인덱스typekeyrowsExtra
없음ALLNULL2,000,000Using where; Using filesort
(member_id)refidx_member830Using filesort
(member_id, created_at)refidx_member_created830 (실제 20)(filesort 없음, 역순으로 읽음)

마지막 인덱스는 이미 정렬된 순서로 읽으므로 정렬 단계가 사라지고, LIMIT 20에 닿자마자 멈춥니다. 쿼리를 고친 뒤에는 이렇게 항상 실행 계획으로 확인하는 습관을 들입니다.

매일 보는 곳

JPA가 만든 쿼리를 꺼내서 EXPLAIN 하기

  1. SQL 로그를 켭니다: spring.jpa.properties.hibernate.format_sql=true + logging.level.org.hibernate.SQL=debug
  2. 바인딩 값(?)까지 보려면 logging.level.org.hibernate.orm.jdbc.bind=trace(Hibernate 6) 또는 p6spy 같은 도구를 씁니다.
  3. 로그의 SQL에 값을 채워 DB 콘솔에서 EXPLAIN을 실행합니다.

ORM을 쓰면 SQL을 직접 안 쓰니 실행 계획을 잊기 쉽습니다. 느린 API가 있으면 "어떤 SQL이 몇 번 나가는지"(24편 N+1)와 "각 SQL의 실행 계획"을 차례로 봅니다.

실수 예시

개발 DB에서는 빨랐는데 운영에서 느리다

개발 DB의 주문이 500건이면 풀 스캔도 1ms라 문제가 안 보입니다. 게다가 옵티마이저는 데이터가 적으면 일부러 인덱스를 안 쓰기도 해서, 개발 DB의 실행 계획은 운영과 다를 수 있습니다.

해결: 운영과 비슷한 규모의 데이터가 있는 환경(스테이징, 운영 복제본)에서 실행 계획을 확인하고, 운영에서는 슬로우 쿼리 로그(예: long_query_time=1)를 켜 두어 느린 쿼리를 계속 수집합니다.

지금은 넘어가도 되는 것 · 옵티마이저 비용 모델, 모든 type·Extra 값 암기, 조인 알고리즘(Nested Loop·Hash Join) 세부, 옵티마이저 힌트, PostgreSQL EXPLAIN 형식 (원리는 같음)

5설명해보기

답을 열기 전에 먼저 소리 내어 설명해 보세요.

EXPLAIN 결과에서 가장 먼저 보는 네 칸과 그 이유는?
key로 인덱스를 실제로 쓰는지, type으로 콕 집어 읽는지 전체를 훑는지, rows로 반환 건수에 비해 얼마나 많이 읽는지, Extra로 별도 정렬이나 임시 테이블 같은 추가 작업이 있는지를 봅니다.
type=ALL, rows=500000, Extra=Using filesort는 무엇을 의미하고, 무엇을 해야 하나요?
인덱스 없이 테이블 전체 50만 행을 읽고, 결과를 별도로 정렬한다는 뜻입니다. WHERE 조건과 ORDER BY 컬럼을 함께 커버하는 복합 인덱스를 검토하고, 조건이 인덱스를 못 타는 모양(함수 적용, 형변환 등)인지 확인합니다.
EXPLAIN과 EXPLAIN ANALYZE의 차이는?
EXPLAIN은 실행하지 않고 통계 기반의 예상 계획과 추정 행 수를 보여 주고, EXPLAIN ANALYZE는 쿼리를 실제로 실행해 단계별 실제 시간과 행 수를 보여 줍니다. 추정과 실제가 크게 다르면 통계 갱신을 검토합니다.
