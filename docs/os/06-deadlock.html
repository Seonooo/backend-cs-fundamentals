데드락

05에서 락으로 경쟁 조건을 막았습니다. 그런데 락을 두 개 이상 쓰기 시작하면, 서로가 가진 락을 기다리며 영원히 멈추는 상황이 생길 수 있습니다. 백엔드에서는 자바 코드보다 DB와 커넥션 풀에서 더 자주 만납니다.

1. 개념: 서로가 서로를 기다린다2. 가장 자주 만나는 곳: DB 데드락3. 실무 예시4. 설명해보기

1개념: 서로가 서로를 기다린다

A는 자원 1을 쥔 채 자원 2를 기다리고, B는 자원 2를 쥔 채 자원 1을 기다립니다. 둘 다 상대가 놓기 전까지 자기 것을 놓지 않으니, 누구도 진행할 수 없습니다.

데드락이 생기는 네 가지 조건

아래 네 가지가 모두 성립해야 데드락이 생깁니다. 거꾸로 말하면, 하나만 깨도 막을 수 있습니다.

조건뜻실무에서 깨는 방법
상호 배제자원을 한 번에 하나만 쓸 수 있음락 자체가 이 조건이라 보통 못 깸
점유 대기하나를 쥔 채로 다른 것을 기다림필요한 것을 한 번에 잡기
비선점남의 락을 빼앗을 수 없음타임아웃: 오래 기다리면 포기하고 놓기
순환 대기기다림이 원을 이룸락 순서 고정 ← 가장 많이 씀
실무 원칙 두 가지 — ① 여러 자원을 잠글 때는 항상 같은 순서로 (예: id가 작은 것부터). ② 락 대기에는 타임아웃을 둔다. 이 둘로 대부분이 해결됩니다.

2가장 자주 만나는 곳: DB 데드락

DB는 UPDATE·DELETE 하는 행에 락을 겁니다(22편). 두 트랜잭션이 같은 행들을 반대 순서로 수정하면 1번 그림과 똑같은 원이 생깁니다.

애플리케이션 로그에 찍히는 메시지 (MySQL)
Deadlock found when trying to get lock; try restarting transaction
// Spring에서는 보통 CannotAcquireLockException / DeadlockLoserDataAccessException 계열로 감싸져 올라옴

3실무 예시

실수 예시

A→B 송금과 B→A 송금이 동시에 일어났다

보내는 사람 계좌부터 잠그면, 두 송금이 서로 반대 순서로 계좌를 잠급니다.

✕ 요청마다 잠그는 순서가 다름
void transfer(Long from, Long to, long amt) {
  Account a = repo.findByIdForUpdate(from);
  Account b = repo.findByIdForUpdate(to);
  a.withdraw(amt); b.deposit(amt);
}
// 1→2 송금: 1, 2 순서로 잠금
// 2→1 송금: 2, 1 순서로 잠금 → 데드락
✓ 항상 id 작은 쪽부터
void transfer(Long from, Long to, long amt) {
  Long first  = Math.min(from, to);
  Long second = Math.max(from, to);
  repo.findByIdForUpdate(first);
  repo.findByIdForUpdate(second);
  // 이후 출금·입금 처리
}
// 어느 방향이든 1 → 2 순서 → 순환 불가

여러 행을 한 번에 수정하는 배치도 같은 원리입니다. 대상 id를 정렬한 뒤 처리하면 배치끼리 데드락이 나지 않습니다.

실수 예시

커넥션 풀 데드락: 요청 하나가 커넥션을 두 개 필요로 한다

주문 트랜잭션 안에서 로그 저장을 @Transactional(propagation = REQUIRES_NEW)로 분리했습니다. REQUIRES_NEW는 새 커넥션을 하나 더 씁니다. 평소엔 괜찮다가 트래픽이 몰리면 서버 전체가 멈춥니다.

해결: 요청 하나가 커넥션을 동시에 여러 개 잡지 않게 설계하는 것이 우선입니다(로그 저장을 트랜잭션 밖으로 빼거나 비동기로). 불가피하다면 풀 크기를 "동시 요청 수 × (요청당 필요한 커넥션 수 − 1) + 1" 이상으로 잡아야 합니다 (23편).

실수 예시

같은 스레드 풀 안에서 하위 작업을 기다린다

크기 4인 스레드 풀에서 실행되는 작업이, 같은 풀에 하위 작업을 넣고 그 결과를 .join()으로 기다립니다. 상위 작업 4개가 풀을 다 차지하면, 하위 작업은 실행될 스레드가 없어 영원히 대기열에 머뭅니다. 커넥션 풀 데드락과 같은 모양입니다.

해결: 상위 작업과 하위 작업의 풀을 분리하고, 대기에는 타임아웃을 둡니다 (07편).

장애 대응

데드락 에러를 받았을 때

  1. 재시도: DB가 롤백한 쪽은 트랜잭션 전체를 다시 실행하면 대개 성공합니다. 재시도 횟수는 제한합니다.
  2. 원인 확인: MySQL은 SHOW ENGINE INNODB STATUS의 LATEST DETECTED DEADLOCK에 어떤 두 쿼리가 어떤 락을 잡고 있었는지 나옵니다.
  3. 근본 해결: 두 쿼리가 잠그는 순서를 맞추거나, 트랜잭션을 짧게 줄여 겹칠 확률을 낮춥니다.

자바 코드 안의 데드락은 스레드 덤프 맨 아래에 Found one Java-level deadlock이라고 JVM이 직접 알려 줍니다. 다만 JVM은 DB 락이나 커넥션 풀 대기는 데드락으로 감지하지 못합니다.

4설명해보기

답을 열기 전에 먼저 소리 내어 설명해 보세요.

데드락이 무엇이고, 실무에서 가장 많이 쓰는 예방법은?
둘 이상의 작업이 서로가 가진 자원을 기다리며 영원히 진행하지 못하는 상태입니다. 순환 대기를 깨기 위해 락을 잡는 순서를 항상 같게 고정하는 것이 가장 흔한 예방법이고, 락 대기에 타임아웃을 두는 것도 함께 씁니다.
A→B와 B→A 송금이 동시에 일어날 때 데드락을 막는 방법은?
송금 방향과 관계없이 계좌 id가 작은 쪽부터 잠급니다. 그러면 두 트랜잭션이 같은 순서로 락을 요청하므로 순환 대기가 생길 수 없습니다.
DB에서 데드락 에러가 나면 애플리케이션은 어떻게 대응해야 하나요?
DB가 한 트랜잭션을 롤백했으므로 그 트랜잭션 전체를 제한된 횟수만큼 재시도합니다. 동시에 데드락 로그로 어떤 쿼리들이 충돌했는지 확인해 락 순서를 맞추거나 트랜잭션을 짧게 만드는 근본 해결을 합니다.
REQUIRES_NEW를 쓰면 왜 커넥션 풀이 멈출 수 있나요?
REQUIRES_NEW는 기존 트랜잭션의 커넥션을 쥔 채 새 커넥션을 하나 더 요청합니다. 동시 요청 수가 풀 크기만큼 되면 모두 하나씩 쥔 채 두 번째를 기다리게 되어, 아무도 끝나지 못하는 데드락 상태가 됩니다.
