컨텍스트 스위칭과 CPU·I/O 바운드

톰캣 스레드는 기본 200개인데, 서버 CPU 코어는 4개뿐입니다. 이게 어떻게 가능하고, 왜 괜찮은지를 이해하면 "스레드를 몇 개 둘까"와 "스레드 덤프에서 무엇을 봐야 하나"에 답할 수 있습니다.

1코어 하나는 한 번에 스레드 하나만 실행한다

CPU 코어가 4개면, 어느 한 순간 진짜로 실행 중인 스레드는 최대 4개입니다. 나머지 스레드는 차례를 기다립니다. OS는 아주 짧은 시간(수 ms) 단위로 실행할 스레드를 바꿔 가며, 모두가 동시에 도는 것처럼 보이게 합니다.

컨텍스트 스위칭은 실행 중이던 스레드의 상태(어디까지 실행했는지 등)를 저장하고, 다음 스레드의 상태를 불러오는 작업입니다. 한 번은 수 µs 수준으로 짧지만, CPU 캐시에 올라와 있던 데이터도 쓸모없어지기 때문에 스레드가 지나치게 많아 전환이 잦아지면 일보다 전환에 시간을 쓰게 됩니다.

2CPU 바운드 vs I/O 바운드

그렇다면 스레드는 코어 수만큼만 두는 게 좋을까요? 작업이 CPU를 쓰는지, 기다리는지에 따라 다릅니다.

I/O 바운드CPU 바운드
예DB 조회, 외부 API 호출, 파일 읽기이미지 리사이즈, 암호화·해시, 대용량 엑셀 생성
시간 대부분응답을 기다림계산함
적당한 스레드 수코어 수보다 훨씬 많이코어 수 근처
스레드를 늘리면대기 시간을 겹쳐 처리량 증가빨라지지 않고 전환 비용만 증가
출발점 공식 — 스레드 수 ≈ 코어 수 × (1 + 대기 시간 ÷ CPU 시간)
예: 4코어, 요청당 CPU 10ms + 대기 90ms → 4 × (1 + 9) = 40개. 정답이 아니라 출발점이고, 실제 값은 부하 테스트로 맞춥니다.

3Java 스레드 상태 — 스레드 덤프를 읽는 열쇠

스레드 덤프를 뜨면 각 스레드 옆에 상태가 찍힙니다. 이 상태로 "지금 뭘 하고 있나"를 판단합니다.

주의: 소켓에서 DB·API 응답을 기다리는 스레드는 WAITING이 아니라 RUNNABLE로 찍힙니다. JVM이 볼 때는 OS 안에서 읽기를 실행 중이기 때문입니다. 그래서 RUNNABLE이라고 다 일하는 중은 아니고, 스택의 맨 윗줄을 함께 봐야 합니다.

설계 이유

톰캣 스레드가 코어 수보다 훨씬 많은 이유

4코어 서버에서 톰캣 스레드를 4개로 두면, 네 요청이 모두 DB 응답을 기다리는 동안 CPU는 놀고 있는데 다섯 번째 요청은 들어오지도 못합니다. 웹 요청은 대부분 I/O 바운드라서, 기다리는 시간을 다른 요청으로 채우기 위해 기본값이 200개처럼 크게 잡혀 있습니다.

실수 예시

요청 스레드에서 무거운 계산을 돌렸다

관리자 페이지의 "엑셀 다운로드"가 수십 초 동안 CPU를 쓰는데, 이를 일반 API와 같은 톰캣 스레드에서 처리했습니다. 여러 명이 동시에 누르자 코어가 꽉 차서, CPU를 거의 쓰지 않는 일반 API까지 차례를 기다리며 느려집니다.

해결: CPU 바운드 작업은 코어 수 근처 크기의 별도 스레드 풀이나 배치로 분리하고, 사용자에게는 "생성 중 → 완료되면 다운로드" 방식으로 응답합니다 (07편).

5설명해보기

답을 열기 전에 먼저 소리 내어 설명해 보세요.

컨텍스트 스위칭이란 무엇이고, 왜 스레드가 너무 많으면 손해인가요?
코어에서 실행할 스레드를 바꿀 때 이전 스레드의 실행 상태를 저장하고 다음 스레드의 상태를 불러오는 작업입니다. 그동안에는 실제 일이 진행되지 않고 CPU 캐시도 식습니다. 스레드가 코어에 비해 지나치게 많으면 전환이 잦아져 처리량이 오히려 떨어집니다.
외부 API 호출이 대부분인 서버의 스레드 풀을 코어 수(4)로 두면 어떻게 되나요?
스레드 4개가 모두 응답을 기다리는 동안 CPU는 놀지만 새 요청은 큐에서 대기합니다. I/O 바운드 작업은 대기 비율만큼 스레드를 더 두어야 CPU를 활용할 수 있습니다. (또는 08편의 가상 스레드, 17편의 논블로킹 방식)
스레드 덤프에서 대부분이 BLOCKED라면 무엇을 의심하나요?
여러 스레드가 같은 synchronized 락을 기다리는 락 경합입니다. 덤프에서 그 락을 잡고 있는 스레드가 무엇을 하는지 확인하고, 락 안에서 느린 작업(I/O 등)을 하고 있지 않은지, 임계 영역을 줄일 수 있는지 봅니다.
DB 응답을 기다리는 스레드가 덤프에서 RUNNABLE로 보이는 이유는?
JVM 입장에서는 소켓 읽기라는 네이티브 코드를 실행 중이기 때문입니다. 실제로는 OS 안에서 데이터가 오기를 기다리는 중이라, 상태만 보지 말고 스택 맨 위의 메서드를 함께 봐야 합니다.
