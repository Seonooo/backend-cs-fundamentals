격리 수준과 MVCC

05편에서 "한 스레드가 바꾼 값이 다른 스레드에 언제 보이나"(가시성)를 봤습니다. DB에서도 똑같은 질문이 나옵니다. 동시에 도는 트랜잭션끼리 서로의 변경을 언제, 얼마나 보나? 이것을 정하는 것이 격리 수준이고, 요즘 DB가 이를 구현하는 방식이 MVCC입니다.

1격리가 약하면 생기는 현상

현상무슨 일예
Dirty Read다른 트랜잭션이 아직 커밋 안 한 값을 읽음곧 롤백될 잔액을 보고 결제 승인
Non-Repeatable Read같은 행을 두 번 읽었는데 값이 다름트랜잭션 중간에 다른 쪽이 가격을 바꿔 커밋
Phantom Read같은 조건으로 두 번 조회했는데 행이 늘거나 줄음"오늘 주문 수"를 두 번 셌는데 다름

2격리 수준: 어디까지 막을까

격리 수준DirtyNon-RepeatablePhantom비고
READ UNCOMMITTED발생발생발생거의 안 씀
READ COMMITTED막음발생발생PostgreSQL·Oracle 기본값
REPEATABLE READ막음막음표준상 발생*MySQL InnoDB 기본값
SERIALIZABLE막음막음막음가장 안전, 가장 느림

* MySQL InnoDB의 REPEATABLE READ는 일반 조회(스냅샷 읽기)에서 팬텀도 대부분 보이지 않습니다. 위로 갈수록 동시성이 좋고, 아래로 갈수록 안전하지만 느립니다.

3MVCC: 읽기는 과거 사진을 본다

MVCC(다중 버전 동시성 제어)는 행을 수정할 때 이전 버전을 남겨 두고, 읽는 쪽에는 자기 기준 시점의 버전을 보여 주는 방식입니다. 덕분에 일반 SELECT(스냅샷 읽기)와 쓰기는 서로를 막지 않습니다. 단, SELECT … FOR UPDATE 같은 잠금 읽기나 쓰기끼리는 여전히 서로 기다립니다(22편). 읽는 트랜잭션이 락을 기다리지 않으니 조회가 많은 서비스에서 성능이 좋습니다.

4MVCC로 못 막는 것: 갱신 손실

격리 수준이 REPEATABLE READ여도 "읽고 → 애플리케이션에서 계산하고 → 쓰기" 패턴은 깨집니다. 05편의 count++와 똑같은 모양이 DB에서 반복되는 것입니다.

해결 방법모양자세히
원자적 UPDATEUPDATE account SET balance = balance - 30 WHERE id = ? AND balance >= 30계산을 DB에 맡김 · 가장 단순
비관적 락SELECT … FOR UPDATE로 읽을 때부터 잠금22편
낙관적 락버전 컬럼으로 "내가 읽은 뒤 바뀌었나" 확인22편

PostgreSQL의 REPEATABLE READ는 이 상황에서 B의 쓰기를 에러(could not serialize access)로 거부해 재시도하게 만듭니다. DB마다 동작이 다르다는 점도 기억해 둡니다.

5실무 예시

실수 예시

포인트 차감이 가끔 틀린다

JPA로 이렇게 작성했습니다. 로컬에서는 정확한데, 같은 사용자가 두 기기에서 동시에 결제하면 4번 그림처럼 차감 하나가 사라집니다.

✕ 읽고-계산하고-쓰기
@Transactional
public void use(Long id, int amount) {
  Point p = pointRepo.findById(id).get(); // 스냅샷 읽기
  p.setBalance(p.getBalance() - amount);  // 앱에서 계산
}   // 커밋 시 UPDATE … SET balance = 계산값
✓ DB에서 원자적으로
@Modifying
@Query("""
  update Point p set p.balance = p.balance - :amt
  where p.id = :id and p.balance >= :amt
""")
int use(Long id, int amt);
// 반환값 0이면 잔액 부족 → 실패 처리

벌크 UPDATE는 JPA의 영속성 컨텍스트를 거치지 않으므로, 같은 트랜잭션에서 이후 그 엔티티를 다시 읽을 때 주의합니다 (24편).

실수 예시

트랜잭션 안에서 기다렸는데 값이 안 바뀐다

하나의 긴 트랜잭션 안에서 "상태가 COMPLETED가 될 때까지 1초마다 조회"하는 코드를 짰습니다. 다른 요청이 이미 COMPLETED로 바꿔 커밋했는데도 영원히 옛 값을 봅니다. MySQL의 REPEATABLE READ에서는 트랜잭션이 처음 본 사진을 계속 보여 주기 때문입니다(3번 그림 왼쪽).

해결: 폴링은 트랜잭션 밖에서, 조회할 때마다 짧은 트랜잭션으로 합니다. 애초에 트랜잭션을 길게 열어 두는 것 자체가 커넥션과 옛 버전 보관 비용을 늘립니다.

설계 이유

격리 수준을 올리면 다 해결되지 않나?

SERIALIZABLE로 올리면 이상 현상은 사라지지만, 조회까지 락을 걸거나 충돌 시 에러를 내서 동시 처리량이 크게 떨어지고 데드락(06편)도 늘어납니다. 실무에서는 보통 DB 기본 격리 수준을 유지하고, 정확성이 꼭 필요한 곳(잔액, 재고, 쿠폰)에만 원자적 UPDATE나 락을 적용합니다.

지금은 넘어가도 되는 것 · Undo 로그와 Read View의 내부 구조, 스냅샷 격리와 SERIALIZABLE의 이론적 차이(write skew 등), 각 DB의 팬텀 처리 방식 세부

6설명해보기

답을 열기 전에 먼저 소리 내어 설명해 보세요.

MVCC가 무엇이고, 어떤 이점이 있나요?
행을 수정할 때 이전 버전을 남겨 두고, 읽는 트랜잭션에는 자기 기준 시점의 버전을 보여 주는 방식입니다. 읽기가 락을 걸지 않아 읽기와 쓰기가 서로를 기다리지 않으므로 동시 처리 성능이 좋습니다.
REPEATABLE READ인데 "잔액 조회 후 차감" 로직에서 금액이 틀어졌다. 왜인가요?
MVCC의 스냅샷 읽기는 락을 걸지 않아, 두 트랜잭션이 같은 잔액을 읽고 각자 계산한 값으로 덮어쓰는 갱신 손실이 생깁니다. 원자적 UPDATE(balance = balance - ?), SELECT FOR UPDATE, 낙관적 락으로 막아야 합니다.
MySQL과 PostgreSQL의 기본 격리 수준은? 차이가 체감되는 상황은?
MySQL InnoDB는 REPEATABLE READ, PostgreSQL은 READ COMMITTED입니다. 한 트랜잭션 안에서 같은 데이터를 여러 번 읽을 때 MySQL은 처음 본 값을 계속 보여 주고, PostgreSQL은 매번 최신 커밋 값을 보여 줍니다.
