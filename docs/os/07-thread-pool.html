스레드 풀과 비동기 처리

01에서 "스레드는 만드는 비용이 있으니 만들어 두고 돌려쓴다"고 했습니다. 이 풀링 패턴은 앞으로 HTTP 커넥션 풀(15편), DB 커넥션 풀(23편)에서 똑같이 반복됩니다. 여기서 풀의 동작을 제대로 익혀 두면 나머지 둘은 거의 공짜로 이해됩니다.

1. 스레드 풀은 작업을 이렇게 받는다2. 스프링에서 만나는 스레드 풀3. 실무 예시4. 설명해보기

1스레드 풀은 작업을 이렇게 받는다

자바의 ThreadPoolExecutor(스프링의 ThreadPoolTaskExecutor도 내부는 같음)는 작업이 들어올 때 아래 순서로 판단합니다. 큐가 스레드 추가보다 먼저라는 점이 가장 많이 헷갈리는 부분입니다.

참고: 톰캣의 요청 스레드 풀은 자체 구현이라 반대로 동작합니다. 스레드를 max(기본 200)까지 먼저 늘린 뒤에 큐에 쌓습니다. 위 규칙은 ThreadPoolExecutor·ThreadPoolTaskExecutor(@Async 등)에 해당합니다.

설정의미기억할 점
corePoolSize평소 유지하는 스레드 수04편의 공식으로 출발점 잡기
queueCapacity스레드가 모두 바쁠 때 대기할 수 있는 작업 수무한이면 max는 영원히 안 쓰임
maxPoolSize큐가 가득 찼을 때 늘릴 수 있는 최대치순간 폭주 대비용
거부 정책다 찼을 때의 처리AbortPolicy: 예외 / CallerRunsPolicy: 제출한 스레드가 직접 실행(자연스러운 속도 조절)
풀링의 공통 질문 세 가지 — ① 몇 개까지 둘까(크기) ② 다 쓰고 있으면 어떻게 기다릴까(대기열·타임아웃) ③ 그래도 안 되면 어떻게 할까(거부). 15편 HTTP 커넥션 풀, 23편 DB 커넥션 풀에서도 똑같이 이 세 가지를 묻게 됩니다.

2스프링에서 만나는 스레드 풀

쓰는 방법설정 안 하면 쓰는 풀주의
@Async스프링 부트가 만든 기본 풀 (core 8, 큐 무제한)용도별 전용 Executor를 만들어 이름으로 지정
CompletableFuture.supplyAsync(…)JVM 공용 ForkJoinPool (코어 수 − 1개)공용 풀에서 블로킹 I/O를 하면 JVM 전체가 영향 → Executor를 꼭 넘기기
요청 처리톰캣 스레드 풀 (max 200)느린 작업이 이 풀을 다 차지하지 않게

스프링 부트 3.2+에서 가상 스레드를 켜면 기본 동작이 달라집니다 (08편). 사용하는 버전의 문서를 한 번 확인하세요.

3실무 예시

좋은 패턴

주문 후 알림 발송을 @Async 전용 풀로 분리

주문 API가 알림 발송(외부 API)까지 기다리면 응답이 느려지고, 알림 서버 장애가 주문 실패로 번집니다. 부가 작업은 전용 풀로 넘기고 바로 응답합니다.

✓ 전용 Executor 정의 후 이름으로 지정
@Bean(name = "notifyExecutor")
public ThreadPoolTaskExecutor notifyExecutor() {
    ThreadPoolTaskExecutor ex = new ThreadPoolTaskExecutor();
    ex.setCorePoolSize(4);
    ex.setMaxPoolSize(8);
    ex.setQueueCapacity(500);                          // 유한한 큐
    ex.setThreadNamePrefix("notify-");                 // 로그·덤프에서 식별
    ex.setRejectedExecutionHandler(new ThreadPoolExecutor.CallerRunsPolicy());
    return ex;
}

@Async("notifyExecutor")
public void sendOrderNotification(Long orderId) { … }

@Async도 @Transactional처럼 프록시로 동작하므로, 같은 클래스 안에서 호출하면 비동기로 실행되지 않습니다. 별도 빈으로 분리해서 호출합니다.

실수 예시

무한 큐 때문에 장애를 늦게 알았다

Executors.newFixedThreadPool(10)은 내부적으로 크기 제한이 없는 큐를 씁니다. 처리 속도보다 작업이 빨리 들어오면 거부되지 않고 큐에 끝없이 쌓입니다.

  • 큐에 쌓인 작업만큼 힙 메모리가 늘어남 → 결국 OOM (02편)
  • 작업이 실행되기까지 몇 분씩 걸려도 에러가 나지 않아 문제를 늦게 발견
  • max를 20으로 설정해도 큐가 절대 차지 않으니 스레드는 10개에서 늘지 않음

해결: 큐 크기를 유한하게 정하고, 거부 시 동작(예외 + 알람, 또는 CallerRuns)을 명시합니다. 운영에서는 풀의 활성 스레드 수와 큐 길이를 모니터링합니다.

좋은 패턴

외부 API 세 곳을 병렬로 호출

상품 상세 화면에 재고·리뷰·추천을 각각 다른 서버에서 가져옵니다. 순서대로 부르면 세 응답 시간의 합, 병렬로 부르면 가장 느린 하나의 시간이 됩니다.

✓ 전용 풀 + 타임아웃
var stock   = CompletableFuture.supplyAsync(() -> stockClient.get(id),  apiExecutor);
var reviews = CompletableFuture.supplyAsync(() -> reviewClient.get(id), apiExecutor);
var recs    = CompletableFuture.supplyAsync(() -> recClient.get(id),    apiExecutor)
                  .completeOnTimeout(List.of(), 300, TimeUnit.MILLISECONDS); // 추천은 없어도 됨

CompletableFuture.allOf(stock, reviews, recs).join();

Executor를 넘기지 않으면 공용 ForkJoinPool에서 블로킹 호출이 실행되어, 같은 풀을 쓰는 다른 코드(병렬 스트림 등)까지 느려집니다.

실수 예시

스레드를 재사용하기 때문에 생기는 ThreadLocal 문제

풀의 스레드는 요청이 끝나도 죽지 않고 다음 요청을 받습니다. 그래서 ThreadLocal에 넣은 값을 지우지 않으면, 다음 요청(다른 사용자)이 그 값을 봅니다. 01편의 싱글톤 필드 문제와 같은 결과입니다.

✓ 쓰고 나면 반드시 지우기
try {
    UserContext.set(user);
    chain.doFilter(req, res);
} finally {
    UserContext.clear();   // ThreadLocal.remove()
}

반대로 ThreadLocal에 담긴 값(로그 추적 ID인 MDC, 보안 컨텍스트)은 @Async로 넘어간 다른 스레드에는 자동으로 전달되지 않습니다. 스프링에서는 TaskDecorator로 복사해 넘깁니다.

장애 대응

톰캣 스레드 200개가 한 곳에 묶였다

결제사 API가 느려지자, 결제 요청을 처리하던 톰캣 스레드들이 전부 응답을 기다리며 묶였습니다. 그러자 결제와 무관한 상품 조회 API까지 스레드를 못 받아 멈춥니다. 한 기능의 느림이 서버 전체 장애가 된 것입니다.

해결: 외부 호출에 짧은 타임아웃을 두고, 느려질 수 있는 호출은 전용 풀로 격리(벌크헤드)해서 그 풀만 막히게 합니다. 자세한 내용은 16편에서 다룹니다.

4설명해보기

답을 열기 전에 먼저 소리 내어 설명해 보세요.

core 10, max 50, 큐 무제한인 풀에 작업이 폭주하면 스레드는 몇 개까지 늘어나나요?
10개에서 늘지 않습니다. core만큼 스레드가 찬 뒤 새 작업은 큐에 들어가는데, 큐가 무제한이라 절대 가득 차지 않으므로 max까지 늘어나는 단계에 도달하지 않습니다. 작업은 큐에 계속 쌓이고 메모리와 대기 시간이 늘어납니다.
@Async를 쓸 때 전용 Executor를 지정해야 하는 이유는?
기본 풀은 여러 용도가 함께 쓰고 큐가 무제한이라, 한 종류의 작업이 몰리면 다른 비동기 작업까지 밀리고 문제가 늦게 드러납니다. 용도별로 크기와 큐, 거부 정책을 정한 전용 풀을 두면 격리와 모니터링이 쉬워집니다.
스레드 풀에서 ThreadLocal을 쓸 때 주의할 점은?
스레드가 재사용되므로 요청이 끝날 때 값을 지우지 않으면 다음 요청이 이전 사용자의 값을 보게 됩니다. finally에서 remove해야 합니다. 또 ThreadLocal 값은 다른 스레드(@Async)로 자동 전달되지 않습니다.
스레드 풀, HTTP 커넥션 풀, DB 커넥션 풀의 공통점은?
만드는 비용이 큰 자원을 미리 만들어 재사용하고, 크기 상한이 있어 다 쓰고 있으면 대기가 생기며, 대기에 타임아웃이나 거부 정책이 없으면 고갈이 장애로 번진다는 점입니다.
