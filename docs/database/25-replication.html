복제와 읽기/쓰기 분리

대부분의 서비스는 쓰기보다 읽기가 훨씬 많습니다. 그래서 DB를 복제(replication)해 읽기 요청을 복사본으로 나눕니다. 서버를 늘리는 가장 흔한 방법이지만, 그 대가로 "복사본은 조금 늦을 수 있다"는 일관성 문제가 따라옵니다. 10편의 DNS TTL과 같은 종류의 트레이드오프입니다.

1. 구조: 쓰기는 하나로, 읽기는 여럿으로2. 복제 지연: 방금 쓴 것이 안 보인다3. 스프링에서 나누는 방법4. 실무 예시5. 설명해보기

1구조: 쓰기는 하나로, 읽기는 여럿으로

2복제 지연: 방금 쓴 것이 안 보인다

평소 복제 지연은 수 ms~수백 ms지만, Primary에 쓰기가 몰리거나 Replica에서 무거운 쿼리가 돌면 수 초 이상 벌어지기도 합니다. 그 사이에 Replica를 읽으면 옛 값이 보입니다.

원칙 — 쓰기 직후 바로 그 결과를 읽어야 하는 흐름(가입 후 내 정보, 주문 후 주문 상세, 결제 후 잔액)은 Primary에서 읽습니다. 조금 늦어도 괜찮은 조회(목록, 통계, 검색)만 Replica로 보냅니다.

3스프링에서 나누는 방법

흔한 방식은 @Transactional(readOnly = true)이면 Replica, 아니면 Primary로 보내는 것입니다. AbstractRoutingDataSource로 현재 트랜잭션이 읽기 전용인지 보고 데이터소스를 고릅니다.

핵심 부분만
public class ReplicationRoutingDataSource extends AbstractRoutingDataSource {
    @Override
    protected Object determineCurrentLookupKey() {
        return TransactionSynchronizationManager.isCurrentTransactionReadOnly()
                ? "replica" : "primary";
    }
}

// 주의: 트랜잭션 속성이 정해진 "뒤에" 커넥션을 얻도록 감싸야 라우팅이 동작함
@Bean @Primary
public DataSource dataSource(DataSource routingDataSource) {
    return new LazyConnectionDataSourceProxy(routingDataSource);
}

LazyConnectionDataSourceProxy가 없으면 트랜잭션 매니저가 readOnly 여부를 표시하기 전에 커넥션을 먼저 얻어 버려서, 항상 Primary로만 가는 문제가 생깁니다. 이 구성은 팀·프레임워크 버전에 따라 방식이 다르니 기존 설정을 먼저 확인합니다.

4실무 예시

실수 예시

회원가입 직후 "내 정보"가 가끔 404

2번 그림 그대로입니다. 가입 API는 Primary에 쓰고, 프론트엔드가 곧바로 호출한 내 정보 API는 readOnly = true라 Replica로 갔습니다.

  • 가입 응답에 필요한 정보를 바로 담아 돌려주어, 직후 조회 자체를 없앱니다.
  • 또는 "방금 쓴 사용자"의 조회는 짧은 시간 동안 Primary로 보냅니다.
  • 재시도로 해결하는 건 증상만 가리므로 피합니다.
실수 예시

readOnly 메서드 안에서 쓰기를 했다

조회 메서드에 @Transactional(readOnly = true)를 붙였는데, 그 안에서 "조회수 +1" 같은 쓰기를 합니다. Replica로 라우팅되면 쓰기가 거부됩니다.

MySQL 에러
The MySQL server is running with the --read-only option so it cannot execute this statement

라우팅이 없더라도 JPA는 readOnly 트랜잭션에서 변경 감지를 생략할 수 있어, 엔티티를 바꿔도 UPDATE가 안 나가는 식으로 조용히 무시되기도 합니다. 쓰기는 쓰기 트랜잭션에서 합니다.

장애 대응

Replica를 늘렸는데 복제 지연이 오히려 커졌다

관리자 통계 화면의 무거운 집계 쿼리를 Replica로 보냈더니, Replica가 바빠서 복제 반영이 밀리고 일반 사용자 조회까지 옛 데이터를 보게 됐습니다. 모니터링에서 복제 지연 시간(MySQL Seconds_Behind_Source 등)을 항상 봅니다. 분석·통계용 쿼리는 사용자용과 분리된 Replica로 보내는 것이 안전합니다.

설계 이유

"복사본은 늦을 수 있다"는 곳곳에 있다

복사본원본늦을 수 있는 이유편
DNS 캐시권한 네임서버TTL10
영속성 컨텍스트DB 행벌크 UPDATE가 우회24

빠르게 하려고 복사본을 두면, "얼마나 늦어도 괜찮은가"를 기능마다 정해야 합니다. 이 질문이 마지막 26편 캐시의 핵심입니다.

답을 열기 전에 먼저 소리 내어 설명해 보세요.

읽기/쓰기 분리의 장점과 대가는?
읽기 요청을 여러 Replica로 나눠 Primary 부하를 줄이고 읽기 처리량을 늘릴 수 있습니다. 대신 복제가 비동기라 Replica가 잠시 늦을 수 있어, 쓰기 직후 읽기에서 옛 값이 보이는 일관성 문제가 생깁니다.
회원가입 직후 내 정보 조회가 가끔 404가 나는 원인과 해결책은?
가입은 Primary에 쓰였지만 조회는 Replica로 갔고, 복제가 아직 반영되지 않았기 때문입니다. 쓰기 직후 읽기는 Primary로 보내거나, 쓰기 응답에 필요한 데이터를 담아 직후 조회를 없앱니다.
readOnly 기반 라우팅에 LazyConnectionDataSourceProxy가 필요한 이유는?
트랜잭션 매니저가 트랜잭션을 시작하며 readOnly 여부를 표시하기 전에 커넥션을 먼저 얻으면, 라우팅 시점에는 읽기 전용인지 알 수 없어 항상 기본(Primary)으로 갑니다. 실제 쿼리를 실행할 때까지 커넥션 획득을 미뤄 올바른 데이터소스를 고르게 합니다.
