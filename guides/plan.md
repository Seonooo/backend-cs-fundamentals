# 실행 계획 파일

> **읽는 시점**: 새 작업을 시작하며 `plan/do/`에 계획 파일을 만들 때, 또는 계획을 완료 처리할 때.

## 흐름
1. **시작**: `plan/do/YYYY-MM-DD-slug.md`를 만듭니다. 날짜는 작업 시작일이고, slug는 작업을 나타내는 짧은 영어 이름입니다(예: `2026-10-01-redis-intro.md`).
2. **진행**
   - 계획 파일의 단계 순서대로 진행합니다.
   - 사용자와 결정이 필요한 단계는 현재 상태와 수정안을 보여 주고 결정을 받습니다.
   - 단계가 끝날 때마다 체크하고, 결정과 결과를 "결정 / 메모"에 적습니다.
3. **완료**
   - 완료 처리 전에 "발생한 문제와 재발 방지" 절을 채웁니다. 문제가 없었으면 "없음"이라고 적습니다. 문제가 있었으면 `guides/lessons.md`에 L 번호로 기록했는지 확인합니다.
   - 모든 단계가 체크되면 상태를 "완료"로 바꾸고, 완료일과 결과 커밋을 적습니다.
   - 그다음 파일을 `plan/done/`으로 옮깁니다(`plan/`은 git 제외 대상이라 일반 `mv`).
4. **보류**: 당장 하지 않을 계획은 상태를 "보류"로 두고, 언제 진행할지(선행 조건)를 적습니다.

## 형식

```markdown
# 작업 제목

- **상태**: 진행 중 | 완료 | 보류
- **시작일**: YYYY-MM-DD
- **완료일**: YYYY-MM-DD (완료 시)
- **결과 커밋**: `해시` (완료 시)

## 목표
왜 하는지, 끝났을 때 무엇이 달라지는지. 관련·선행 계획이 있으면 파일명으로 적음

## 단계
| 단계 | 상태 | 내용 | 대상 파일 |
|---|---|---|---|
| 1 | [ ] | … | … |

## 항목별 결정 / 메모
### [ ] 1 · 제목
- **현재**: …
- **수정안**: …
- **결정 / 메모**: (날짜) 결정 내용

## 검증
이 작업에 해당하는 검사 명령과 눈으로 확인할 항목

## 발생한 문제와 재발 방지 (완료 전 필수)
| 문제 | lessons 번호 | 장치 |
|---|---|---|
| … (없으면 "없음") | L-NN | 검사 규칙 / hook / guide 한 줄 / 기록만 |
```
