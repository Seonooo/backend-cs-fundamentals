Redis: 왜 빠르고, 명령은 왜 원자적인가

Redis는 앞에서 여러 번 "쓰는 곳"으로 나왔습니다. 세션 저장소(14편), 선착순 수량 차감(22편), 원격 캐시(26편). 이 편부터는 Redis 자체를 봅니다. 핵심은 하나입니다. Redis는 명령을 한 줄로 세워 하나씩 실행합니다. 그래서 명령 하나는 다른 명령과 섞이지 않지만, 느린 명령 하나가 모두를 기다리게 만들기도 합니다.

1. 데이터는 메모리에 있고, 비용은 대부분 네트워크 왕복이다2. 명령은 한 줄로 서서 하나씩 실행된다3. 느린 명령 하나가 모두를 기다리게 한다4. 자료구조는 용도로 고른다5. 실무 예시6. 설명해보기

1데이터는 메모리에 있고, 비용은 대부분 네트워크 왕복이다

Redis는 데이터를 메모리에 두는 키-값 저장소입니다. 키 하나에 문자열, 목록, 집합 같은 값을 저장하고, GET·SET 같은 명령으로 읽고 씁니다. 디스크에서 페이지를 찾아 읽는 DB와 달리, 명령이 메모리의 데이터를 바로 다룹니다.

03편 그림을 다시 떠올려 보면, 메모리 읽기는 약 100ns이고 서버 간 네트워크 왕복은 약 0.5ms입니다. 5천 배 차이입니다. 그래서 우리 서버가 Redis 명령 하나를 보내고 답을 받는 시간은 Redis 안에서 일하는 시간보다 네트워크를 오가는 시간이 대부분입니다.

핵심 — Redis 호출 한 번 ≈ 네트워크 왕복 한 번. 빠르게 쓰려면 명령 하나를 가볍게 만드는 것보다 왕복 횟수를 줄이는 것이 먼저입니다. 24편의 N+1과 같은 이야기입니다. 반복문 안에서 키 100개를 하나씩 GET하면 왕복 100번, MGET으로 한 번에 읽으면 1번입니다.

2명령은 한 줄로 서서 하나씩 실행된다

여러 서버가 동시에 명령을 보내도, Redis는 명령을 한 스레드에서 하나씩 차례로 실행합니다. 한 명령이 실행되는 동안 다른 명령은 끼어들지 못합니다. 17편에서 본 이벤트 루프와 같은 구조입니다. 적은 스레드가 많은 연결을 돌아가며 처리하고, 락을 잡을 일이 없어서 빠릅니다.

그래서 명령 하나는 원자적입니다. INCR views는 "읽고, 1 더하고, 쓰기"를 Redis 안에서 한 번에 끝내므로, 여러 서버가 동시에 보내도 숫자가 빠지지 않습니다. 하지만 명령 여러 개를 이어 붙인 것은 원자적이지 않습니다. 우리 서버가 GET으로 읽고, 자바에서 1을 더하고, SET으로 쓰면 그 사이에 다른 서버의 명령이 끼어듭니다. 05편의 count++가 서버 여러 대 규모로 다시 나타난 것입니다.

여러 단계를 원자적으로 하고 싶을 때방법기억할 점
숫자 증감, "없을 때만 쓰기"원자 명령: INCR·DECR, SET … NX가장 단순하고 빠름. 먼저 이것으로 되는지 봄
명령 몇 개를 끼어들기 없이 연속 실행MULTI … EXEC모아서 한 번에 실행할 뿐, 중간 결과를 보고 다음 명령을 정할 수는 없고, 롤백도 없음(실행 중 한 명령이 실패해도 나머지는 실행됨)
"읽고 판단해서 쓰기"Lua 스크립트스크립트 전체가 한 명령처럼 실행됨. 대신 스크립트가 길면 그동안 모두가 기다림(3절)

3느린 명령 하나가 모두를 기다리게 한다

한 줄로 서서 하나씩 실행한다는 것은, 앞의 명령이 오래 걸리면 뒤의 명령이 전부 기다린다는 뜻이기도 합니다. 17편에서 이벤트 루프에 블로킹 호출을 섞으면 전체가 느려진다고 한 것과 같은 원리입니다. 명령 대부분은 키 하나를 다뤄 순식간에 끝나지만, 데이터 양에 비례해 오래 걸리는 명령이 문제입니다.

위험한 명령왜대신
KEYS pattern모든 키를 훑음. 키가 수백만 개면 그동안 Redis 전체가 멈춤SCAN — 조금씩 나눠 훑어서 사이사이 다른 명령이 실행됨
거대한 컬렉션 통째로 조회
(HGETALL, SMEMBERS, LRANGE 0 -1)		원소가 수십만 개면 조회도, 결과 전송도 오래 걸림필요한 만큼만 조회, 컬렉션을 작게 나누기
큰 키 삭제 DEL원소가 많은 키를 지우는 데도 시간이 듦UNLINK — 키는 바로 사라지고 메모리 정리는 뒤에서

이렇게 원소가 너무 많거나 값이 너무 큰 키를 큰 키(big key)라고 부릅니다. 큰 키는 명령을 느리게 만들 뿐 아니라, 29편에서 볼 Cluster 구성에서 한 노드에만 부하를 몰리게 합니다. 느리게 실행된 명령은 Redis가 SLOWLOG에 기록하므로, 응답이 가끔 튄다면 먼저 여기를 봅니다.

4자료구조는 용도로 고른다

Redis의 값은 문자열만이 아닙니다. 자료구조마다 전용 명령이 있어서, 알맞은 것을 고르면 읽고 계산하고 쓰는 일을 Redis 안에서 한 명령으로 끝낼 수 있습니다. 2절의 원자성과 1절의 왕복 절약을 함께 얻는 셈입니다.

자료구조모양실무에서 쓰는 곳대표 명령
String값 하나 (문자열·숫자)캐시(26편), 카운터, 선착순 수량(22편)GET SET INCR
Hash필드-값 묶음객체 하나의 여러 필드(장바구니, 세션 속성)HSET HGET HINCRBY
List순서 있는 목록최근 본 상품, 간단한 작업 큐LPUSH RPOP LRANGE
Set중복 없는 집합중복 참여 방지, 태그, 좋아요 누른 사람SADD SISMEMBER
Sorted Set점수로 정렬된 집합랭킹, 점수(시각) 순 예약 작업ZADD ZINCRBY ZRANGE

어떤 자료구조든 키에 만료 시간(TTL)을 걸 수 있습니다(EXPIRE, SET … EX). 캐시와 세션처럼 언젠가 사라져야 하는 값에는 TTL을 붙이는 것이 기본입니다. TTL을 빠뜨린 키가 쌓이면 어떤 일이 생기는지는 28편에서 봅니다.

List를 작업 큐로 쓰면 간단하지만, 작업을 꺼낸 서버가 처리 도중 죽으면 그 작업은 사라집니다. 작업을 잃으면 안 되는 곳에는 확인 응답이 있는 메시지 시스템을 씁니다.

5실무 예시

실수 예시

조회수가 트래픽이 몰릴 때만 덜 올라간다

상품 조회수를 Redis에 저장하면서, 값을 읽어 자바에서 1을 더한 뒤 다시 썼습니다. 트래픽이 적을 때는 정확하지만, 인기 상품에 요청이 몰리면 2절 그림처럼 증가가 사라집니다.

✕ 읽고 → 계산 → 쓰기
String v = redis.opsForValue().get(key);
long next = (v == null ? 0 : Long.parseLong(v)) + 1;
redis.opsForValue().set(key, String.valueOf(next));
// GET과 SET 사이에 다른 서버가 끼어듦
✓ 계산을 Redis에 맡김
redis.opsForValue().increment(key);
// INCR 한 명령, 끼어들 틈 없음

스프링의 StringRedisTemplate 기준입니다. increment는 Redis의 INCR을 보냅니다.

실수 예시

관리 기능 하나가 Redis 전체를 멈췄다

관리자 화면에 "현재 로그인한 사용자 수"를 보여 주려고 redisTemplate.keys("session:*")를 썼습니다. 이 메서드는 내부적으로 KEYS 명령을 보냅니다. 세션 키가 수백만 개로 늘자, 관리자가 화면을 열 때마다 Redis가 몇 초씩 멈추고 로그인·장바구니 API까지 타임아웃이 났습니다.

해결: 개수가 필요하면 세션을 만들고 지울 때 카운터(INCR/DECR)나 Set으로 따로 관리합니다. 키 목록이 꼭 필요하면 SCAN으로 조금씩 훑습니다(스프링에서는 redisTemplate.scan(ScanOptions), 다 쓴 커서는 닫기). 운영 Redis에서는 KEYS 명령 자체를 막아 두는 경우가 많습니다.

좋은 패턴

실시간 인기 상품 순위를 Sorted Set으로

주문이 들어올 때마다 DB에서 "상품별 주문 수"를 집계해 정렬하면 무겁습니다. Sorted Set은 점수를 올리는 것과 정렬된 상위 N개를 꺼내는 것을 각각 한 명령으로 합니다.

✓ 점수 올리기 · 상위 10개 조회
ZINCRBY ranking:2026-09-29 1 product:42         // 주문 1건마다 점수 +1
ZRANGE  ranking:2026-09-29 0 9 REV WITHSCORES  // 점수 높은 순 10개
EXPIRE  ranking:2026-09-29 172800                // 이틀 뒤 자동 삭제

날짜를 키에 넣어 하루 단위로 나누면, 키 하나가 끝없이 커지는 것(큰 키)도 막을 수 있습니다.

장애 대응

Redis 응답이 가끔 수백 ms씩 튄다

평소 1ms도 안 걸리던 Redis 호출이 가끔 수백 ms로 튀면서, 그 시간 동안 들어온 모든 요청이 함께 느려집니다(16편의 장애 전파). 원인은 대개 한 줄 대기열 앞에 선 느린 명령입니다.

  1. SLOWLOG GET으로 느렸던 명령과 시각 확인
  2. redis-cli --bigkeys로 큰 키 찾기 (SCAN으로 훑으므로 운영에서도 비교적 안전)
  3. 큰 키는 날짜·ID 범위로 쪼개고, 통째로 읽는 코드를 필요한 만큼만 읽도록 수정
지금은 넘어가도 되는 것 · 이벤트 루프 구현(epoll 등), 네트워크 입출력을 나눠 맡는 I/O 스레드 기능(기본은 꺼져 있고, 켜도 명령 실행 자체는 한 스레드), 자료구조의 내부 인코딩, MULTI와 함께 쓰는 WATCH, Redis 8의 JSON·벡터 같은 확장 기능

6설명해보기

답을 열기 전에 먼저 소리 내어 설명해 보세요.

Redis는 명령을 한 스레드로 실행하는데 왜 빠른가요?
데이터가 메모리에 있어서 명령 하나가 매우 짧게 끝나고, 스레드 간 락이나 전환 비용이 없기 때문입니다. 실제로 호출 시간의 대부분은 Redis 안의 실행이 아니라 네트워크 왕복입니다. 그래서 성능을 올리려면 왕복 횟수를 줄이는 것(MGET 등)이 효과적입니다.
INCR은 원자적인데, GET으로 읽고 SET으로 쓰는 코드는 왜 안전하지 않나요?
명령 하나는 끼어들기 없이 실행되지만, 명령 두 개 사이에는 다른 서버의 명령이 끼어들 수 있습니다. 두 서버가 같은 값을 읽고 각자 계산해 쓰면 한쪽 증가가 사라집니다. 계산을 Redis에 맡기는 원자 명령(INCR)이나, 여러 단계가 필요하면 Lua 스크립트를 씁니다.
운영 Redis에서 KEYS 명령을 쓰면 안 되는 이유는?
KEYS는 모든 키를 한 번에 훑는 명령이라 키가 많으면 오래 걸리고, 명령이 한 줄로 실행되는 Redis에서는 그동안 다른 모든 명령이 기다립니다. 키 목록이 필요하면 조금씩 나눠 훑는 SCAN을 쓰고, 개수는 별도 카운터로 관리합니다.
실시간 랭킹을 만들 때 어떤 자료구조를 쓰고, 왜 그런가요?
Sorted Set입니다. 점수를 올리는 것(ZINCRBY)과 점수 순으로 상위 N개를 꺼내는 것(ZRANGE … REV)이 각각 한 명령이라, 원자적이고 왕복도 적습니다. 날짜 등으로 키를 나누고 TTL을 걸어 키가 끝없이 커지지 않게 합니다.
