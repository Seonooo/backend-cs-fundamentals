가상 스레드

04에서 "웹 요청은 대부분 기다리는 시간"이라고 했습니다. 기다리는 동안에도 OS 스레드 하나를 통째로 붙잡고 있는 것이 기존 방식의 한계였습니다. Java 21의 가상 스레드는 기존 코드를 거의 그대로 두고 이 문제를 풉니다. 대신 병목이 다른 곳으로 옮겨간다는 점을 꼭 알아야 합니다.

1. 기존 스레드의 한계2. 가상 스레드는 기다리는 동안 자리를 비켜 준다3. 실무 예시4. 설명해보기

1기존 스레드의 한계

지금까지의 자바 스레드(플랫폼 스레드)는 OS 스레드와 1:1입니다. 스레드마다 스택 메모리(02편)와 OS 자원이 들고, 04편의 컨텍스트 스위칭 비용도 있어서 수천 개를 넘기기 어렵습니다. 그래서 톰캣은 스레드를 200개 정도로 제한하고 풀링합니다(07편). 문제는 이 200개가 대부분의 시간을 DB·API 응답을 기다리며 보낸다는 것입니다.

2가상 스레드는 기다리는 동안 자리를 비켜 준다

가상 스레드는 JVM이 관리하는 아주 가벼운 스레드입니다. 실제 실행은 소수의 OS 스레드(캐리어 스레드, 보통 코어 수만큼) 위에 올라타서 합니다. 핵심은 블로킹 I/O를 만나면 캐리어에서 내려와 다른 가상 스레드에게 자리를 넘긴다는 점입니다.

플랫폼 스레드가상 스레드
OS 스레드와 관계1:1여러 개가 소수의 캐리어를 나눠 씀
만드는 비용비쌈 → 풀링매우 쌈 → 풀링하지 않음 (작업마다 새로)
동시에 둘 수 있는 수수백~수천수십만 이상
코드 작성 방식블로킹 코드똑같은 블로킹 코드
잘 맞는 작업—I/O 바운드 (CPU 바운드에는 이득 없음)
핵심 — 가상 스레드는 요청을 더 빠르게 만들지 않습니다. 기다리는 동안 자원을 덜 써서 동시에 더 많이 처리하게 해 줍니다. 요청 하나의 응답 시간은 그대로입니다.

3실무 예시

운영 설정

스프링 부트에서 켜기

application.yml (Spring Boot 3.2+, Java 21+)
spring:
  threads:
    virtual:
      enabled: true   # 톰캣 요청 처리, @Async 등이 가상 스레드로 실행됨

설정 하나로 요청마다 가상 스레드가 배정됩니다. 코드는 바꾸지 않아도 되지만, 아래의 "병목 이동"을 반드시 확인하고 켭니다.

실수 예시

처리량은 늘었는데 DB 커넥션 에러가 쏟아진다

예전에는 톰캣 스레드 200개가 "동시에 DB를 쓰려는 요청 수"를 자연스럽게 200개로 막아 주고 있었습니다. 가상 스레드를 켜면 이 제한이 사라져 수천 개의 요청이 동시에 DB 커넥션을 달라고 합니다. 그런데 커넥션 풀은 여전히 10~수십 개입니다.

해결: 커넥션 풀 대기 시간을 적절히 두고, 필요하면 DB·외부 API를 부르는 구간에 Semaphore 등으로 동시 호출 수를 명시적으로 제한합니다. 외부 API의 초당 호출 제한(rate limit)도 같은 이유로 다시 점검합니다.

실수 예시

synchronized 안에서 I/O를 하면 캐리어가 묶인다 (JDK 21~23)

JDK 21~23에서는 가상 스레드가 synchronized 블록 안에서 블로킹 I/O를 하면 캐리어에서 내려오지 못하고 캐리어를 붙잡습니다(피닝, pinning). 캐리어는 코어 수만큼밖에 없으니, 이런 스레드가 몇 개만 생겨도 전체가 멈춘 것처럼 됩니다.

✕ JDK 21~23에서 피닝
synchronized (lock) {
    paymentClient.call(req);  // 블로킹 I/O → 캐리어 점유
}
✓ ReentrantLock 사용 or JDK 24+
lock.lock();
try { paymentClient.call(req); }
finally { lock.unlock(); }

JDK 24(JEP 491)부터 synchronized로 인한 피닝은 해결됐습니다. 사용 중인 JDK 버전을 먼저 확인하세요. 네이티브 메서드 호출 등 일부 경우는 여전히 캐리어를 붙잡을 수 있습니다.

실수 예시

가상 스레드를 풀에 넣어 재사용했다

습관처럼 가상 스레드를 개수 제한 풀에 넣으면 장점이 사라집니다. 가상 스레드는 작업마다 새로 만들고 버리는 것이 원래 사용법입니다. 동시 실행 수를 제한하고 싶다면 풀 크기가 아니라 Semaphore로 제한합니다.

✓ 작업마다 새 가상 스레드
try (var executor = Executors.newVirtualThreadPerTaskExecutor()) {
    ids.forEach(id -> executor.submit(() -> client.fetch(id)));
}

4설명해보기

답을 열기 전에 먼저 소리 내어 설명해 보세요.

가상 스레드가 I/O 바운드 서버의 처리량을 높이는 원리는?
가상 스레드는 블로킹 I/O를 만나면 실행 중이던 캐리어(OS 스레드)에서 내려와 대기하고, 그 캐리어는 다른 가상 스레드를 실행합니다. 기다리는 요청이 OS 스레드를 차지하지 않으므로 적은 OS 스레드로 훨씬 많은 요청을 동시에 처리할 수 있습니다.
가상 스레드를 켰더니 DB 커넥션 타임아웃이 늘었다. 왜인가요?
예전에는 톰캣 스레드 수가 동시에 DB를 쓰려는 요청 수를 자연스럽게 제한했습니다. 가상 스레드로 그 제한이 사라져 수천 개 요청이 동시에 적은 수의 커넥션을 기다리게 된 것입니다. Semaphore 등으로 동시성을 명시적으로 제한해야 합니다.
가상 스레드를 켜면 요청 하나의 응답 시간도 빨라지나요?
아닙니다. DB나 API 응답을 기다리는 시간 자체는 그대로입니다. 대기 중 자원을 덜 쓰게 해서 동시에 처리할 수 있는 요청 수를 늘릴 뿐입니다.
피닝(pinning)이 무엇이고 왜 문제인가요?
가상 스레드가 블로킹되어도 캐리어에서 내려오지 못하고 붙잡고 있는 상태입니다. 캐리어는 코어 수 정도밖에 없어서 피닝이 여러 개 생기면 다른 가상 스레드가 실행될 곳이 없어집니다. JDK 21~23에서는 synchronized 안의 블로킹이 대표 원인이었고, JDK 24에서 해결됐습니다.
