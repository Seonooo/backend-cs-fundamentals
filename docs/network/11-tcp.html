TCP·UDP와 연결 비용

HTTP도, DB 드라이버도, Redis 클라이언트도 대부분 TCP 연결 위에서 동작합니다. TCP 연결은 공짜가 아닙니다. 맺을 때 왕복 시간이 들고, 끊은 뒤에도 흔적이 남습니다. 이 두 가지가 keep-alive와 커넥션 풀이 존재하는 이유입니다.

백엔드 개발자가 다루는 연결은 거의 TCP입니다. 데이터가 빠지면 안 되니까요. 그래서 이 편은 TCP 중심으로 봅니다.

2연결을 맺는 비용: 3-way handshake

TCP는 데이터를 보내기 전에 "보낼게 → 알았어, 나도 보낼게 → 알았어" 세 번의 신호로 연결을 맺습니다. 이 과정에 왕복(RTT) 한 번이 걸립니다.

서버 사이 왕복이 1ms라면 별것 아니지만, 다른 리전의 API처럼 왕복이 50ms면 호출마다 연결 준비만 50ms(HTTPS면 100ms 이상)가 붙습니다.

3연결은 네 값으로 구분되고, OS 자원을 쓴다

서버는 8080 포트 하나로 수많은 연결을 받습니다. 연결 하나는 (내 IP, 내 포트, 상대 IP, 상대 포트) 네 값의 조합으로 구분되기 때문입니다. 연결을 거는 쪽은 매번 OS가 빈 포트(임시 포트)를 하나 골라 씁니다.

또 하나: 리눅스에서 소켓(연결)은 파일처럼 파일 디스크립터를 하나씩 씁니다. 프로세스가 열 수 있는 파일 디스크립터 수에는 한도가 있습니다(ulimit -n).

4TIME_WAIT: 끊은 뒤에도 남는 흔적

연결을 먼저 끊은 쪽은 늦게 도착하는 패킷을 정리하기 위해 그 연결 정보를 잠시(리눅스 기본 60초) TIME_WAIT 상태로 들고 있습니다. 그동안 그 (IP, 포트) 조합은 재사용이 제한됩니다. 정상적인 동작이지만, 짧은 연결을 대량으로 만들면 임시 포트가 TIME_WAIT로 가득 차서 새 연결을 못 맺는 상황이 옵니다.

핵심 — 연결을 새로 맺는 것 = 왕복 지연 + 임시 포트 소모 + 끊은 뒤 TIME_WAIT. 그래서 같은 상대와 여러 번 통신한다면 연결을 유지하고 재사용합니다 (HTTP keep-alive, 커넥션 풀 → 15편, 23편).

5실무 예시

실수 예시

외부 API를 호출할 때마다 새 연결을 만들었다

호출마다 HTTP 클라이언트를 새로 만들거나, 풀 없이 연결을 맺고 닫는 코드가 초당 수백 번 실행됩니다. 호출 지연이 늘고, 어느 순간 이런 에러가 나기 시작합니다.

증상
java.net.BindException: Cannot assign requested address   // 임시 포트 고갈

$ ss -tan state time-wait | wc -l
28000                                                   // TIME_WAIT 연결 수

해결: HTTP 클라이언트는 애플리케이션에서 하나를 만들어 재사용하고(빈으로 등록), 커넥션 풀과 keep-alive를 켭니다. 커널 설정으로 TIME_WAIT를 줄이는 것은 마지막 수단입니다.

실수 예시

연결을 닫지 않았다 — 풀 고갈, 또는 Too many open files

응답 본문(InputStream)을 끝까지 읽거나 닫지 않으면, 그 연결은 반납되지도 닫히지도 않고 남습니다. 풀을 쓰는 클라이언트라면 반납되지 않은 연결이 쌓여 풀이 먼저 고갈되고(연결 획득 대기·타임아웃, 15편), 풀 없이 매번 연결한다면 파일 디스크립터가 늘다가 한도에 닿습니다.

✕ 응답을 닫지 않음
HttpResponse res = client.execute(req);
if (res.getCode() != 200) {
    return null;   // 본문을 안 닫고 반환
}
✓ try-with-resources로 항상 닫기
try (var res = client.execute(req)) {
    if (res.getCode() != 200) return null;
    return read(res.getEntity());
}

확인: ls /proc/<pid>/fd | wc -l로 열린 파일 수가 계속 늘어나는지 봅니다. 한도만 올리면 증상만 늦출 뿐입니다.

장애 대응

가끔 나는 Connection reset by peer

평소엔 잘 되다가 간헐적으로 Connection reset이 납니다. 흔한 원인은 유휴 연결입니다. 우리 풀에서 한동안 안 쓴 연결을, 중간의 로드밸런서나 상대 서버가 이미 (유휴 시간 초과로) 끊어 버렸는데, 우리는 그걸 모르고 재사용한 것입니다.

해결: 우리 쪽 유휴 연결 만료 시간을 상대(로드밸런서) 쪽보다 짧게 설정해, 상대가 끊기 전에 우리가 먼저 정리하게 합니다 (15편).

6설명해보기

답을 열기 전에 먼저 소리 내어 설명해 보세요.

TCP와 UDP의 차이와 각각의 쓰임새는?
TCP는 연결을 맺고 데이터가 빠짐없이 순서대로 도착하도록 보장하며, HTTP·DB 연결처럼 정확성이 중요한 곳에 씁니다. UDP는 연결 없이 보내고 보장이 없지만 가볍고 빨라 DNS 조회 등에 씁니다.
외부 API를 호출할 때마다 새 TCP 연결을 만들면 생기는 문제는?
호출마다 핸드셰이크 왕복(HTTPS면 TLS까지) 지연이 붙고, 임시 포트와 파일 디스크립터를 소모하며, 끊을 때마다 TIME_WAIT가 쌓여 결국 새 연결을 못 맺을 수 있습니다. 커넥션 풀과 keep-alive로 연결을 재사용해야 합니다.
TIME_WAIT는 어느 쪽에 생기고, 왜 필요한가요?
연결을 먼저 끊은 쪽에 생깁니다. 늦게 도착한 이전 연결의 패킷이 같은 포트 조합의 새 연결에 섞이지 않도록 잠시 그 조합을 보류하는 것입니다. 정상 동작이지만 짧은 연결이 대량으로 생기면 포트 고갈로 이어집니다.
간헐적인 Connection reset의 흔한 원인과 해결책은?
풀에 있던 유휴 연결을 로드밸런서나 상대 서버가 이미 끊었는데, 우리가 모르고 재사용한 경우입니다. 우리 쪽 유휴 연결 만료 시간을 상대보다 짧게 두어 먼저 정리하게 합니다.
