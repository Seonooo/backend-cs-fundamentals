메모리 구조와 JVM 메모리

01에서 스택은 스레드마다, 힙은 공유라고 했습니다. 이번에는 JVM 안에서 메모리가 실제로 어떻게 나뉘는지, 그리고 실무에서 자주 만나는 GC 멈춤과 OutOfMemoryError가 어디서 생기는지 봅니다.

1JVM 메모리 지도

스프링 서버(JVM 프로세스)의 메모리는 크게 네 곳으로 나뉩니다. 어디에 무엇이 들어가는지만 알면, 에러 메시지만 보고도 어디가 넘쳤는지 알 수 있습니다.

에러 메시지어디가 넘쳤나흔한 원인
OutOfMemoryError: Java heap space힙대량 데이터를 한 번에 메모리에 올림, 메모리 누수
OutOfMemoryError: Metaspace메타스페이스클래스가 계속 새로 생성됨 (동적 프록시·리로드 남용). 단, -XX:MaxMetaspaceSize를 지정했을 때만 이 에러가 남. 기본값은 무제한이라 지정하지 않으면 네이티브 메모리가 계속 늘어 컨테이너 OOMKilled로 나타남
StackOverflowError한 스레드의 스택끝나지 않는 재귀 호출
unable to create native thread스레드를 더 못 만듦스레드를 무한정 생성, OS 스레드 수 한도

01에서 "데이터 영역"으로 따로 그렸던 static 변수는, 요즘 JVM(Java 8+)에서는 값이 힙에 저장됩니다. 어느 쪽이든 모든 스레드가 공유한다는 점은 같습니다.

2코드 한 줄이 메모리에 놓이는 모습

아래 메서드가 실행될 때, 각 변수와 객체가 어디에 놓이는지 따라가 봅니다.

OrderService.java
public List<Order> myOrders(long userId) {          // userId 값 1 → 스택
    List<Order> orders = new ArrayList<>();         // orders(참조) → 스택, ArrayList 객체 → 힙
    orders.addAll(orderRepository.findByUserId(userId)); // Order 객체들 → 힙
    return orders;
}
핵심 — 스택 프레임은 메서드가 끝나면 즉시 사라집니다. 힙의 객체는 누군가 참조하는 동안 살아 있고, 아무도 참조하지 않으면 GC 대상이 됩니다. 메모리 누수는 "안 쓰는데 누군가 계속 참조하고 있는" 상태입니다.

3GC는 어떻게 동작하나

GC(가비지 컬렉터)는 더 이상 아무도 참조하지 않는 객체를 찾아 힙에서 치웁니다. 이때 JVM은 대부분의 객체가 금방 죽는다는 점을 이용해 힙을 나이별로 나눕니다. 요청 하나를 처리하며 만든 DTO, 리스트 같은 객체는 응답을 보내면 바로 쓸모가 없어지기 때문입니다.

GC가 일하는 동안 애플리케이션 스레드가 잠깐 멈출 수 있습니다. 이를 Stop-The-World라고 합니다. 평소에는 몇 ms 수준이라 티가 안 나지만, 힙이 가득 차서 큰 GC가 자주 돌면 그동안 들어온 요청이 전부 기다려 간헐적인 응답 지연으로 나타납니다.

4실무 예시

실수 예시

전체 데이터를 한 번에 조회해서 OOM

개발 DB에는 데이터가 1천 건이라 문제없던 정산 배치가, 운영에서 1백만 건을 만나 Java heap space로 죽습니다. 조회 결과 전체가 하나의 List로 힙에 올라가기 때문입니다.

✕ 전부 메모리에
List<Order> all = orderRepository.findAll();
// 100만 개 객체가 동시에 힙에
for (Order o : all) settle(o);
✓ 나눠서 처리
Pageable page = PageRequest.of(0, 1000);
Slice<Order> s;
do {
  s = orderRepository.findAllBy(page);
  s.forEach(this::settle);
  page = s.nextPageable();
} while (s.hasNext());
// 한 번에 1000개씩만 힙에

실제로는 offset 방식 페이징이 뒤로 갈수록 느려지므로 "마지막 id 이후 1000건"처럼 커서 방식을 많이 씁니다. JPA를 쓴다면 처리한 엔티티가 영속성 컨텍스트에 계속 쌓이지 않게 하는 것도 필요합니다 (24편).

실수 예시

static Map 캐시가 계속 커지는 메모리 누수

"간단히 캐시하자"며 static Map에 넣기만 하고 지우지 않으면, 그 객체들은 영원히 참조되어 GC가 치울 수 없습니다. 힙 사용량 그래프를 보면 차이가 바로 보입니다.

✕ 지우지 않는 캐시
private static final Map<Long, UserProfile> CACHE = new HashMap<>();
// 사용자가 늘어날수록 끝없이 커짐 (게다가 HashMap은 스레드 안전하지도 않음 → 05편)

해결: 크기 제한과 만료 시간이 있는 캐시 라이브러리(Caffeine 등)를 쓰거나 Redis 같은 외부 캐시를 씁니다 (26편).

실수 예시

JPA 양방향 연관관계의 무한 재귀 → StackOverflowError

Member가 Order 목록을, Order가 Member를 참조하는 양방향 관계에서 엔티티를 그대로 JSON으로 응답하거나 Lombok @ToString을 쓰면, 서로를 계속 호출하다 스택이 넘칩니다.

✕ 호출이 끝나지 않음
member.toString()
 → orders.toString()
   → order.toString()
     → member.toString()   // 다시 처음으로… 프레임이 계속 쌓임
       → …  StackOverflowError

해결: 엔티티 대신 응답 DTO를 만들어 반환하고, 연관 필드는 @ToString에서 제외합니다.

운영 설정

컨테이너 메모리 한도와 힙 크기

컨테이너 메모리가 2GB인데 -Xmx2g로 힙을 꽉 채우면, 힙 밖의 메모리(메타스페이스, 스레드 스택, 네트워크 버퍼 등)가 들어갈 자리가 없습니다. JVM이 OOM을 내기도 전에 컨테이너가 강제 종료(OOMKilled)됩니다.

그래서 컨테이너 환경에서는 힙을 고정값 대신 비율로 지정하는 경우가 많습니다. 예: -XX:MaxRAMPercentage=75. 참고로 아무것도 지정하지 않으면 JVM은 기본적으로 사용 가능한 메모리의 1/4 정도만 힙으로 잡아, 반대로 메모리를 놀리게 됩니다.

장애 대응

간헐적으로 응답이 느려질 때 GC를 의심한다

평소 50ms이던 API가 몇 분에 한 번씩 수 초씩 느려진다면, 모니터링 도구(Grafana, APM 등)에서 GC 멈춤 시간과 힙 사용량을 같이 봅니다. 느려진 시점과 GC 시점이 겹치면 힙이 부족하거나 누수가 있다는 신호입니다. 원인을 확인할 때는 힙 덤프를 떠서 어떤 객체가 메모리를 차지하는지 봅니다.

지금은 넘어가도 되는 것 · G1·ZGC 등 GC 알고리즘의 내부 동작(최신 GC는 힙을 작은 구역으로 나눠 관리하지만 "젊은 객체와 오래된 객체를 다르게 다룬다"는 원리는 같음), 객체 헤더 구조, JIT 컴파일러와 이스케이프 분석(메서드 밖으로 나가지 않는 객체를 힙에 만들지 않는 최적화)

5설명해보기

답을 열기 전에 먼저 소리 내어 설명해 보세요.

스택과 힙에는 각각 무엇이 저장되고, 언제 정리되나요?
스택에는 메서드 호출 프레임(지역 변수, 파라미터, 객체 참조)이 저장되고, 메서드가 끝나면 즉시 사라집니다. 힙에는 new로 만든 객체가 저장되고, 아무도 참조하지 않게 되면 GC가 정리합니다. 스택은 스레드마다 따로, 힙은 모든 스레드가 공유합니다.
GC가 있는 자바에서도 메모리 누수가 생기는 이유는?
GC는 "참조되지 않는 객체"만 치웁니다. 더 이상 쓰지 않는데도 static 컬렉션이나 오래 사는 객체가 계속 참조하고 있으면 GC 입장에서는 살아 있는 객체라 치울 수 없습니다. 그래서 지우지 않는 캐시, 등록만 하고 해제하지 않는 리스너가 대표적인 누수 원인입니다.
대부분의 GC가 힙을 Young과 Old로 나누는 이유는?
대부분의 객체는 생성 직후 금방 쓸모가 없어집니다(요청 처리 중 만든 DTO 등). 새 객체만 모인 작은 영역을 자주 청소하면 적은 비용으로 대부분의 메모리를 회수할 수 있고, 오래 사는 객체는 가끔만 검사하면 되기 때문입니다.
컨테이너 메모리 2GB에 -Xmx2g를 주면 어떤 일이 생기나요?
JVM 프로세스는 힙 외에도 메타스페이스, 스레드 스택, 네트워크 버퍼 등 힙 밖의 메모리를 씁니다. 힙만으로 한도를 채우면 합계가 한도를 넘어 컨테이너가 OOMKilled로 강제 종료됩니다. 힙은 컨테이너 한도의 일부(예: 75%)로 잡아야 합니다.
