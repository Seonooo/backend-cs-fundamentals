DNS와 요청의 전체 흐름

코드에는 api.payment.com 같은 이름을 쓰지만, 실제 연결은 IP로 합니다. 이름을 IP로 바꿔 주는 것이 DNS입니다. 이 편에서는 DNS가 여러 단계에서 캐시된다는 점과, 요청 하나가 응답을 받기까지 거치는 전체 단계를 한 장으로 정리합니다.

1. DNS: 가까운 곳부터 물어본다2. 요청 하나가 응답을 받기까지3. 실무 예시4. 설명해보기

1DNS: 가까운 곳부터 물어본다

이름을 IP로 바꿀 때 매번 인터넷 끝까지 묻지 않습니다. 가까운 캐시부터 차례로 확인하고, 답을 얻으면 TTL(유효 시간) 동안 저장해 둡니다. 03편에서 본 "가까운 곳에 복사본" 원리가 여기서도 나옵니다.

레코드뜻예
A이름 → IPv4 주소api.example.com → 203.0.113.10
CNAME이름 → 다른 이름 (별칭)api.example.com → my-alb-123.elb.amazonaws.com

클라우드 로드밸런서는 IP가 바뀔 수 있어서 IP 대신 이름(CNAME 등)으로 연결하는 것이 일반적입니다. 그래서 "IP가 바뀌면 DNS 캐시가 따라가는가"가 실무 문제가 됩니다.

2요청 하나가 응답을 받기까지

우리 서버가 외부 HTTPS API를 처음 호출할 때 일어나는 일을 시간 순서로 펼치면 이렇습니다. 브라우저 개발자 도구의 Network 탭에서 보는 폭포(waterfall) 그림과 같은 모양입니다.

"주소창에 URL을 입력하면 일어나는 일" — 위 그림이 이 질문의 답입니다. DNS로 IP를 찾고 → 그 IP의 443 포트로 TCP 연결 → TLS로 암호화 채널 수립 → HTTP 요청 전송 → (로드밸런서 → 서버 → DB) → 응답 수신 → 브라우저가 화면을 그림.

3실무 예시

실수 예시

DNS를 바꿨는데 일부 트래픽이 계속 옛 서버로 간다

서버를 이전하며 DNS의 IP를 바꿨는데, 몇 시간 동안 일부 사용자가 옛 서버로 접속합니다. 레코드의 TTL이 86400초(1일)였기 때문에, 이미 조회해 간 곳들은 최대 하루 동안 옛 IP를 씁니다.

✓ 이전 전 준비
1. 이전 며칠 전: TTL을 86400 → 60초로 낮춤
2. 기존 TTL(1일)이 지나 모두가 짧은 TTL을 받을 때까지 대기
3. IP 변경 → 약 1분 안에 대부분 새 IP로 이동
4. 옛 서버는 한동안 유지 (캐시를 무시하는 클라이언트 대비)
5. 안정되면 TTL을 다시 올림
실수 예시

DB 장애 조치 후에도 애플리케이션이 옛 DB로 붙는다

AWS RDS 같은 관리형 DB는 장애 시 대기 DB로 넘어가며 같은 이름의 IP를 바꿉니다. 그런데 애플리케이션이 계속 연결 실패를 냅니다. 원인은 두 가지입니다.

  • JVM DNS 캐시: networkaddress.cache.ttl 설정에 따라 JVM이 옛 IP를 오래 기억할 수 있습니다. 현재 JDK는 기본 30초 정도지만, 환경이나 설정에 따라 영구 캐시되는 경우가 있어 확인이 필요합니다.
  • 커넥션 풀: DNS가 새 IP를 알아도, 풀에 이미 열려 있던 연결은 옛 IP로 이어져 있습니다. 커넥션 최대 수명(HikariCP maxLifetime)이 지나 새로 연결할 때 비로소 새 IP로 갑니다 (23편).

해결: JVM DNS TTL을 명시적으로 짧게(예: 30~60초) 두고, 커넥션 풀의 최대 수명과 검증 설정을 확인합니다.

장애 대응

API가 느린데, 어느 단계가 느린지 모르겠다

외부 API 호출이 느릴 때 위 폭포 그림의 단계를 나눠 봅니다. curl은 단계별 시간을 바로 보여 줍니다.

$ curl -o /dev/null -s -w "…" https://api.payment.com/health
dns:        0.021s   ← 여기가 크면 DNS 문제
connect:    0.052s   ← TCP 연결까지 (dns 포함 누적)
tls:        0.089s   ← TLS까지 (누적)
first_byte: 1.940s   ← 응답 첫 바이트까지: 상대 서버 처리가 느림
total:      1.952s

-w에 %{time_namelookup} %{time_connect} %{time_appconnect} %{time_starttransfer} %{time_total}를 넣으면 위 값들이 나옵니다. 준비 단계가 크면 네트워크·DNS, first_byte만 크면 상대 서버 쪽 문제입니다.

브라우저 주소창에 https://www.example.com을 입력하면 일어나는 일을 순서대로 설명해 보세요.
DNS로 도메인의 IP를 찾고(캐시 → 리졸버 순), 그 IP의 443 포트로 TCP 3-way handshake를 합니다. 이어서 TLS 핸드셰이크로 인증서를 확인하고 암호화 키를 정한 뒤, HTTP 요청을 보냅니다. 요청은 로드밸런서를 거쳐 서버에 도착해 처리되고, 응답을 받은 브라우저가 화면을 그립니다.
DNS TTL이 길면 좋은 점과 나쁜 점은?
좋은 점은 캐시에서 바로 답을 얻어 조회가 빠르고 DNS 서버 부하가 적다는 것입니다. 나쁜 점은 IP를 바꿨을 때 TTL이 지날 때까지 옛 IP가 계속 쓰인다는 것입니다. 그래서 이전 작업 전에는 TTL을 미리 낮춥니다.
같은 서버에 두 번째 요청이 첫 요청보다 빠른 이유는?
DNS 결과가 캐시되어 조회가 생략되고, 첫 요청에서 만든 TCP·TLS 연결을 재사용하면 핸드셰이크 왕복도 생략되기 때문입니다. 남는 것은 요청 전송, 서버 처리, 응답 수신뿐입니다.
DB 장애 조치로 IP가 바뀌었는데 애플리케이션이 계속 실패한다면 무엇을 확인하나요?
JVM의 DNS 캐시 TTL이 너무 길거나 영구 캐시로 설정되어 있지 않은지, 그리고 커넥션 풀에 옛 IP로 연결된 커넥션이 남아 있는지(최대 수명, 검증 설정) 확인합니다.
