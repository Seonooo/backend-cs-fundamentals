블로킹 vs 논블로킹 I/O

04편부터 계속 나온 문제가 있습니다. "스레드가 I/O를 기다리는 동안 아무것도 못 한다." 이 문제에 대한 답은 크게 셋입니다. 스레드를 많이 두기(스레드 풀, 07편), 기다리는 스레드를 싸게 만들기(가상 스레드, 08편), 그리고 이 편의 주제인 아예 기다리지 않기(논블로킹 + 이벤트 루프)입니다.

1. 두 가지 처리 모델2. 세 가지 선택지 비교3. 실무 예시4. 설명해보기

1두 가지 처리 모델

블로킹 방식에서는 스레드가 DB에 쿼리를 보내면 결과가 올 때까지 그 자리에 멈춰 있습니다. 논블로킹 방식에서는 "결과가 오면 이걸 실행해 줘"라고 맡겨 두고, 스레드는 즉시 다른 일을 하러 갑니다.

2세 가지 선택지 비교

MVC + 스레드 풀MVC + 가상 스레드WebFlux (논블로킹)
코드 스타일평범한 순차 코드평범한 순차 코드Mono/Flux 연결 (리액티브)
기다리는 동안OS 스레드 점유캐리어를 비켜 줌스레드가 기다리지 않음
동시 처리 한계스레드 수 (수백)매우 큼매우 큼
라이브러리 제약없음거의 없음 (피닝 주의)전부 논블로킹이어야 함 (JDBC ✕ → R2DBC)
디버깅·학습쉬움쉬움어려움 (스택 추적이 끊김)

참고로 톰캣도 내부적으로 연결 수락과 읽기 대기에는 논블로킹(NIO)을 씁니다. 다만 요청을 처리하는 부분(우리 컨트롤러 코드)은 워커 스레드에서 블로킹 방식으로 실행됩니다.

핵심 — 논블로킹의 이점은 "모든 구간이 논블로킹일 때"만 나옵니다. 사슬 중 하나라도 블로킹이면 소수의 이벤트 루프 스레드가 그 자리에서 멈추고, 그 스레드가 맡은 모든 요청이 함께 멈춥니다.

3실무 예시

실수 예시

WebFlux에서 JDBC(JPA)로 DB를 조회했다

WebFlux로 만든 API에서 기존 JPA 리포지토리를 그대로 호출했습니다. 트래픽이 조금만 늘어도 모든 API의 응답 시간이 함께 치솟습니다. JDBC는 블로킹이라, 코어 수만큼밖에 없는 이벤트 루프 스레드가 DB 응답을 기다리며 멈췄기 때문입니다.

✕ 이벤트 루프에서 블로킹 호출
@GetMapping("/orders/{id}")
public Mono<Order> get(@PathVariable Long id) {
    return Mono.just(orderJpaRepo.findById(id).get());
    // ↑ 이벤트 루프 스레드가 DB를 기다리며 멈춤
}
✓ 논블로킹 드라이버 or 격리
// 1) R2DBC 등 논블로킹 드라이버 사용
return orderR2dbcRepo.findById(id);

// 2) 불가피하면 블로킹 전용 스케줄러로 격리
return Mono.fromCallable(() -> orderJpaRepo.findById(id).get())
           .subscribeOn(Schedulers.boundedElastic());

개발 중에는 BlockHound 같은 도구로 이벤트 루프에서 블로킹 호출이 일어나면 바로 예외를 내게 할 수 있습니다.

실수 예시

이벤트 루프에서 무거운 계산이나 sleep

이벤트 루프 스레드에서 수백 ms짜리 JSON 변환, 암호화, Thread.sleep을 하면 I/O가 아니어도 똑같이 멈춥니다. 04편의 CPU 바운드 작업처럼, 무거운 계산은 별도 스케줄러(스레드 풀)로 넘깁니다.

상황추천
일반적인 CRUD API, JPA 사용, 팀이 MVC에 익숙MVC (+ Java 21이면 가상 스레드 검토)

가상 스레드가 나오면서 "많은 동시 연결을 위해서만 WebFlux를 택하는" 이유는 줄었습니다. 대신 WebFlux는 스트리밍과 백프레셔(받는 쪽 속도에 맞춰 흘려보내기) 같은 리액티브 고유의 장점으로 선택합니다.

매일 보는 곳

MVC에서 WebClient를 쓰는 것은 괜찮다

Spring MVC 애플리케이션에서 논블로킹 HTTP 클라이언트인 WebClient를 쓰고 .block()으로 결과를 받는 것은 괜찮습니다. 어차피 요청 스레드는 블로킹 모델이니까요. 반대로 WebFlux 핸들러 안에서 .block()을 부르면 이벤트 루프를 멈추게 하므로 금지입니다. 새로 시작한다면 MVC에서는 RestClient(15편)가 더 단순합니다.

4설명해보기

답을 열기 전에 먼저 소리 내어 설명해 보세요.

블로킹 I/O와 논블로킹 I/O의 차이를 스레드 관점에서 설명해 보세요.
블로킹 I/O에서는 스레드가 결과가 올 때까지 멈춰 기다리므로 동시 요청 수만큼 스레드가 필요합니다. 논블로킹 I/O에서는 요청을 맡겨 두고 스레드는 즉시 다른 일을 하며, 결과가 도착하면 이벤트로 받아 이어서 처리하므로 적은 스레드로 많은 요청을 처리할 수 있습니다.
WebFlux 애플리케이션에서 JDBC로 DB를 조회하면 어떤 문제가 생기나요?
JDBC는 블로킹이라 코어 수 정도밖에 없는 이벤트 루프 스레드가 DB 응답을 기다리며 멈추고, 그 스레드가 맡은 다른 모든 요청도 함께 지연됩니다. R2DBC 같은 논블로킹 드라이버를 쓰거나 블로킹 전용 스케줄러로 격리해야 합니다.
I/O 대기 문제에 대한 세 가지 접근을 비교해 보세요.
스레드 풀은 스레드를 많이 두어 대기를 겹치지만 OS 스레드 수에 한계가 있습니다. 가상 스레드는 기다리는 동안 OS 스레드를 비켜 주어 블로킹 코드 그대로 높은 동시성을 얻습니다. 논블로킹은 스레드가 아예 기다리지 않지만, 모든 구간이 논블로킹이어야 하고 코드가 복잡해집니다.
