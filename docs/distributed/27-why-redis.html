Redis는 왜 쓰는가: 풀려는 문제와 쓰지 않을 때

26편에서 캐시를 둘 곳으로 로컬 캐시와 Redis를 비교했습니다. 이 편은 한 단계 앞의 질문에서 시작합니다. 애초에 Redis는 왜 필요하고, 언제는 필요 없는가. Redis를 "넣으면 빨라지는 부품"이 아니라 특정 문제를 푸는 도구로 보고, 그 문제가 무엇인지, 푸는 대가는 무엇인지, 넣기 전에 무엇을 물어야 하는지를 봅니다.

1. 서버가 여러 대가 되면 함께 볼 상태가 생긴다2. 빠른 대신 메모리 크기와 네트워크 왕복을 치른다3. Redis가 없어도 되는 경우가 많다4. 공유·속도·잃어도 되는 데이터에 맞는다5. 넣기 전에 다섯 가지를 묻는다6. 실무 예시7. 설명해보기

1서버가 여러 대가 되면 함께 볼 상태가 생긴다

서버가 한 대일 때는 상태를 JVM 메모리에 두면 됩니다. 로그인 세션도, 캐시도, 선착순 남은 수량도 그렇습니다. 그런데 트래픽이 늘어 서버를 여러 대로 늘리면(스케일아웃) 이 방법이 깨집니다. 로드밸런서가 요청을 아무 서버로나 보내기 때문입니다.

  • 서버 1의 메모리에 있는 로그인 정보를 서버 2는 모릅니다. 새로고침하면 로그인이 풀립니다(14편).
  • 서버마다 캐시를 따로 두면, 같은 상품의 가격이 서버마다 다르게 보입니다(26편).
  • 남은 수량을 서버마다 따로 세면, 합쳐서 준비한 수량보다 많이 팔립니다(22편).

그래서 이런 상태는 모든 서버가 함께 보는 곳으로 옮겨야 합니다. 먼저 떠오르는 곳은 DB입니다. DB는 모두가 공유하고 꺼져도 남습니다. 하지만 세션 조회, 조회수 +1, 캐시 조회처럼 요청마다 읽고 쓰는 작은 값까지 모두 DB로 보내면, 디스크에 안전하게 기록하는 비용과 SQL 처리, 한정된 커넥션(23편) 때문에 DB가 먼저 병목이 됩니다.

Redis는 데이터를 메모리에 두고, 여러 서버가 네트워크로 함께 읽고 쓰는 키-값 저장소입니다. 공식 FAQ는 창시자가 실시간 로그 분석 서비스(LLOOGG)를 확장하려고 Redis를 만들었다고 설명합니다(2009년 공개). 창시자는 그 서비스를 MySQL 등으로 버티다가 더 이상 확장할 수 없게 되었을 때 만들었다고 회고합니다. 지금 공식 문서는 Redis를 DB, 캐시, 스트리밍 엔진, 메시지 브로커 등으로 쓸 수 있다고 소개합니다.

핵심 — Redis가 푸는 문제는 "빠른 저장"이 아니라 "여러 서버가 함께 보는 상태를, DB보다 가볍고 빠르게"입니다. 서버가 한 대이거나 서버끼리 값을 공유할 필요가 없다면, 이 문제 자체가 없습니다.

2빠른 대신 메모리 크기와 네트워크 왕복을 치른다

공식 FAQ는 Redis의 트레이드오프를 한 문장으로 설명합니다. 메모리에 두기 때문에 아주 빠른 읽기·쓰기를 얻는 대신, 데이터가 메모리보다 클 수 없다는 것입니다. 얻는 것과 치르는 것을 나눠 보면 이렇습니다.

얻는 것치르는 것
메모리에 둠명령 하나가 매우 짧게 끝남데이터 크기 = 메모리 크기. 공식 FAQ 예시로 작은 문자열 키 100만 개가 약 85MB, 필드 5개짜리 Hash 100만 개가 약 160MB. 메모리는 디스크보다 비쌈
네트워크로 공유모든 서버가 같은 값을 봄호출마다 네트워크 왕복. 로컬 메모리보다 수천 배 느린 경로가 생김
메모리는 꺼지면 사라짐—디스크 저장 기능이 있지만, 기본 설정(스냅숏 저장)에서는 비정상 종료 때 최근 몇 분의 쓰기를 잃을 수 있음(29편)

03편 그림을 다시 떠올려 보면, 메모리 읽기는 약 100ns이고 서버 간 네트워크 왕복은 약 0.5ms입니다. 5천 배 차이입니다. 그래서 우리 서버가 Redis 명령 하나를 보내고 답을 받는 시간은 Redis 안에서 일하는 시간보다 네트워크를 오가는 시간이 대부분입니다.

핵심 — Redis 호출 한 번 ≈ 네트워크 왕복 한 번. Redis를 빠르게 쓰려면 왕복 횟수를 줄이는 것이 먼저이고(24편의 N+1과 같은 이야기), 왕복 자체가 아까운 값이라면 애초에 Redis가 아니라 로컬 메모리에 둘 값일 수 있습니다(3절).

메모리 상한(maxmemory)을 정해 두면, 기본 정책(noeviction)에서는 상한에 닿는 순간 쓰기 명령이 오류로 실패하고 읽기만 계속됩니다. 캐시로 쓸 때 무엇을 먼저 지울지 정하는 방법은 31편에서 봅니다.

3Redis가 없어도 되는 경우가 많다

Redis를 넣으면 1절의 문제는 풀리지만, 없던 비용이 생깁니다.

  • 요청마다 네트워크 왕복 — 로컬 메모리로 충분했던 값도 이제 매번 다른 서버를 다녀옵니다.
  • 장애점이 하나 늘어남 — Redis가 느려지거나 죽으면, 그 응답을 기다리는 요청이 함께 밀립니다(16편의 장애 전파).
  • 같은 데이터가 두 곳에 — DB와 Redis의 값이 어긋날 수 있고, 언제 지우고 다시 채울지 설계해야 합니다(26편).
  • 운영 비용 — 메모리 서버 비용, 모니터링, 장애 조치 구성(29편)이 추가됩니다.

그래서 Redis를 넣기 전에, 같은 목적을 Redis 없이 이룰 수 있는지 먼저 봅니다.

하고 싶은 것Redis 없이 먼저 볼 것그래도 Redis가 필요해지는 때
자주 읽는 값을 빠르게로컬 캐시(Caffeine 등, 26편)서버마다 값이 달라지면 안 되거나, 서버마다 따로 담기엔 데이터가 클 때
느린 조회를 빠르게인덱스·실행 계획(18·19편), 쿼리 수 줄이기(24편)쿼리를 고쳐도 같은 결과를 아주 자주 읽을 때
동시에 수량 줄이기·중복 방지DB 조건부 UPDATE, 유니크 제약, DB 락(22편)요청이 한순간에 몰려 DB가 그 경쟁을 감당하지 못할 때 (선착순 등)
로그인 상태 유지토큰(JWT, 14편)서버에서 세션을 강제로 끊어야 하는데 서버가 여러 대일 때

로컬 캐시는 JVM 안의 메모리라 네트워크 왕복이 없지만, 서버마다 따로 있어 서로 공유되지 않습니다. 26편 3절의 비교 표가 이 차이입니다.

4공유·속도·잃어도 되는 데이터에 맞는다

1~3절을 합치면, Redis가 잘 맞는 데이터는 세 조건을 함께 가집니다.

  1. 여러 서버가 함께 봐야 한다 — 아니면 로컬 메모리로 충분합니다.
  2. 요청마다 읽고 쓸 만큼 빨라야 한다 — 가끔 읽는 값이면 DB로 충분합니다.
  3. 잃어도 다시 만들 수 있거나, 어차피 수명이 짧다 — 원본이 DB에 있거나, 잠깐 쓰고 버리는 값입니다.

공식 문서가 꼽는 쓰임새를 이 세 조건으로 읽어 보면 모두 들어맞습니다.

쓰임새왜 공유하나잃으면자료구조 · 관련 편
캐시 (Cache-aside)모든 서버가 같은 값을 보도록DB에서 다시 읽으면 됨String·Hash, 26편
세션 저장어느 서버로 가도 로그인 유지다시 로그인Hash(Spring Session), 14편
요청 횟수 제한서버 전체의 합산 횟수로 제한잠시 제한이 느슨해짐String(INCR + 만료)
랭킹모두 같은 순위를 봄DB 집계로 다시 만듦Sorted Set, 31편
분산 락모든 서버가 보는 하나의 락락이 풀려 두 서버가 동시에 들어갈 수 있음String(SET … NX), 30편
작업 큐여러 서버가 작업을 나눠 처리작업이 빠지거나 두 번 처리될 수 있음List·Streams

공식 FAQ가 소개하는 흔한 설계도 같은 이야기입니다. 쓰기가 아주 많은 작은 데이터는 Redis에, 큰 데이터는 SQL 같은 디스크 DB에 둡니다.

핵심 — 세 번째 조건(잃어도 되는가)이 가장 자주 빠뜨리는 질문입니다. 원본 데이터를 Redis에만 두는 것이 금지된 것은 아니지만, 그러려면 29편에서 볼 유실 범위(마지막 몇 초·몇 분, 장애 조치 때의 쓰기)를 받아들일 수 있어야 합니다. 공식 문서도 PostgreSQL 수준의 데이터 안전이 필요하면 디스크 저장 방식 두 가지(RDB와 AOF)를 함께 쓰라고 안내합니다.

5넣기 전에 다섯 가지를 묻는다

실무에서 "여기에 Redis를 쓸까?"를 판단할 때는 아래 순서로 묻습니다. ①~③은 쓸지 말지를, ④·⑤는 쓴다면 무엇을 먼저 설계할지를 정합니다.

  • ② 원본이 없는 데이터(포인트 잔액, 주문 상태처럼 잃으면 안 되는 것)는 DB가 원본이고, Redis는 그 사본이나 빠른 계산용으로 둡니다. Redis에만 두려면 29편의 유실 범위를 확인합니다.
  • ④ Redis가 죽었을 때를 정하지 않으면, 캐시 하나 때문에 서비스 전체가 멈춥니다. 캐시라면 "Redis 오류 → DB로 응답"이 기본 폴백입니다(실무 예시).
  • ⑤ DB와 어긋나는 시간을 얼마나 허용할지가 TTL과 캐시 무효화 방식을 정합니다(26편).

6실무 예시

실수 예시

거의 안 바뀌는 설정값까지 Redis에 넣었다

카테고리 목록, 배너 설정처럼 하루에 한 번 바뀔까 말까 한 값을 "캐시는 Redis"라는 습관대로 Redis에 넣었습니다. 한 화면을 그리는 데 이런 조회가 여러 번 필요해서, 요청마다 Redis 왕복이 몇 번씩 생겼습니다. Redis가 잠시 느려진 날에는 설정 조회까지 함께 느려졌습니다.

해결: 5절 ①에서 "서버끼리 같은 값이어야 하나?"를 물었다면, 몇 분 정도 서버마다 달라도 괜찮은 값이었습니다. 로컬 캐시(Caffeine)에 짧은 만료 시간을 두어 왕복을 없애고, Redis는 서버 간 공유가 꼭 필요한 값에만 남겼습니다.

장애 대응

Redis가 느려지자 캐시만 쓰던 API까지 모두 멈췄다

Redis 응답이 느려진 동안, 캐시 조회가 응답을 기다리며 요청 스레드를 붙잡았습니다. 명령 타임아웃을 정하지 않아 기본값(스프링 부트 + Lettuce에서 60초)만큼 기다렸고, 스레드가 바닥나 캐시와 상관없는 API까지 밀렸습니다(07·16편). 게다가 캐시 오류가 예외로 올라가 500을 냈습니다. 스프링 캐시 추상화의 기본 오류 처리기는 캐시 예외를 그대로 다시 던지기 때문입니다.

✓ 짧은 타임아웃 + 캐시 오류는 로그만 남기고 DB로
# application.yml — 평소 응답 시간을 보고 정함
spring.data.redis.timeout: 500ms

@Configuration
class CacheConfig implements CachingConfigurer {
    @Override
    public CacheErrorHandler errorHandler() {
        return new LoggingCacheErrorHandler();
        // 조회 오류는 캐시 미스로 처리 → 메서드가 실행되어 DB에서 읽음
    }
}

캐시는 "없어도 되는 것"이라 이렇게 폴백할 수 있습니다. 세션이나 락처럼 Redis 없이는 동작할 수 없는 쓰임새라면, 폴백 대신 29편의 구성(레플리카, 자동 장애 조치)으로 Redis 자체를 덜 죽게 만듭니다.

설계 이유

서버를 늘리자 세션을 어디에 둘지 다시 정했다

서버를 두 대로 늘리자 새로고침할 때마다 로그인이 풀렸습니다(14편 실무 예시). 선택지는 세 가지였습니다.

선택지장점대가
서버 메모리 그대로가장 빠르고 단순서버가 여러 대면 동작하지 않음
토큰(JWT)서버에 저장할 것이 없음발급한 토큰을 서버에서 강제로 끊기 어려움(14편)
Redis (Spring Session)모든 서버가 공유, 서버에서 세션을 지워 강제 로그아웃 가능Redis가 로그인의 필수 인프라가 됨 → 29편의 장애 대비

관리자가 특정 사용자를 즉시 로그아웃시켜야 한다는 요구가 있어 Redis를 골랐습니다. 세션은 잃어도 "다시 로그인"으로 복구되므로 4절의 세 조건에도 맞습니다.

실수 예시

포인트 잔액을 Redis에만 두었다가 일부가 사라졌다

적립이 잦아 DB가 부담된다는 이유로 포인트 잔액을 Redis에만 두고 INCRBY로 늘렸습니다. 그러다 Redis 장애 조치(primary 교체)가 일어난 뒤, 직전 몇 초 동안 적립된 포인트가 사라졌습니다. Redis의 복제는 기본적으로 비동기라, 레플리카에 아직 전달되지 않은 쓰기는 장애 조치 때 사라질 수 있습니다(29편).

해결: 5절 ②의 질문 "잃어도 다시 만들 원본이 있나?"에 "아니오"인 데이터였습니다. 원본은 DB에 두고, Redis는 조회용 사본이나 합산 카운터로만 쓴 뒤 주기적으로 DB에 반영하도록 바꿨습니다.

지금은 넘어가도 되는 것 · 창시자 회고의 세부 배경, 다른 인메모리 저장소(Memcached, Hazelcast 등)와의 비교, Redis 8의 JSON·검색·벡터 같은 확장 기능, AWS ElastiCache의 선택 기능 Durability(Valkey 9.0 이상, 여러 가용 영역에 쓰기를 기록), 캐시 전용 노드를 따로 두는 구성

Redis는 어떤 문제를 풀려고 쓰나요? 서버가 한 대라면요?
서버가 여러 대가 되면 세션·캐시·카운터·락처럼 모든 서버가 함께 봐야 하는 상태가 생깁니다. JVM 메모리는 서버끼리 공유되지 않고, 요청마다 읽고 쓰는 작은 값을 모두 DB로 보내면 DB가 병목이 됩니다. Redis는 이런 상태를 메모리에 두고 네트워크로 공유해 빠르게 처리합니다. 서버가 한 대이거나 공유할 필요가 없으면 이 문제 자체가 없어서, 로컬 메모리로 충분한 경우가 많습니다.
Redis를 넣으면 생기는 비용은 무엇인가요?
호출마다 네트워크 왕복이 생기고, Redis가 느려지거나 죽으면 그것을 기다리는 요청이 함께 밀리는 장애점이 늘어납니다. DB와 Redis에 같은 데이터가 있으면 어긋날 수 있어 무효화를 설계해야 합니다. 데이터는 메모리 크기를 넘을 수 없고 메모리는 비싸며, 기본 설정에서는 비정상 종료 때 최근 쓰기를 잃을 수 있습니다.
어떤 데이터가 Redis에 맞고, 어떤 데이터는 DB에 두나요?
여러 서버가 함께 봐야 하고, 요청마다 읽고 쓸 만큼 빨라야 하며, 잃어도 다시 만들 수 있거나 수명이 짧은 데이터가 맞습니다. 캐시, 세션, 요청 횟수 제한, 랭킹 같은 것입니다. 포인트 잔액이나 주문 상태처럼 잃으면 안 되고 원본이 따로 없는 데이터는 DB가 원본이고, Redis는 사본이나 빠른 계산용으로만 씁니다.
로컬 캐시 대신 Redis를 고르는 기준은 무엇인가요?
서버마다 값이 잠깐 달라도 되고 데이터가 작으면 로컬 캐시가 네트워크 왕복이 없어 더 빠르고 단순합니다. 서버 간 값이 반드시 같아야 하거나(가격, 재고 표시 등), 서버마다 따로 담기엔 데이터가 크거나, 세션처럼 서버끼리 공유해야 동작하는 값이면 Redis를 씁니다.
Redis 장애가 서비스 전체 장애로 번지지 않게 하려면 무엇을 하나요?
명령 타임아웃을 평소 응답 시간에 맞춰 짧게 정해(스프링 부트 + Lettuce 기본값은 60초) 요청 스레드가 오래 묶이지 않게 합니다. 캐시처럼 없어도 되는 쓰임새는 캐시 오류를 로그만 남기고 DB로 응답하게 합니다(스프링에서는 CacheErrorHandler, 기본은 예외를 다시 던짐). 세션이나 락처럼 Redis가 꼭 필요한 쓰임새는 레플리카와 자동 장애 조치로 Redis 자체의 가용성을 높입니다.
