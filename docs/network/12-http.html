HTTP 기본과 멱등성

HTTP는 클라이언트와 서버가 주고받는 요청과 응답의 약속입니다. HTTP/1.1과 HTTP/2는 TCP 위에서, HTTP/3은 QUIC(UDP 기반) 위에서 동작합니다. 메서드와 상태 코드를 "문법"으로 외우기보다, 재시도해도 안전한가(멱등성)와 이 상태 코드는 누가 잘못한 건가를 판단하는 데 쓰는 것이 실무 포인트입니다.

1. HTTP 메시지는 약속된 형식이다2. 메서드와 멱등성3. 상태 코드: 누구의 잘못인가4. 실무 예시5. 설명해보기

1HTTP 메시지는 약속된 형식이다: 시작 줄 · 헤더 · 본문

요청
POST /orders HTTP/1.1       ← 메서드, 경로
Host: api.shop.com
Content-Type: application/json
Authorization: Bearer eyJ…   ← 헤더
Idempotency-Key: 7f3a-…

{"productId": 12, "qty": 1}  ← 본문
응답
HTTP/1.1 201 Created        ← 상태 코드
Content-Type: application/json
Location: /orders/981        ← 헤더

{"orderId": 981}             ← 본문

위 모습은 HTTP/1.1 기준입니다. HTTP/1.1은 시작 줄과 헤더를 사람이 읽을 수 있는 글자로 쓰고, 본문은 JSON이든 이미지든 어떤 바이트든 담을 수 있습니다. HTTP/2와 HTTP/3도 시작 줄·헤더·본문이라는 뜻은 같고, 연결에 실어 보내는 방식만 바이너리 프레임으로 바뀝니다. 스프링 코드에서는 차이가 거의 보이지 않으니 "뜻은 같고 전송 방식만 다르다"고 기억하면 됩니다.

HTTP는 무상태입니다. 서버는 이전 요청을 기억하지 않으니, 필요한 정보(누구인지, 어떤 형식인지)를 매 요청의 헤더에 담아 보냅니다. 로그인 상태를 어떻게 유지하는지는 14편에서 다룹니다.

2메서드와 멱등성

멱등성은 "같은 요청을 여러 번 보내도 서버에 남는 효과가 한 번 보낸 것과 같다"는 성질입니다. 응답까지 같을 필요는 없습니다(DELETE의 두 번째 응답이 404여도 멱등). 네트워크는 언제든 응답을 잃어버릴 수 있기 때문에, 그냥 다시 보내도 되는지를 판단하는 기준이 됩니다.

메서드용도멱등재시도
GET조회 (상태를 바꾸지 않는 것이 약속. 로그·조회수 같은 부수 효과는 있을 수 있음)✓안전
PUT대상 전체를 이 값으로 교체✓안전
DELETE삭제✓안전 (두 번째는 404일 수 있지만 상태는 같음)
PATCH일부 수정보통 ✕동작에 따라 다름
POST생성, 처리 요청✕그냥 재시도하면 중복 위험

3상태 코드: 누구의 잘못인가

코드뜻헷갈리기 쉬운 짝
200 / 201 / 204성공 / 생성됨 / 성공, 본문 없음
400요청 자체가 잘못됨 (형식 오류, 검증 실패 등)
401 / 403누구인지 모름(인증 필요) / 누군지 알지만 권한 없음401 = 로그인하세요, 403 = 당신은 안 됩니다
404 / 409대상 없음 / 현재 상태와 충돌 (이미 존재, 버전 충돌)
429너무 많이 요청함 (속도 제한)재시도는 Retry-After 이후
500우리 애플리케이션 내부 오류
502 / 503 / 504프록시가 받은 응답이 이상함 / 지금 처리 불가 / 프록시가 기다리다 포기보통 로드밸런서가 만들어서 돌려줌

4xx는 대체로 "요청을 고쳐서 보내라"(같은 요청을 재시도해 봐야 소용없음)는 뜻이지만, 429·408은 예외적으로 잠시 뒤 재시도할 수 있습니다. 5xx는 "서버 쪽 문제"(잠시 뒤 재시도로 성공할 수 있음)입니다. 재시도 여부를 판단할 때도 이 구분을 씁니다(16편).

4실무 예시

실수 예시

결제 요청 타임아웃 → 재시도 → 이중 결제

클라이언트가 결제를 요청했고 서버는 결제를 이미 처리했지만, 응답이 오는 도중 타임아웃이 났습니다. 클라이언트는 실패로 알고 다시 보냅니다. 타임아웃은 "실패"가 아니라 "결과를 모름"입니다.

✓ 서버 쪽 구현의 뼈대
-- 멱등 키에 유니크 제약: 동시에 두 요청이 와도 하나만 저장됨 (05편의 원자성)
CREATE TABLE payment (
  id BIGINT PRIMARY KEY,
  idempotency_key VARCHAR(64) NOT NULL UNIQUE,
  …
);
// 이미 있으면 기존 결과 반환, 없으면 처리 후 저장 (유니크 위반 시 기존 결과 조회)
장애 대응

502와 504, 우리 앱 로그에는 에러가 없다

클라이언트는 502/504를 받았는데 스프링 로그에는 에러가 없습니다. 이 코드들은 대개 우리 앱이 아니라 앞단 로드밸런서가 만든 응답이기 때문입니다.

코드흔한 원인확인할 것
504 Gateway Timeout우리 앱의 응답이 LB의 대기 시간(예: 60초)보다 오래 걸림느린 API, 앱 쪽 타임아웃이 LB보다 긴지
502 Bad GatewayLB가 재사용하려던 연결을 앱이 먼저 끊음, 앱이 죽거나 재시작 중앱의 keep-alive 유지 시간이 LB 유휴 시간보다 짧은지, 배포 중이었는지
503 Service UnavailableLB에 등록된 대상 서버가 없음, 또는 앱이 과부하로 거절대상 등록·배포 상태, 서버 상태 (09편). 참고: AWS ALB는 대상이 전부 unhealthy면 오히려 전체로 보내는 fail-open 동작

502의 keep-alive 원인은 11편의 Connection reset과 같은 구조입니다. 방향만 반대입니다. 연결을 받는 쪽(앱)은 연결을 거는 쪽(LB)보다 유휴 연결을 더 오래 유지해야 합니다.

실수 예시

GET 요청으로 데이터를 바꿨다

GET /coupons/123/use처럼 조회 메서드로 상태를 바꾸면, 브라우저 미리 불러오기·검색 봇·캐시·재시도 로직이 "GET은 안전하다"고 믿고 마음대로 다시 호출합니다. 쿠폰이 사용자도 모르게 사용되는 식의 사고가 납니다. 상태를 바꾸는 요청은 POST·PUT·PATCH·DELETE로 만듭니다.

실수 예시

모든 응답을 200으로 보내고 본문에 실패를 담았다

✕ 실패인데 200
HTTP/1.1 200 OK
{"success": false, "message": "재고 부족"}

모니터링·로드밸런서·재시도 로직은 상태 코드만 봅니다. 모든 응답이 200이면 에러율 그래프가 항상 0%이고, 장애가 나도 알람이 울리지 않습니다. 실패는 알맞은 4xx/5xx로 응답하고, 본문에는 원인 코드와 메시지를 담습니다.

5설명해보기

답을 열기 전에 먼저 소리 내어 설명해 보세요.

멱등성이란 무엇이고, 왜 중요한가요?
같은 요청을 여러 번 보내도 서버에 남는 효과가 한 번 보낸 것과 같은 성질입니다. 응답까지 같을 필요는 없습니다. 네트워크 오류나 타임아웃이 나면 요청이 처리됐는지 알 수 없는데, 멱등한 요청은 그냥 재시도해도 안전하므로 장애 대응과 재시도 설계의 기준이 됩니다.
결제 요청이 타임아웃 났을 때 그냥 재시도하면 안 되는 이유와 해결책은?
타임아웃은 실패가 아니라 결과를 모르는 상태라, 서버에서는 이미 결제가 처리됐을 수 있습니다. POST는 멱등하지 않아 재시도하면 이중 결제가 됩니다. 요청마다 멱등 키를 보내고, 서버가 키에 유니크 제약을 걸어 같은 키면 저장된 결과를 반환하게 합니다.
401과 403의 차이는?
401은 인증 정보가 없거나 잘못되어 누구인지 알 수 없다는 뜻이고, 403은 누구인지는 알지만 그 작업을 할 권한이 없다는 뜻입니다.
클라이언트가 502를 받았는데 애플리케이션 로그에는 에러가 없다면?
502는 대개 앞단 로드밸런서가 만든 응답입니다. 앱이 LB보다 먼저 유휴 연결을 끊었거나(앱의 keep-alive 시간이 LB 유휴 시간보다 짧음), 배포·재시작 중이었는지를 확인합니다.
