타임아웃·재시도·장애 전파

지금까지의 조각이 한데 모이는 편입니다. 스레드 풀(07), 커넥션 풀(15), 멱등성(12). 실무 장애의 상당수는 외부 서비스 하나가 느려진 것이 우리 서버 전체로 번지는 형태입니다. 이 편은 그 번지는 길을 끊는 네 가지 도구, 타임아웃·재시도·서킷 브레이커·벌크헤드를 다룹니다.

1. 느림은 이렇게 번진다2. 타임아웃: 모든 외부 호출에, 바깥보다 짧게3. 재시도: 안전할 때만, 간격을 두고, 몇 번만4. 서킷 브레이커: 계속 실패하면 잠시 부르지 않는다5. 실무 예시6. 설명해보기

1느림은 이렇게 번진다

에러는 빨리 실패하니 오히려 덜 위험합니다. 진짜 위험한 건 느림입니다. 느린 호출은 자원을 쥔 채로 기다리게 만들고, 기다리는 줄은 앞에서 본 풀들을 타고 번집니다.

2타임아웃: 모든 외부 호출에, 바깥보다 짧게

  • 모든 네트워크 호출에 둔다: HTTP(15편의 세 가지), DB 쿼리, Redis, 메시지 브로커
  • 값은 근거로 정한다: 그 API의 평소 응답 시간 상위 99%(p99)에 여유를 조금 더한 값. "넉넉히 30초"는 타임아웃이 없는 것과 비슷합니다.
  • 안쪽이 바깥보다 짧게: 호출 사슬에서 바깥이 먼저 포기하면, 안쪽은 아무도 기다리지 않는 일을 계속합니다.

3재시도: 안전할 때만, 간격을 두고, 몇 번만

기준재시도 O재시도 X
요청 종류멱등한 요청(GET, PUT), 멱등 키가 있는 POST (12편)멱등 키 없는 POST
실패 종류연결 실패, 타임아웃, 502·503·504, 429(Retry-After 후)400·401·403·404 등 4xx (다시 보내도 같음)
방법지수 백오프(0.2s → 0.4s → 0.8s) + 지터(무작위 흔들기) + 횟수 제한(보통 2~3회)

4서킷 브레이커: 계속 실패하면 잠시 부르지 않는다

상대가 확실히 아픈데 계속 부르면, 우리는 매번 타임아웃만큼 기다리고 상대는 회복할 틈이 없습니다. 서킷 브레이커는 최근 실패율(또는 느린 호출 비율)이 기준을 넘으면 호출 자체를 막고 즉시 실패(또는 대체 응답)합니다.

벌크헤드는 배의 격벽처럼 자원을 칸막이로 나누는 것입니다. 외부 호출마다 전용 스레드 풀(07편)이나 전용 커넥션 수를 두면, 결제 API가 막혀도 결제 칸만 잠기고 다른 기능은 살아남습니다.

5실무 예시

좋은 패턴

Resilience4j로 결제 호출 보호하기

✓ application.yml
resilience4j:
  circuitbreaker:
    instances:
      payment:
        sliding-window-size: 50              # 최근 50건 기준
        failure-rate-threshold: 50           # 50% 넘게 실패하면 열림
        slow-call-duration-threshold: 2s     # 2초 넘으면 '느린 호출'
        slow-call-rate-threshold: 50         # 느린 호출 50% 넘어도 열림
        wait-duration-in-open-state: 10s
        permitted-number-of-calls-in-half-open-state: 5
✓ 대체 응답(fallback)과 함께
@CircuitBreaker(name = "payment", fallbackMethod = "payLater")
public PayResult pay(PayRequest req) {
    return paymentClient.pay(req);   // 15편: 타임아웃이 설정된 클라이언트
}

private PayResult payLater(PayRequest req, Throwable t) {
    return PayResult.pending(req.orderId());   // "결제 확인 중" 처리 후 나중에 재확인
}

대체 응답은 비즈니스 결정입니다. 추천 목록처럼 빈 값으로 대체해도 되는 것이 있고, 결제처럼 "보류 후 재확인"이 필요한 것이 있습니다.

실수 예시

재시도 폭풍: 복구 중인 서버를 다시 쓰러뜨렸다

결제 서버가 잠시 멈췄다 살아나는 순간, 모든 클라이언트가 동시에 쌓아 둔 재시도를 쏟아부어 다시 쓰러졌습니다. 간격이 고정(매 1초)이라 모든 재시도가 같은 순간에 몰렸습니다.

해결: 지수 백오프에 지터를 더해 재시도 시점을 흩뜨리고, 재시도는 한 층에서만, 서킷 브레이커로 상대가 아플 때는 아예 부르지 않습니다.

실수 예시

트랜잭션 안에서 외부 API를 호출했다

@Transactional 메서드 안에서 결제 API를 부르면, 결제 응답을 기다리는 동안 DB 커넥션도 함께 쥐고 있습니다. 결제가 느려지면 톰캣 스레드뿐 아니라 DB 커넥션 풀(23편)까지 고갈되어, DB를 쓰는 모든 기능이 멈춥니다. 또 결제는 성공했는데 이후 DB 커밋이 실패하면 되돌릴 방법도 없습니다.

해결: 외부 호출은 트랜잭션 밖으로 빼고, "주문 생성(트랜잭션) → 결제 호출 → 결과 반영(트랜잭션)"처럼 나눕니다 (20편).

설계 이유

빨리 실패하는 것이 친절하다

30초 뒤의 실패보다 1초 만의 실패가 사용자에게도, 서버에게도 낫습니다. 사용자는 바로 다시 시도하거나 다른 행동을 할 수 있고, 서버는 스레드와 커넥션을 붙잡지 않습니다. 이 편의 네 도구는 모두 "기다림에 상한을 두고, 안 될 것 같으면 빨리 포기한다"는 한 가지 원칙의 변형입니다.

지금은 넘어가도 되는 것 · 서킷 브레이커 라이브러리의 내부 상태 머신 구현, 슬라이딩 윈도우 알고리즘 세부, 서비스 메시(Istio 등)의 재시도 정책

답을 열기 전에 먼저 소리 내어 설명해 보세요.

외부 API 하나가 30초씩 응답하지 않을 때, 타임아웃이 없는 서버에 일어나는 일을 순서대로 설명해 보세요.
그 API를 호출한 요청 스레드들이 응답을 기다리며 묶이고, 트래픽이 계속 들어오면 톰캣 스레드가 모두 소진됩니다. 그러면 그 API와 무관한 요청까지 처리되지 못하고, 헬스 체크도 실패해 로드밸런서가 서버를 제외하며, 남은 서버로 부하가 몰려 연쇄 장애가 됩니다.
재시도해도 되는 경우와 안 되는 경우를 구분해 보세요.
멱등한 요청이나 멱등 키가 있는 요청이, 연결 실패·타임아웃·5xx처럼 일시적일 수 있는 이유로 실패했을 때 재시도합니다. 4xx처럼 요청 자체가 잘못된 경우나 멱등하지 않은 POST는 재시도하지 않습니다. 재시도할 때는 백오프, 지터, 횟수 제한을 둡니다.
서킷 브레이커의 세 상태와 목적은?
닫힘에서는 정상 호출하며 실패율을 재고, 기준을 넘으면 열림이 되어 호출하지 않고 즉시 실패합니다. 일정 시간 뒤 반열림에서 일부만 시험 호출해 성공하면 닫힘, 실패하면 다시 열림으로 갑니다. 아픈 상대를 계속 기다리느라 우리 자원이 묶이는 것을 막고, 상대에게 회복 시간을 줍니다.
호출 사슬에서 타임아웃은 어떤 순서로 정해야 하나요?
바깥 호출의 타임아웃이 안쪽 호출(재시도 포함)보다 길어야 합니다. 바깥이 먼저 포기하면 안쪽은 아무도 기다리지 않는 작업을 계속하며 자원을 낭비하고, 사용자의 재시도와 겹쳐 중복 처리가 생길 수 있습니다.
