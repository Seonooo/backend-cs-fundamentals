DB 커넥션 풀

세 번째이자 마지막 풀입니다. 07편 스레드 풀, 15편 HTTP 커넥션 풀과 같은 패턴이라 새로 배울 것은 적습니다. 대신 DB 커넥션은 트랜잭션·락·쿼리 속도와 얽혀 있어서, 서비스 전체가 멈추는 장애가 가장 자주 나는 풀이기도 합니다.

1세 가지 풀, 같은 질문

스레드 풀 (07)HTTP 커넥션 풀 (15)DB 커넥션 풀 (HikariCP)
재사용하는 것스레드TCP·TLS 연결DB 연결 (TCP + 인증 + 세션)
크기core / max전체 / 호스트당maximumPoolSize (기본 10)
다 쓰고 있으면큐에서 대기반납 대기반납 대기
대기 한도큐 크기, 거부 정책연결 획득 타임아웃connectionTimeout (기본 30초)
오래된 자원 정리keepAlive유휴 만료, 최대 수명maxLifetime (기본 30분), idleTimeout (기본 10분, minimumIdle < maximumPoolSize일 때만 동작)
핵심 — 커넥션 풀 고갈의 원인은 거의 항상 "커넥션을 너무 오래 쥐는 것"입니다. 풀 크기를 늘리기 전에, 누가 왜 오래 쥐고 있는지부터 찾습니다.

2커넥션은 언제부터 언제까지 쥐고 있나

기본적으로 트랜잭션이 시작될 때 풀에서 빌리고, 커밋·롤백할 때 반납합니다(20편). 그런데 스프링 부트의 OSIV(Open Session In View)가 켜져 있으면(기본값 켜짐), JPA 지연 로딩을 위해 처음 DB를 쓴 순간부터 응답을 다 만들 때까지 커넥션을 쥐고 있습니다.

스프링 부트는 OSIV가 켜져 있으면 시작 로그에 경고를 남깁니다. API 서버라면 spring.jpa.open-in-view: false로 끄고, 필요한 데이터는 트랜잭션 안에서 DTO로 만들어 반환하는 것이 일반적입니다 (24편).

3크기: 클수록 좋은 게 아니다

DB 서버도 CPU·디스크가 한정되어 있어서, 동시에 실행하는 쿼리가 너무 많으면 오히려 서로 경합하며 느려집니다(04편의 컨텍스트 스위칭과 같은 이야기). HikariCP 문서는 출발점으로 "DB 서버의 코어 수 × 2 + 디스크 수" 정도의 작은 풀을 제안합니다. 경험에서 나온 출발점일 뿐이니, 최종 크기는 DB의 CPU·I/O 사용률을 보며 부하 테스트로 정합니다. 그리고 반드시 서버 대수를 곱해서 봐야 합니다.

4실무 예시

장애 대응

Connection is not available, request timed out after 30000ms

가장 유명한 HikariCP 에러
SQLTransientConnectionException: HikariPool-1 -
  Connection is not available, request timed out after 30000ms
  (total=10, active=10, idle=0, waiting=37)

풀 10개가 모두 사용 중이고 37개 요청이 기다리다 30초 만에 포기했다는 뜻입니다. 풀을 키우기 전에, 지금까지 배운 원인 목록을 차례로 확인합니다.

원인어디서 배웠나
트랜잭션 안에서 외부 API 호출16, 20편
OSIV가 켜져 응답 끝까지 점유이 편 2번
느린 쿼리 (인덱스 없음)18, 19편
락 대기 (다른 트랜잭션이 행을 잡고 있음)22편
REQUIRES_NEW로 요청당 커넥션 2개06편
가상 스레드로 동시 요청 급증08편
커넥션 누수 (직접 얻은 커넥션을 닫지 않음)leakDetectionThreshold로 확인
좋은 패턴

설정과 지표를 함께 둔다

✓ application.yml 예
spring:
  jpa:
    open-in-view: false
  datasource:
    hikari:
      maximum-pool-size: 20
      connection-timeout: 3000        # 30초는 너무 김 → 빨리 실패 (16편)
      max-lifetime: 1740000           # DB·방화벽의 연결 종료 시간보다 짧게
      leak-detection-threshold: 20000 # 20초 넘게 안 돌려주면 경고 로그

그리고 Actuator + Micrometer로 hikaricp_connections_active, hikaricp_connections_pending 같은 지표를 모니터링합니다. pending(대기)이 0보다 자주 커지면 장애 전에 신호가 옵니다.

실수 예시

새벽에 한가하다가 아침 첫 요청들이 실패한다

트래픽이 없는 동안 풀의 커넥션이 오래 쉬었는데, 그사이 DB(wait_timeout)나 중간 방화벽이 유휴 연결을 끊었습니다. 11편·15편에서 본 "상대가 먼저 끊은 유휴 연결" 문제와 같습니다.

흔한 에러
Communications link failure … The last packet successfully received from the server was 28,800,123 milliseconds ago

해결: HikariCP의 maxLifetime을 DB와 방화벽의 유휴 종료 시간보다 짧게 두어, 상대가 끊기 전에 풀이 먼저 커넥션을 교체하게 합니다. 이 설정은 10편에서 본 DB 장애 조치(IP 변경) 뒤 새 IP로 옮겨 가는 데도 도움이 됩니다.

5설명해보기

답을 열기 전에 먼저 소리 내어 설명해 보세요.

트래픽이 늘자 "Connection is not available" 에러가 난다. 풀 크기부터 늘리는 게 맞나요?
먼저 커넥션을 오래 쥐는 원인을 찾아야 합니다. 긴 트랜잭션, 트랜잭션 안의 외부 호출, 느린 쿼리, 락 대기, OSIV 같은 원인을 그대로 두고 풀만 키우면 DB 부하와 연결 수 한도 문제로 옮겨 갈 뿐입니다.
OSIV를 끄라고 권하는 이유는?
OSIV가 켜져 있으면 지연 로딩을 위해 요청이 끝날 때까지 DB 커넥션을 쥐고 있어, 외부 API 호출이나 응답 변환 시간까지 커넥션이 묶입니다. 끄면 트랜잭션 구간에서만 커넥션을 쓰므로 풀을 훨씬 효율적으로 씁니다. 대신 필요한 데이터는 트랜잭션 안에서 미리 조회해야 합니다.
커넥션 풀 크기를 정할 때 서버 대수를 고려해야 하는 이유는?
DB가 받는 연결 수는 풀 크기에 서버 대수를 곱한 값이기 때문입니다. 서버를 늘리거나 롤링 배포로 서버가 잠시 겹치면 DB의 max_connections를 넘어 새 연결이 거부될 수 있습니다.
