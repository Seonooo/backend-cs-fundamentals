HTTP 클라이언트 커넥션 풀

11편과 13편에서 TCP·TLS 연결을 새로 맺는 비용을 봤습니다. 그래서 우리 서버가 외부 API를 부를 때는 연결을 풀에 모아 두고 재사용합니다. 07편의 스레드 풀과 완전히 같은 패턴이라, 같은 세 가지 질문(크기·대기·고갈)을 던지면 됩니다.

1커넥션 풀의 모양

HTTP 클라이언트의 풀에는 제한이 두 겹으로 걸립니다. 전체 최대 연결 수와 호스트(route)당 최대 연결 수입니다. 실무에서 발목을 잡는 건 대부분 두 번째입니다.

2타임아웃은 세 가지다

풀을 쓰는 HTTP 호출에는 기다리는 구간이 세 군데 있고, 각각 따로 타임아웃을 둡니다. 하나라도 비어 있으면 그 구간에서 무한정 기다릴 수 있습니다.

3스프링에서 설정하기

스프링의 HTTP 클라이언트(RestTemplate, RestClient, Feign 등)는 실제 통신을 밑에 붙인 구현체에 맡깁니다. 구현체에 따라 설정할 수 있는 풀이 없거나 기본값이 작으므로, 무엇을 쓰고 있는지부터 확인합니다. 예를 들어 Apache HttpClient 5의 풀은 기본값이 전체 25개, 호스트당 5개로 작은 편입니다.

✓ RestClient + Apache HttpClient 5 풀 설정 예
var cm = PoolingHttpClientConnectionManagerBuilder.create()
    .setMaxConnTotal(100)
    .setMaxConnPerRoute(20)                                   // 호스트당
    .setDefaultConnectionConfig(ConnectionConfig.custom()
        .setConnectTimeout(Timeout.ofSeconds(1))              // ② 연결
        .setSocketTimeout(Timeout.ofSeconds(3))               // ③ 읽기
        .setTimeToLive(TimeValue.ofMinutes(5))                // 연결 최대 수명
        .setValidateAfterInactivity(TimeValue.ofSeconds(10))  // 오래 쉰 연결은 확인 후 사용
        .build())
    .build();

var http = HttpClients.custom()
    .setConnectionManager(cm)
    .setDefaultRequestConfig(RequestConfig.custom()
        .setConnectionRequestTimeout(Timeout.ofMillis(500))   // ① 풀 대기
        .build())
    .evictIdleConnections(TimeValue.ofSeconds(30))            // 유휴 연결 정리
    .build();

RestClient paymentClient = RestClient.builder()
    .requestFactory(new HttpComponentsClientHttpRequestFactory(http))
    .baseUrl("https://api.payment.com")
    .build();   // 빈으로 등록해 재사용

숫자는 예시입니다. 호스트당 최대치는 "그 API를 동시에 부르는 요청 수"와 "상대 서버가 허용하는 동시 연결 수"를 함께 보고 정합니다.

4실무 예시

실수 예시

특정 외부 API 호출만 느려졌다

트래픽이 늘자 결제 API 호출 시간이 수백 ms 늘었습니다. 결제사에 문의해도 자기네 응답 시간은 정상이라고 합니다. 원인은 1번 그림 그대로, 호스트당 최대 연결 수(기본값 5) 때문에 우리 서버 안에서 연결을 기다린 것입니다. 늘어난 시간은 결제사가 아니라 ① 풀 대기 구간이었습니다.

확인: 클라이언트의 풀 지표(사용 중 / 대기 중 / 유휴 연결 수)를 Micrometer 등으로 노출해 두면 바로 보입니다.

실수 예시

호출할 때마다 클라이언트를 새로 만들었다

✕ 풀이 매번 새로 생김
public Result pay(Req req) {
  RestTemplate rt = new RestTemplate(
      new HttpComponentsClientHttpRequestFactory());
  return rt.postForObject(url, req, Result.class);
}
✓ 빈 하나를 재사용
private final RestClient paymentClient;  // 주입

public Result pay(Req req) {
  return paymentClient.post().body(req)
      .retrieve().body(Result.class);
}

풀 기반 클라이언트를 호출마다 새로 만들면 매번 빈 풀이 새로 생겨 연결이 재사용되지 않습니다. 11편의 TIME_WAIT 폭증, 13편의 TLS 비용이 그대로 돌아옵니다. 참고로 아무 설정 없는 new RestTemplate()은 JDK 기본 연결(HttpURLConnection)을 써서 JVM 공용 keep-alive로 연결은 재사용되지만, 타임아웃이 무한대이고 풀 설정을 조절할 수 없다는 점이 더 위험합니다.

장애 대응

가끔 나는 NoHttpResponseException / Connection reset

11편에서 본 유휴 연결 문제입니다. 풀에 오래 쉬던 연결을 꺼냈는데, 상대 서버나 중간 로드밸런서가 이미 끊어 버린 상태입니다.

  • 유휴 연결 정리 시간을 상대보다 짧게: 상대 LB 유휴 시간이 60초라면 우리는 30초 정도에 정리
  • 오래 쉰 연결은 쓰기 전에 확인: validateAfterInactivity
  • 최대 수명: DNS로 IP가 바뀌어도(10편) 옛 연결을 영원히 쓰지 않게
실수 예시

풀 대기 타임아웃이 없어서 서버 전체가 멈췄다

결제 API가 느려져 연결이 반납되지 않자, 결제를 부르는 요청 스레드들이 ① 풀 대기에서 무한정 기다렸습니다. 톰캣 스레드가 여기에 전부 묶이면서 결제와 상관없는 API까지 멈췄습니다 (07편 마지막 예시와 같은 흐름).

해결: 세 가지 타임아웃을 모두 짧게 명시하고, 느려지면 빠르게 실패하도록 만듭니다. 실패 이후의 재시도·차단 전략은 16편에서 다룹니다.

5설명해보기

답을 열기 전에 먼저 소리 내어 설명해 보세요.

HTTP 클라이언트에 커넥션 풀을 쓰는 이유는?
호출마다 TCP·TLS 연결을 새로 맺으면 핸드셰이크 왕복과 연산 비용이 들고, 임시 포트와 TIME_WAIT가 쌓입니다. 연결을 풀에 두고 재사용하면 이 비용이 사라져 지연과 자원 소모가 줄어듭니다.
풀 전체는 여유가 있는데 특정 API 호출만 느린 이유는?
호스트당 최대 연결 수 제한에 걸린 것입니다. 그 호스트로 가는 연결이 모두 사용 중이면 풀 전체에 여유가 있어도 새 요청은 연결이 반납될 때까지 기다립니다.
HTTP 호출의 세 가지 타임아웃을 구분해 보세요.
연결 획득 타임아웃은 풀에서 연결을 빌리기까지, 연결 타임아웃은 새 TCP 연결을 맺기까지, 읽기 타임아웃은 요청을 보낸 뒤 응답 데이터가 오기까지 기다리는 한도입니다.
스레드 풀, HTTP 커넥션 풀, DB 커넥션 풀의 공통 튜닝 포인트는?
크기(상한), 다 쓰고 있을 때의 대기와 그 타임아웃, 오래된 자원의 정리입니다. 대기에 한도가 없으면 한 곳의 느림이 대기 줄을 통해 전체로 번집니다.
