트랜잭션과 @Transactional

트랜잭션은 여러 쿼리를 "전부 성공하거나, 전부 없던 일로" 묶는 단위입니다. 개념은 단순한데, 스프링의 @Transactional이 프록시로 동작한다는 점 때문에 실무 실수가 많이 나옵니다. 05편의 synchronized 함정도 여기서 비롯됐습니다.

1. 트랜잭션이 보장하는 것2. @Transactional은 프록시가 대신 처리한다3. 롤백 규칙과 전파4. 실무 예시5. 설명해보기

1트랜잭션이 보장하는 것

계좌 이체는 "A에서 출금"과 "B에 입금" 두 쿼리입니다. 출금만 되고 서버가 죽으면 돈이 사라집니다. 트랜잭션으로 묶으면 둘 다 반영되거나(커밋), 둘 다 취소됩니다(롤백).

ACID한 문장으로
원자성 (Atomicity)전부 되거나 전부 안 되거나
일관성 (Consistency)제약 조건(잔액 ≥ 0, 유니크 등)을 깨는 상태로 끝나지 않음
격리성 (Isolation)동시에 도는 트랜잭션끼리 서로 얼마나 보이나 (21편)
지속성 (Durability)커밋된 것은 서버가 죽어도 남음 (03편의 fsync)
잊기 쉬운 사실 — 트랜잭션이 열려 있는 동안 그 요청은 DB 커넥션 하나를 계속 쥐고 있습니다. 트랜잭션 길이 = 커넥션 점유 시간입니다. 그래서 트랜잭션은 짧을수록 좋습니다 (23편).

2@Transactional은 프록시가 대신 처리한다

스프링은 @Transactional이 붙은 빈을 프록시(대리 객체)로 감쌉니다. 외부에서 메서드를 부르면 프록시가 먼저 받아 트랜잭션을 시작하고, 진짜 메서드를 호출한 뒤, 끝나면 커밋이나 롤백을 합니다.

이 구조에서 실무 규칙 세 가지가 나옵니다.

  1. 같은 클래스 안에서 부른 메서드의 @Transactional은 무시된다. (this 호출은 프록시를 거치지 않음)
  2. 커밋은 메서드가 끝난 "뒤" 프록시가 한다. (05편 synchronized 함정의 원인)
  3. private 메서드에 붙여도 적용되지 않는다. (프록시가 가로챌 수 없음)

3롤백 규칙과 전파

상황기본 동작기억할 점
RuntimeException, Error롤백
체크 예외 (IOException 등)커밋롤백하려면 rollbackFor = Exception.class
전파 REQUIRED (기본)이미 트랜잭션이 있으면 거기에 참여안쪽에서 롤백 표시하면 바깥 전체가 롤백
전파 REQUIRES_NEW기존 것을 잠시 멈추고 새 트랜잭션 (새 커넥션)커넥션을 2개 씀 → 06편 커넥션 풀 데드락 주의
readOnly = true읽기 전용 힌트JPA 변경 감지 생략 등 최적화, 읽기 복제본 라우팅 기준 (25편)

4실무 예시

실수 예시

내부 호출이라 트랜잭션이 안 걸렸다

✕ 같은 클래스 안에서 호출
@Service
public class OrderService {
  public void placeOrder(Req r) {   // 트랜잭션 없음
    this.saveOrder(r);              // 프록시 안 거침
  }
  @Transactional
  public void saveOrder(Req r) { … }  // 적용 안 됨!
}
✓ 트랜잭션 경계를 바깥 메서드에 or 빈 분리
@Service
public class OrderService {
  private final OrderWriter writer;  // 별도 빈

  public void placeOrder(Req r) {
    writer.save(r);   // 프록시를 거침 ✓
  }
}

중간에 예외가 나도 롤백되지 않아 "재고는 줄었는데 주문은 없는" 데이터가 남습니다. 테스트에서 롤백을 꼭 확인합니다.

실수 예시

예외를 잡았는데 UnexpectedRollbackException이 난다

바깥 서비스가 안쪽 서비스(둘 다 REQUIRED)를 부르고, 안쪽의 예외를 try-catch로 잡아 무시했습니다. 그런데 커밋 시점에 이런 에러가 납니다.

로그
UnexpectedRollbackException: Transaction silently rolled back because it has been marked as rollback-only

안쪽 메서드가 런타임 예외로 끝나는 순간, 같은 트랜잭션 전체에 "롤백 전용" 표시가 붙습니다. 바깥에서 예외를 잡아도 그 표시는 지워지지 않으므로, 커밋하려는 순간 롤백되며 이 예외가 납니다.

해결: 실패해도 바깥은 계속되어야 하는 작업이면 안쪽을 별도 트랜잭션으로 분리하거나(REQUIRES_NEW, 커넥션 2개 주의), 예외가 트랜잭션 경계 밖으로 나가지 않도록 안쪽에서 처리합니다.

실수 예시

트랜잭션 안에서 외부 API 호출 (16편 복습)

✕ 결제 응답을 기다리는 동안 커넥션 점유
@Transactional
public void order(Req r) {
  Order o = orderRepo.save(new Order(r));
  paymentClient.pay(o);   // 2초~30초
  o.markPaid();
}
✓ 트랜잭션을 짧게 나눔
public void order(Req r) {
  Long id = orderTx.create(r);         // 짧은 트랜잭션 1
  PayResult p = paymentClient.pay(id); // 트랜잭션 밖
  orderTx.applyPayment(id, p);         // 짧은 트랜잭션 2
}

대신 "주문은 생겼는데 결제 결과 반영 전" 같은 중간 상태가 생깁니다. 주문 상태(PENDING → PAID)와 재확인 작업으로 이 상태를 명시적으로 다룹니다.

좋은 패턴

커밋이 확정된 뒤에만 알림 보내기

트랜잭션 안에서 알림을 보냈는데 이후 커밋이 실패하면, 없는 주문에 대한 알림이 나갑니다. 커밋 이후에 실행되도록 이벤트로 분리합니다.

✓ AFTER_COMMIT 이벤트 리스너
@Transactional
public void order(Req r) {
  Order o = orderRepo.save(new Order(r));
  events.publishEvent(new OrderPlaced(o.getId()));   // 바로 실행 안 됨
}

@TransactionalEventListener(phase = TransactionPhase.AFTER_COMMIT)
public void notify(OrderPlaced e) {
  notifier.send(e.orderId());   // 커밋 성공 후에만 실행 (07편처럼 @Async와 함께 쓰기도 함)
}

5설명해보기

답을 열기 전에 먼저 소리 내어 설명해 보세요.

같은 클래스 안의 @Transactional 메서드를 내부에서 호출하면 트랜잭션이 걸리나요? 이유는?
걸리지 않습니다. 트랜잭션은 스프링 프록시가 외부 호출을 가로챌 때 시작하는데, 내부 호출은 this로 진짜 객체의 메서드를 직접 부르므로 프록시를 거치지 않습니다. 트랜잭션이 필요한 메서드를 별도 빈으로 분리하는 것이 일반적입니다.
@Transactional 메서드에서 체크 예외가 발생하면 롤백되나요?
기본값으로는 롤백되지 않고 커밋됩니다. 스프링은 RuntimeException과 Error에서만 롤백합니다. 체크 예외에도 롤백하려면 rollbackFor를 지정합니다.
트랜잭션을 짧게 유지해야 하는 이유는?
트랜잭션 동안 DB 커넥션을 계속 점유하고, 수정한 행의 락도 유지됩니다. 길어지면 커넥션 풀이 고갈되고 다른 트랜잭션이 락을 기다리게 됩니다. 특히 외부 API 호출처럼 느리고 롤백할 수 없는 작업은 트랜잭션 밖으로 뺍니다.
UnexpectedRollbackException(rollback-only)은 왜 발생하나요?
같은 트랜잭션에 참여한 안쪽 메서드가 런타임 예외로 끝나 트랜잭션 전체가 롤백 전용으로 표시됐는데, 바깥에서 예외를 잡고 커밋을 시도했기 때문입니다. 표시는 지워지지 않으므로 커밋 시점에 롤백되며 이 예외가 납니다.
