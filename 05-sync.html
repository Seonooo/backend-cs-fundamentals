동기화: 경쟁 조건과 락

01에서 스레드들이 힙을 공유한다고 했습니다. 공유된 값을 여러 스레드가 동시에 바꾸면 결과가 틀어집니다. 이 편에서는 왜 틀어지는지, 자바에서 어떻게 막는지, 그리고 서버가 여러 대가 되면 그 방법이 왜 통하지 않는지까지 봅니다.

1. 경쟁 조건: count++도 안전하지 않다2. 자바의 해결 도구3. JVM 락은 그 서버 안에서만 통한다4. 실무 예시5. 설명해보기

1경쟁 조건: count++도 안전하지 않다

count++는 한 줄이지만 CPU 입장에서는 읽기 → 1 더하기 → 쓰기 세 단계입니다. 두 스레드가 이 세 단계를 섞어서 실행하면 한 번의 증가가 사라집니다.

이처럼 실행 순서에 따라 결과가 달라지는 상황을 경쟁 조건(race condition)이라고 하고, 여러 스레드가 동시에 들어가면 안 되는 코드 구간을 임계 영역이라고 합니다. 무서운 점은 대부분의 경우엔 잘 동작한다는 것입니다. 로컬 테스트에선 멀쩡하다가 트래픽이 몰릴 때만 틀어집니다.

위험한 패턴 두 가지 — 읽고-바꾸고-쓰기 (count++, stock = stock - 1)와 확인하고-행동하기 (if (!map.containsKey(k)) map.put(k, v)). 둘 다 "확인한 값"이 "행동할 때"까지 그대로라고 가정하는 코드입니다.

2자바의 해결 도구

가장 기본은 락입니다. 임계 영역에 한 번에 한 스레드만 들어가게 하고, 나머지는 문 앞에서 기다리게 합니다.

도구무엇을 해결하나언제 쓰나
synchronized임계 영역에 한 스레드만가장 간단한 기본 선택
ReentrantLock위와 같음 + 대기 타임아웃, 공정성 옵션"n초 기다려도 안 되면 포기"가 필요할 때
AtomicInteger, AtomicLong변수 하나를 락 없이 원자적으로 변경카운터, 시퀀스
ConcurrentHashMap여러 스레드가 동시에 써도 안전한 Map공유 Map (HashMap 대신)
volatile변경이 다른 스레드에 보이게만 함종료 플래그 같은 단순 신호 (count++는 해결 못 함)
불변 객체바뀌지 않으니 경쟁 자체가 없음가능하면 가장 좋은 선택

메모리 가시성: 바꿨는데 안 보인다

JIT 컴파일러나 CPU는 성능을 위해 값을 레지스터에 담아 두거나 명령 순서를 바꿀 수 있습니다(예: 루프 안의 running 읽기를 한 번만 하도록 최적화). 그래서 한 스레드가 바꾼 값을 다른 스레드가 한참 동안, 혹은 계속 못 볼 수 있습니다. volatile은 "이 변수는 항상 최신 값을 읽고 쓰라"는 표시입니다.

✓ 다른 스레드가 멈추라는 신호를 확실히 보게 하기
private volatile boolean running = true;

public void run() { while (running) { poll(); } }   // 워커 스레드
public void stop() { running = false; }            // 다른 스레드가 호출

volatile은 가시성만 보장합니다. count++ 같은 "읽고-바꾸고-쓰기"는 여전히 깨지므로 Atomic이나 락이 필요합니다. 실무에서는 volatile을 직접 쓸 일보다, 동시성 컬렉션과 Atomic 클래스를 쓰는 일이 훨씬 많습니다.

3JVM 락은 그 서버 안에서만 통한다

synchronized와 ReentrantLock은 JVM 메모리 안의 락입니다. 서버를 두 대로 늘리면 각 서버는 서로의 락을 모릅니다.

그래서 운영 서버가 여러 대인 백엔드에서는 동시성을 모든 서버가 함께 보는 곳에서 막습니다. 대표적으로 DB(조건부 UPDATE, 비관적·낙관적 락)나 Redis(분산 락)입니다. 자세한 방법은 22편에서 다룹니다.

4실무 예시

실수 예시

@Transactional 메서드에 synchronized를 붙였는데도 재고가 틀어진다

서버 한 대에서 테스트하는데도 동시 요청 100개를 보내면 재고가 맞지 않습니다. 락을 걸었는데 왜일까요?

✕ 락이 커밋보다 먼저 풀림
@Transactional
public synchronized void decrease(Long id) {
    Stock stock = stockRepository.findById(id).orElseThrow();
    stock.decrease(1);
}   // ← 여기서 락 해제. 하지만 커밋은 아직!

해결: 애초에 JVM 락은 서버가 늘면 소용이 없으므로, DB에서 원자적으로 처리합니다. 예: UPDATE stock SET qty = qty - 1 WHERE id = ? AND qty > 0 후 변경된 행 수 확인, 또는 비관적/낙관적 락 (20편 트랜잭션, 22편 DB 락).

실수 예시

ConcurrentHashMap을 썼는데도 중복 생성된다

Map 자체는 안전해도, 확인하고-행동하기를 두 번의 호출로 나누면 그 사이에 다른 스레드가 끼어듭니다.

✕ 두 번의 호출 사이 틈
if (!cache.containsKey(key)) {
    cache.put(key, load(key));
}
// 두 스레드가 동시에 통과 → load 2번
✓ 한 번의 원자적 호출
cache.computeIfAbsent(key, this::load);
// 확인과 저장을 한 번에

// 카운트 누적도: map.merge(k, 1, Integer::sum)
실수 예시

static으로 공유한 SimpleDateFormat

"매번 만들면 아까우니까" static 필드 하나로 공유한 SimpleDateFormat은 내부 상태를 가진 객체라 스레드 안전하지 않습니다. 트래픽이 몰리면 가끔 엉뚱한 날짜가 나오거나 예외가 납니다.

✓ 불변 객체로 교체
private static final DateTimeFormatter FMT = DateTimeFormatter.ofPattern("yyyy-MM-dd");
// java.time의 포매터는 불변 → 공유해도 안전

공유할 객체를 고를 때는 문서에서 "thread-safe" / "immutable" 여부를 확인하는 습관을 들입니다.

설계 이유

동시성 문제를 피하는 가장 좋은 방법은 공유하지 않는 것

락을 잘 거는 것보다 공유 상태를 만들지 않는 것이 더 안전합니다. 요청별 값은 지역 변수로(01편), 공유가 필요한 값은 불변 객체로, 서버 간 공유가 필요한 값은 DB·Redis로 보냅니다. 락은 그래도 남는 곳에만 씁니다.

5설명해보기

답을 열기 전에 먼저 소리 내어 설명해 보세요.

count++가 스레드 안전하지 않은 이유를 설명해 보세요.
count++는 읽기, 더하기, 쓰기의 세 단계로 실행됩니다. 두 스레드가 같은 값을 읽은 뒤 각자 더해서 쓰면, 한쪽의 증가가 다른 쪽의 쓰기에 덮여 사라집니다. AtomicInteger나 락으로 세 단계를 하나로 묶어야 합니다.
volatile을 붙이면 count++ 문제가 해결되나요?
아닙니다. volatile은 최신 값이 다른 스레드에 보이게 하는 가시성만 보장합니다. 읽기와 쓰기 사이에 다른 스레드가 끼어드는 문제(원자성)는 그대로라서 Atomic 클래스나 락이 필요합니다.
@Transactional과 synchronized를 같이 써도 동시성 문제가 생기는 이유는?
트랜잭션 커밋은 메서드 바깥의 스프링 프록시가 하고, synchronized 락은 메서드가 끝나면 풀립니다. 락이 풀린 뒤 커밋되기 전의 틈에 다른 스레드가 들어와 커밋되지 않은 옛 값을 읽습니다. 게다가 서버가 여러 대면 JVM 락 자체가 소용없으므로 DB 레벨에서 막아야 합니다.
서버를 여러 대로 늘리면 synchronized가 무용지물이 되는 이유와 대안은?
synchronized는 각 JVM의 메모리 안에서만 유효한 락이라 다른 서버의 스레드를 막지 못합니다. 모든 서버가 공유하는 DB의 원자적 UPDATE, 비관적·낙관적 락, 또는 Redis 분산 락으로 막아야 합니다.
