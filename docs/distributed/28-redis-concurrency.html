Redis는 무엇을 보장하는가 ①: 동시성

27편에서 Redis를 쓰기로 했다면 다음 질문은 이것입니다. 여러 서버가 같은 키를 동시에 바꿔도 안전한가? 답은 세 줄로 정리됩니다. 명령 하나는 원자적입니다. 명령 여러 개를 묶을 때는 방법마다 보장이 다릅니다. 우리 서버에서 오래 걸리는 작업 동안 다른 서버를 막는 일은 Redis 명령만으로는 안 되고 30편의 분산 락이 필요합니다. 이 편은 Redis가 무엇을 보장하고 무엇은 보장하지 않는지를 경계선까지 봅니다.

1. 명령은 한 줄로 서서 하나씩 실행된다2. 한 줄 실행의 대가: 느린 명령 하나가 모두를 기다리게 한다3. 원자 명령으로 되면 원자 명령으로 끝낸다4. 여러 명령은 필요한 보장만큼 묶는다5. Lua 스크립트는 한 명령처럼 실행된다6. 보장하는 것과 보장하지 않는 것7. 실무 예시8. 설명해보기

1명령은 한 줄로 서서 하나씩 실행된다

공식 문서는 Redis를 "명령 실행 관점에서 대부분 단일 스레드인 서버"라고 설명합니다. 여러 서버가 동시에 명령을 보내도, Redis는 명령을 한 스레드에서 하나씩 차례로 실행합니다. 한 명령이 실행되는 동안 다른 명령은 끼어들지 못합니다. 17편에서 본 이벤트 루프와 같은 구조입니다. 적은 스레드가 많은 연결을 돌아가며 처리하고, 락을 잡을 일이 없어서 빠릅니다.

그래서 명령 하나는 원자적입니다. INCR views는 "읽고, 1 더하고, 쓰기"를 Redis 안에서 한 번에 끝내므로, 여러 서버가 동시에 보내도 숫자가 빠지지 않습니다. 하지만 명령 여러 개를 이어 붙인 것은 원자적이지 않습니다. 우리 서버가 GET으로 읽고, 자바에서 1을 더하고, SET으로 쓰면 그 사이에 다른 서버의 명령이 끼어듭니다. 05편의 count++가 서버 여러 대 규모로 다시 나타난 것입니다.

Redis 6.0부터 네트워크 읽기·쓰기를 나눠 맡는 I/O 스레드를 켤 수 있지만(기본은 꺼짐), 명령 실행은 여전히 한 스레드가 차례로 합니다.

2한 줄 실행의 대가: 느린 명령 하나가 모두를 기다리게 한다

한 줄로 서서 하나씩 실행한다는 것은, 앞의 명령이 오래 걸리면 뒤의 명령이 전부 기다린다는 뜻이기도 합니다. 17편에서 이벤트 루프에 블로킹 호출을 섞으면 전체가 느려진다고 한 것과 같은 원리입니다. 명령 대부분은 키 하나를 다뤄 순식간에 끝나지만, 데이터 양에 비례해 오래 걸리는 명령이 문제입니다.

위험한 명령왜대신
KEYS pattern모든 키를 훑음. 키가 수백만 개면 그동안 Redis 전체가 멈춤SCAN — 조금씩 나눠 훑어서 사이사이 다른 명령이 실행됨
거대한 컬렉션 통째로 조회
(HGETALL, SMEMBERS, LRANGE 0 -1)		원소가 수십만 개면 조회도, 결과 전송도 오래 걸림필요한 만큼만 조회, 컬렉션을 작게 나누기
큰 키 삭제 DEL원소가 많은 키를 지우는 데도 시간이 듦UNLINK — 키는 바로 사라지고 메모리 정리는 뒤에서

이렇게 원소가 너무 많거나 값이 너무 큰 키를 큰 키(big key)라고 부릅니다. 큰 키는 명령을 느리게 만들 뿐 아니라, Cluster 구성에서는 한 노드에만 부하를 몰리게 합니다(6절). 느리게 실행된 명령은 Redis가 SLOWLOG에 기록하므로, 응답이 가끔 튄다면 먼저 여기를 봅니다.

Valkey 8.0부터는 기본 설정(lazyfree-lazy-user-del yes)에서 DEL도 메모리를 뒤에서 정리해 UNLINK와 같게 동작합니다. Redis 7에서는 이 설정의 기본값이 꺼져 있어 차이가 있습니다.

키를 찾아 훑을 때는 위 표처럼 KEYS 대신 SCAN을 씁니다. 컬렉션 안을 훑을 때도 같은 방식의 HSCAN(Hash), SSCAN(Set), ZSCAN(Sorted Set)이 있습니다. 다만 SCAN은 조금씩 나눠 훑는 대가로 약속이 느슨합니다.

  • 같은 원소가 두 번 이상 나올 수 있습니다. 훑는 동안 데이터가 바뀌기 때문입니다. 받은 키로 작업할 때는 두 번 처리돼도 괜찮게 만듭니다.
  • COUNT는 "한 번에 이만큼 가져오라"는 힌트일 뿐, 정확한 개수가 아닙니다.
  • MATCH 패턴은 가져온 뒤에 거릅니다. 그래서 맞는 키가 드물면 빈 결과가 여러 번 이어질 수 있습니다. 빈 결과가 끝을 뜻하지는 않고, 커서가 0으로 돌아와야 끝입니다.

3원자 명령으로 되면 원자 명령으로 끝낸다

여러 단계를 원자적으로 하고 싶을 때 가장 먼저 볼 것은 그 일을 한 번에 하는 명령이 이미 있는가입니다. Redis에는 "읽고 계산하고 쓰기"나 "확인하고 쓰기"를 한 명령으로 하는 명령이 많습니다. 두 명령을 이어 쓰면 1절 그림처럼 사이에 다른 명령이 끼어들 틈이 생깁니다.

하고 싶은 일한 명령두 명령으로 하면 생기는 틈스프링
숫자 증감INCR · DECR · INCRBYGET → 계산 → SET: 증가가 사라짐(1절 그림)opsForValue().increment
없을 때만 쓰기 + 만료SET k v NX EX 30SETNX 후 EXPIRE: 사이에 죽으면 만료 없는 키가 남음(30편)setIfAbsent(k, v, Duration)
있을 때만 쓰기SET k v XXEXISTS 후 SET: 사이에 지워질 수 있음setIfPresent(k, v)
바꾸면서 옛 값 받기SET k v GETGET 후 SET: 사이에 다른 값이 들어올 수 있음setGet(…)
객체의 숫자 필드 증감HINCRBYHGET → 계산 → HSETopsForHash().increment

공식 문서는 SET의 옵션이 SETNX·SETEX·GETSET을 대신할 수 있고, 이 명령들은 앞으로 폐기될 수 있다고 안내합니다. 새 코드는 SET 한 명령으로 씁니다.

핵심 — 원자 명령은 가장 단순하고 빠른 보장입니다. "재고가 0보다 클 때만 줄이기"처럼 명령 옵션으로 표현되지 않는 조건이 있을 때만 다음 절의 방법으로 넘어갑니다. 22편에서 "계산을 DB에 맡기는 원자적 UPDATE"를 먼저 본 것과 같은 순서입니다.

4여러 명령은 필요한 보장만큼 묶는다

여러 명령을 한 번에 보내는 방법은 다섯 가지입니다. 뒤로 갈수록 보장이 강해지지만, 그만큼 제약과 위험도 늘어납니다. 필요한 보장이 무엇인지에 따라 고릅니다.

MGET / MSET1번불가 (한 명령)—키가 너무 많으면 길어짐 · 같은 슬롯만같은 명령을 여러 키에
파이프라인1번가능불가 (응답은 끝에)응답이 서버 메모리에 쌓임 → 적당한 크기로 나눠 보냄서로 다른 명령을 빠르게만 보내면 될 때
MULTI / EXEC1번(파이프라인 시)불가불가롤백 없음 · 같은 슬롯만여러 쓰기를 한 덩어리로
WATCH + MULTI여러 번감지해서 통째로 취소가능 (읽고 판단 후 MULTI)충돌이 잦으면 재시도 반복 · 같은 슬롯만"읽고 판단해서 쓰기"를 낙관적으로

WATCH는 22편의 낙관적 락과 같은 생각입니다. 지켜보겠다고 걸어 둔 키가 EXEC 전에 바뀌면 트랜잭션 전체가 실행되지 않고 빈 응답이 돌아옵니다. 그러면 처음부터 다시 읽고 시도합니다. 충돌이 드물면 가볍고, 잦으면 재시도가 반복되어 Lua가 낫습니다.

5Lua 스크립트는 한 명령처럼 실행된다

4절 표의 마지막 줄, Lua 스크립트는 "읽고 판단해서 쓰기"를 끼어들기 없이 한 번에 하는 방법입니다. 스크립트 전체가 명령 하나처럼 실행되므로, 스크립트가 도는 동안 다른 명령은 모두 기다립니다. 2절의 느린 명령과 같은 위험을 스크립트 길이만큼 지게 됩니다.

Lua 스크립트 안에서 쓰는 함수

스크립트 안에서는 Redis가 넣어 둔 redis 객체의 함수로 명령을 부르고 응답을 만듭니다. 입력은 두 전역 표로 받습니다. KEYS에는 스크립트가 다룰 키가, ARGV에는 그 밖의 값이 들어 있고, Lua 표라서 1번부터 셉니다(KEYS[1]).

함수하는 일언제 쓰나
redis.call(명령, 인자…)명령을 실행하고 결과를 돌려줌. 명령이 오류를 내면 스크립트가 거기서 멈추고 오류가 그대로 클라이언트로 감기본. 대부분 이것
redis.pcall(명령, 인자…)명령을 실행하되, 오류가 나도 멈추지 않고 오류를 {err=…} 표로 돌려줌오류를 스크립트 안에서 확인해 기록하거나 다른 응답으로 바꿀 때
redis.error_reply(메시지)오류 응답을 만듦 ({err=메시지}와 같음)조건이 안 맞을 때 호출한 쪽에 오류로 알리기 (스프링에서는 예외)
redis.status_reply(메시지)상태 응답을 만듦 (OK 같은 응답)값 없이 "성공"만 알릴 때
redis.log(레벨, 메시지)서버 로그에 기록. 레벨은 redis.LOG_WARNING 등이고, 서버의 loglevel 이상만 남음드물게 일어나는 이상 상황 기록
redis.register_function(이름, 함수)Functions 라이브러리에 함수를 등록 (Redis 7.0+)FUNCTION LOAD로 올리는 코드 안에서만
redis.call — 오류면 여기서 멈춤
local n = redis.call('INCR', KEYS[1])
-- 값이 숫자가 아니면 오류로 스크립트 중단,
-- 오류가 그대로 클라이언트로
return n
redis.pcall — 오류를 값으로 받아 판단
local r = redis.pcall('INCR', KEYS[1])
if type(r) == 'table' and r.err then
    redis.log(redis.LOG_WARNING, r.err)
    return redis.error_reply('ERR bad counter')
end
return r

스크립트가 돌려준 값은 Redis 응답으로 바뀌는데, 이때 자바 개발자가 놓치기 쉬운 규칙이 있습니다.

스크립트 안바뀌는 모습대처
없는 키를 GET한 결과Lua에서 nil이 아니라 falseredis.call('GET', k) or '0'처럼 기본값을 줌 (실무 예시의 재고 스크립트)
소수 return 3.7정수 3으로 (소수점 아래 버림)소수는 tostring(x)으로 문자열로 돌려줌
표 return {1, nil, 3}첫 nil에서 끊겨 [1]만표 안에 nil을 넣지 않음
return false / truenull / 정수 1스프링 결과 타입(Long, Boolean)에 맞춰 설계

스크립트는 Lua 5.1 샌드박스에서 돕니다. 전역 변수를 만들 수 없어 변수와 함수는 local로 선언하고, require로 모듈을 불러올 수 없습니다. 대신 string·table·math 같은 기본 라이브러리와 cjson(JSON), cmsgpack, struct, bit가 들어 있습니다. Valkey는 같은 함수를 server.call처럼 server 객체로도 제공하고 새 코드에는 이쪽을 권하며, redis 이름도 계속 지원합니다.

스크립트를 보내고 멈추는 명령

스크립트를 실행하는 서버 명령도 EVAL 하나가 아닙니다. 본문을 매번 보낼지, 서버에 올려 두고 해시(SHA1)나 이름으로 부를지, 읽기만 하는지에 따라 나뉩니다. 어느 것이든 스크립트 전체가 한 명령처럼 실행되는 점은 같습니다.

명령하는 일고르는 기준
EVAL 스크립트 키개수 키… 인자…스크립트 본문을 보내 실행기본. 파이프라인 안에서도 이것
SCRIPT LOAD → EVALSHA sha1 …스크립트를 서버 캐시에 올려 두고, 본문 대신 SHA1 해시로 실행같은 스크립트를 자주 실행할 때 (본문을 매번 보내지 않음)
EVAL_RO / EVALSHA_RO읽기 전용 실행. 쓰기 명령은 거부됨 (Redis 7.0+)조회만 하는 스크립트를 레플리카에서도 돌릴 때
SCRIPT KILL실행 중인 스크립트를 멈춤. 아직 쓰기를 하지 않았을 때만느린 스크립트 장애 대응
FUNCTION LOAD → FCALL / FCALL_ROLua 코드를 이름 붙인 함수로 서버에 등록해 부름 (Redis 7.0+, Valkey도 있음)여러 서비스가 함께 쓰는 공통 로직
  • 스크립트 캐시는 언제든 비워질 수 있습니다. 서버 재시작, 장애 조치로 레플리카가 primary가 될 때, SCRIPT FLUSH로 사라집니다. 그러면 EVALSHA는 NOSCRIPT 오류를 냅니다. 스프링의 RedisScript는 EVALSHA를 먼저 보내고 NOSCRIPT면 EVAL로 다시 보내므로 직접 처리할 일은 없습니다. 반면 Functions는 AOF에 저장되고 레플리카로 복제됩니다. 다만 Cluster에서는 노드마다 따로 등록해야 합니다.
  • 스크립트가 접근하는 키는 모두 KEYS로 넘깁니다. 스크립트 안에서 키 이름을 만들어 쓰면 안 됩니다. Redis는 넘겨받은 키 이름을 보고 Cluster에서 어느 노드가 실행할지 정하기 때문입니다. Cluster에서는 넘기는 키가 모두 같은 슬롯이어야 하므로 해시 태그로 묶습니다(6절). 키가 아닌 값은 ARGV로 넘깁니다.
  • 느린 스크립트는 멈추기도 어렵습니다. Redis는 스크립트를 시간 제한으로 끊지 않습니다. 기본 5초(busy-reply-threshold, Redis 7.0 전 이름은 lua-time-limit)를 넘기면 다른 클라이언트의 명령에 BUSY 오류를 돌려주기 시작하고, 받아 주는 명령은 SCRIPT KILL·FUNCTION KILL·SHUTDOWN NOSAVE 정도뿐입니다. 스크립트가 한 번이라도 쓰기를 했다면 반쯤 쓴 상태를 남기지 않도록 SCRIPT KILL도 거부되어, 저장 없이 서버를 끄는 SHUTDOWN NOSAVE만 남습니다. 그래서 스크립트는 짧게, 반복 횟수가 데이터 크기에 따라 커지지 않게 씁니다.

6보장하는 것과 보장하지 않는 것

지금까지를 한 표로 모으면, Redis의 동시성 보장이 어디까지인지 경계가 보입니다.

상황Redis의 보장근거 · 보장 밖이면

Cluster에서는 같은 슬롯 안에서만 묶을 수 있다

데이터가 한 대의 메모리에 다 들어가지 않으면 Redis Cluster로 데이터를 여러 샤드(Primary와 그 레플리카 묶음)에 나눕니다(구성은 29편). 키는 이름을 해시해 0~16383 중 하나의 슬롯에 들어가고, 샤드마다 맡는 슬롯이 다릅니다. 그래서 여러 키를 다루는 명령은 키가 모두 같은 슬롯에 있어야 합니다.

핵심 — Redis의 동시성 보장은 "Redis 안에서 한 번에 실행되는 단위"까지입니다. 명령 하나, MULTI 한 덩어리, 스크립트 하나가 그 단위입니다. 그 단위를 넘어가는 것(여러 명령 사이, 우리 서버의 작업 시간, 장애 조치)은 다른 방법으로 채웁니다.

7실무 예시

실수 예시

조회수가 트래픽이 몰릴 때만 덜 올라간다

상품 조회수를 Redis에 저장하면서, 값을 읽어 자바에서 1을 더한 뒤 다시 썼습니다. 트래픽이 적을 때는 정확하지만, 인기 상품에 요청이 몰리면 1절 그림처럼 증가가 사라집니다.

✕ 읽고 → 계산 → 쓰기
String v = redis.opsForValue().get(key);
long next = (v == null ? 0 : Long.parseLong(v)) + 1;
redis.opsForValue().set(key, String.valueOf(next));
// GET과 SET 사이에 다른 서버가 끼어듦
✓ 계산을 Redis에 맡김
redis.opsForValue().increment(key);
// INCR 한 명령, 끼어들 틈 없음

스프링의 StringRedisTemplate 기준입니다. increment는 Redis의 INCR을 보냅니다.

실수 예시

관리 기능 하나가 Redis 전체를 멈췄다

관리자 화면에 "현재 로그인한 사용자 수"를 보여 주려고 redisTemplate.keys("session:*")를 썼습니다. 이 메서드는 내부적으로 KEYS 명령을 보냅니다. 세션 키가 수백만 개로 늘자, 관리자가 화면을 열 때마다 Redis가 몇 초씩 멈추고 로그인·장바구니 API까지 타임아웃이 났습니다.

해결: 개수가 필요하면 세션을 만들고 지울 때 카운터(INCR/DECR)나 Set으로 따로 관리합니다. 키 목록이 꼭 필요하면 SCAN으로 조금씩 훑습니다(스프링에서는 redisTemplate.scan(ScanOptions), 다 쓴 커서는 닫기). 운영 Redis에서는 KEYS 명령 자체를 막아 두는 경우가 많습니다.

실수 예시

MULTI 안에서 읽은 값이 null이다

"재고가 남아 있으면 차감"을 원자적으로 하려고 스프링의 SessionCallback으로 MULTI를 열고, 그 안에서 재고를 읽어 조건을 확인했습니다. 그런데 읽은 값이 늘 null이었습니다. MULTI 안의 명령은 실행되지 않고 쌓이기만 하다가 EXEC 때 한꺼번에 실행되므로, 중간 결과를 보고 분기할 수 없습니다. 스프링도 트랜잭션·파이프라인 안의 명령 결과를 null로 돌려줍니다.

해결: 분기가 필요 없으면 원자 명령 하나(DECR 후 결과가 음수면 되돌리기)로 끝냅니다. 읽고 판단해야 하면 WATCH로 지켜보다 MULTI를 쓰거나, Lua 스크립트 하나로 읽기·판단·쓰기를 묶습니다.

✓ Lua: 남아 있을 때만 차감, 아니면 -1
local stock = tonumber(redis.call('GET', KEYS[1]) or '0')
if stock > 0 then
    return redis.call('DECR', KEYS[1])
else
    return -1
end
스프링에서 실행 (위 스크립트를 파일로 두고)
private static final RedisScript<Long> DECR_IF_POSITIVE =
    RedisScript.of(new ClassPathResource("scripts/decr-if-positive.lua"), Long.class);
// 한 번만 만들어 재사용 (SHA1을 매번 계산하지 않음)

Long left = redis.execute(DECR_IF_POSITIVE, List.of("stock:" + itemId));

장애 대응

Redis 응답이 가끔 수백 ms씩 튄다

평소 1ms도 안 걸리던 Redis 호출이 가끔 수백 ms로 튀면서, 그 시간 동안 들어온 모든 요청이 함께 느려집니다(16편의 장애 전파). 원인은 대개 한 줄 대기열 앞에 선 느린 명령입니다.

  1. SLOWLOG GET으로 느렸던 명령과 시각 확인
  2. redis-cli --bigkeys로 큰 키 찾기 (SCAN으로 훑으므로 운영에서도 비교적 안전)
  3. 큰 키는 날짜·ID 범위로 쪼개고, 통째로 읽는 코드를 필요한 만큼만 읽도록 수정
지금은 넘어가도 되는 것 · 이벤트 루프 구현(epoll 등)과 I/O 스레드 설정, 스크립트 플래그(#!lua flags=no-writes 등), 그 밖의 스크립트 함수(redis.sha1hex, redis.setresp, redis.acl_check_cmd, redis.set_repl, 디버거용 redis.breakpoint), RESP3 응답 변환, Functions의 라이브러리 구성, 슬롯 이동 중의 MOVED·ASK 응답

8설명해보기

답을 열기 전에 먼저 소리 내어 설명해 보세요.

INCR은 원자적인데, GET으로 읽고 SET으로 쓰는 코드는 왜 안전하지 않나요?
명령 하나는 끼어들기 없이 실행되지만, 명령 두 개 사이에는 다른 서버의 명령이 끼어들 수 있습니다. 두 서버가 같은 값을 읽고 각자 계산해 쓰면 한쪽 증가가 사라집니다. 계산을 Redis에 맡기는 원자 명령(INCR)이나, 여러 단계가 필요하면 Lua 스크립트를 씁니다.
운영 Redis에서 KEYS 명령을 쓰면 안 되는 이유는?
KEYS는 모든 키를 한 번에 훑는 명령이라 키가 많으면 오래 걸리고, 명령이 한 줄로 실행되는 Redis에서는 그동안 다른 모든 명령이 기다립니다. 키 목록이 필요하면 조금씩 나눠 훑는 SCAN을 쓰고, 개수는 별도 카운터로 관리합니다.
파이프라인과 MULTI/EXEC는 무엇이 다른가요?
파이프라인은 여러 명령을 한 번에 보내 왕복을 줄이는 방법일 뿐이라, Redis 안에서는 명령 사이에 다른 서버의 명령이 끼어들 수 있습니다. MULTI/EXEC는 모아 둔 명령을 끼어들기 없이 연속으로 실행합니다. 대신 둘 다 중간 결과를 보고 분기할 수는 없고, MULTI/EXEC에는 롤백도 없습니다.
"읽고 판단해서 쓰기"를 할 때 WATCH와 Lua 중 무엇을 고르나요?
WATCH는 지켜본 키가 바뀌면 트랜잭션을 취소하고 다시 시도하는 낙관적 방식이라, 충돌이 드물 때 가볍습니다. Lua는 읽기·판단·쓰기를 끼어들기 없이 한 번에 실행하므로 충돌이 잦은 곳(선착순 등)에 맞습니다. 대신 Lua는 실행 중 모든 명령이 기다리므로 짧게 유지합니다.
Lua 스크립트에서 redis.call과 redis.pcall은 어떻게 다른가요?
둘 다 스크립트 안에서 Redis 명령을 실행합니다. redis.call은 명령이 오류를 내면 스크립트가 그 자리에서 멈추고 오류가 클라이언트로 전달됩니다. redis.pcall은 멈추지 않고 오류를 {err=…} 표로 돌려주므로, 스크립트가 오류를 확인해 로그를 남기거나 redis.error_reply로 다른 오류 응답을 만들 수 있습니다. 보통은 redis.call을 쓰고, 오류를 직접 다뤄야 할 때만 pcall을 씁니다.
EVALSHA가 NOSCRIPT 오류를 내는 건 언제이고, 어떻게 대응하나요?
EVALSHA는 서버의 스크립트 캐시에 올려 둔 스크립트를 해시로 부르는데, 이 캐시는 재시작, 장애 조치, SCRIPT FLUSH로 비워질 수 있습니다. 그러면 NOSCRIPT가 나고, 스크립트 본문을 다시 보내(EVAL 또는 SCRIPT LOAD) 실행합니다. 스프링의 RedisScript는 이 재시도를 자동으로 합니다. 서버에 남아 있어야 하는 공통 로직이면 저장·복제되는 Functions를 고려합니다.
Redis가 동시성에 대해 보장하지 않는 것은 무엇인가요?
파이프라인으로 보낸 명령 사이의 원자성, MULTI/EXEC의 롤백, 우리 서버에서 오래 걸리는 작업 동안 다른 서버를 막는 것, 장애 조치 뒤에도 성공한 쓰기가 남는 것은 보장하지 않습니다. 보장하는 단위는 명령 하나, MULTI 한 덩어리, Lua 스크립트 하나처럼 Redis 안에서 한 번에 실행되는 단위까지입니다. 그 밖은 분산 락(30편)이나 DB로 채웁니다. Cluster에서는 슬롯이 다른 키를 한 명령으로 묶을 수 없어 해시 태그를 씁니다.
