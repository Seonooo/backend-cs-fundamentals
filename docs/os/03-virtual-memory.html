가상 메모리와 페이지 캐시

JVM 힙도 결국 운영체제가 준 메모리 위에 있습니다. 여기서는 깊은 구현 대신 "디스크는 엄청나게 느리고, OS는 메모리로 그 느림을 숨긴다"는 감각 하나를 가져갑니다. 이 감각이 인덱스(18편)와 캐시(26편)를 이해하는 바탕이 됩니다.

1. 저장 장치마다 속도가 얼마나 다른가2. 가상 메모리: 프로세스마다 자기만의 주소 공간3. 페이지 캐시: OS가 남는 메모리로 디스크를 숨긴다4. 실무 예시5. 설명해보기

1저장 장치마다 속도가 얼마나 다른가

데이터가 어디에 있느냐에 따라 읽는 시간이 수천~수백만 배 차이 납니다. 숫자가 너무 작아서 감이 안 오니, 1ns(나노초)를 1초로 늘려서 비교해 봅니다.

핵심 — 백엔드 성능 튜닝의 상당수는 "디스크나 네트워크까지 가는 횟수를 줄이는 것"입니다. 인덱스, 캐시, 커넥션 재사용, 쿼리 횟수 줄이기(N+1)가 모두 이 표의 아래쪽을 피하려는 노력입니다.

2가상 메모리: 프로세스마다 자기만의 주소 공간

01에서 "프로세스끼리는 서로의 메모리를 볼 수 없다"고 했습니다. 이걸 가능하게 하는 것이 가상 메모리입니다. 프로세스는 자기가 메모리 전체를 혼자 쓰는 것처럼 보이는 가상 주소만 사용하고, 실제 RAM의 어디에 놓일지는 OS가 페이지(보통 4KB) 단위로 연결해 줍니다.

스왑: 편리하지만 서버에선 위험 신호

RAM이 부족하면 OS는 오래 안 쓴 페이지를 디스크(스왑 영역)로 옮겨 공간을 만듭니다. 프로그램이 죽지는 않지만, 그 페이지가 다시 필요해지면 위 그래프의 "RAM → 디스크" 차이만큼 느려집니다. 특히 JVM은 GC 때 힙을 넓게 훑기 때문에, 힙 일부가 스왑으로 밀려나 있으면 GC 멈춤이 수십 배 길어집니다. 그래서 서버에서는 스왑이 쓰이기 시작하면 메모리가 부족하다는 경고로 봅니다.

3페이지 캐시: OS가 남는 메모리로 디스크를 숨긴다

OS는 애플리케이션이 쓰지 않는 남는 RAM을 놀리지 않고, 최근에 읽고 쓴 파일 내용을 담아 둡니다. 이것이 페이지 캐시입니다. 같은 파일을 다시 읽으면 디스크 대신 메모리에서 바로 돌려주고, 애플리케이션이 메모리를 더 필요로 하면 OS가 캐시를 비워 돌려줍니다.

쓰기도 비슷합니다. 파일에 쓰면 OS는 일단 페이지 캐시에 쓰고 "완료"라고 답한 뒤, 나중에 모아서 디스크에 기록합니다. 그래서 DB처럼 "정말 디스크에 기록됐는지"가 중요한 프로그램은 fsync로 즉시 기록을 강제합니다. 트랜잭션 커밋이 생각보다 느린 이유 중 하나가 이것입니다 (20편).

4실무 예시

매일 보는 곳

free 메모리가 거의 없는데, 장애일까?

서버에 접속해 free -h를 쳤더니 free가 512MB밖에 없습니다. 놀랄 필요는 없습니다.

$ free -h
              total   used    free   shared  buff/cache  available
Mem:           15Gi   6.1Gi   512Mi   12Mi     8.9Gi      9.0Gi
Swap:            0B      0B      0B
  • buff/cache 8.9Gi — 대부분 페이지 캐시입니다. 애플리케이션이 필요하면 OS가 비워서 내줍니다.
  • available 9.0Gi — 실제로 새로 쓸 수 있는 양. 이 값을 보면 됩니다.
  • Swap used — 0이 아니고 계속 늘어나면 그때가 경고입니다.
장애 대응

재시작 직후에만 느린 서버 — 캐시가 비어 있다

DB나 검색 엔진을 재시작하면 한동안 쿼리가 느리다가 점점 빨라집니다. 재시작으로 DB 자체 캐시(버퍼 풀)가 비워져, 처음 요청들이 디스크까지 가기 때문입니다. 서버(머신) 자체를 재부팅했다면 OS 페이지 캐시도 함께 비워집니다. 참고로 MySQL은 종료할 때 버퍼 풀에 있던 페이지 목록을 저장했다가 시작할 때 다시 읽어 와 이를 완화합니다. 이를 콜드 캐시라고 하고, 자주 쓰는 데이터를 미리 읽어 두는 것을 워밍업이라고 합니다. JVM도 비슷해서, 배포 직후에는 JIT 컴파일 전이라 첫 요청들이 느립니다.

설계 이유

Kafka는 디스크에 쓰는데 왜 빠를까

Kafka는 메시지를 파일 끝에 순서대로 붙여 쓰고, 컨슈머도 대부분 방금 쓴 메시지를 읽습니다. 방금 쓴 데이터는 페이지 캐시에 있으니 디스크까지 가지 않고 메모리에서 읽힙니다. 그래서 Kafka 서버는 JVM 힙을 작게 잡고, 남은 RAM을 OS 페이지 캐시에 양보하는 것이 일반적인 권장 설정입니다.

실수 예시

메모리를 꽉 채워 스왑이 돌기 시작했다

한 서버에 여러 JVM을 띄우며 힙을 넉넉히 잡았더니, 평소엔 괜찮다가 트래픽이 몰릴 때 모든 API가 동시에 느려집니다. 모니터링을 보면 스왑 사용량이 올라가 있고 GC 멈춤 시간이 크게 늘어 있습니다. 해결은 스왑을 늘리는 게 아니라 힙 합계를 물리 메모리 안으로 줄이는 것입니다. 참고로 쿠버네티스 환경은 보통 스왑 없이 운영되므로, 같은 상황이 느려지는 대신 OOMKilled로 나타납니다 (02편).

5설명해보기

답을 열기 전에 먼저 소리 내어 설명해 보세요.

가상 메모리가 있어서 얻는 이점 두 가지는?
첫째, 격리: 프로세스는 가상 주소만 쓰고 실제 위치는 OS가 관리하므로 다른 프로세스의 메모리에 접근할 수 없습니다. 둘째, 유연성: 실제 RAM보다 큰 주소 공간을 쓸 수 있고, 부족하면 OS가 덜 쓰는 페이지를 디스크로 옮길 수 있습니다(대신 느려짐).
free 결과에서 free는 작고 buff/cache가 크다. 메모리 부족인가요?
대부분 아닙니다. buff/cache는 OS가 남는 메모리로 담아 둔 페이지 캐시라서, 애플리케이션이 필요하면 비워서 내줍니다. 판단은 available 값과 스왑 사용량 증가 여부로 합니다.
서버에서 스왑이 쓰이면 왜 JVM 애플리케이션이 특히 느려지나요?
스왑된 페이지에 접근할 때마다 디스크에서 다시 읽어야 하는데, 이는 RAM보다 수천 배 이상 느립니다. JVM은 GC 시 힙을 넓게 훑기 때문에, 힙 일부가 스왑에 있으면 GC 멈춤이 크게 길어지고 그동안 모든 요청이 멈춥니다.
DB를 재시작하면 한동안 느린 이유는?
재시작으로 DB 버퍼 풀에 담겨 있던 데이터가 사라져(머신 재부팅이면 OS 페이지 캐시도), 처음 쿼리들은 디스크에서 읽어야 하기 때문입니다(콜드 캐시). 자주 쓰는 데이터가 다시 메모리에 올라오면 원래 속도로 돌아옵니다.
