분산 락

05편에서 서버가 여러 대면 synchronized 같은 JVM 락은 소용없다고 했습니다. 모든 서버가 함께 보는 곳에 락이 있어야 합니다. 22편에서는 DB 락을 봤고, 이 편은 Redis로 만드는 분산 락을 봅니다. 만드는 법은 짧지만, "이 락을 어디까지 믿을 수 있나"를 아는 것이 핵심입니다. 그 답은 28·29편에서 본 원자성, 만료, 비동기 복제에서 나옵니다.

1. 서버가 여러 대면 락도 모두가 보는 곳에 있어야 한다2. 잡기는 한 명령으로, 풀기는 내 것인지 확인하고3. 작업이 만료보다 길면 두 명이 동시에 잡는다4. 락이 풀린 뒤 도착한 쓰기는 락이 막지 못한다5. 장애 조치 때 락이 사라질 수 있다6. 실무 예시7. 설명해보기

1서버가 여러 대면 락도 모두가 보는 곳에 있어야 한다

분산 락은 여러 서버가 공유하는 저장소(여기서는 Redis)에 "지금 누가 이 일을 하는 중"이라는 표시를 두고, 표시가 있으면 다른 서버는 기다리거나 포기하게 하는 방식입니다. 모든 서버가 같은 Redis를 보므로, 서버가 몇 대든 한 번에 한 서버만 들어갑니다.

막고 싶은 것먼저 볼 방법
DB의 한 행(재고, 잔액)을 동시에 고치는 것DB에서 해결: 원자적 UPDATE, 비관적·낙관적 락 (22편). 데이터와 락이 같은 곳에 있어 가장 정확함
숫자 하나를 동시에 줄이는 것 (선착순 수량)원자 명령: DB 조건부 UPDATE(22편) 또는 Redis DECR(28편). 락이 필요 없음
DB가 아닌 것: 외부 API 호출, 파일 생성, 같은 배치가 두 서버에서 동시에 도는 것분산 락
DB 락 대기가 몰려 DB가 버거운 것분산 락으로 앞단에서 줄 세우기 + DB 제약을 최종 방어선으로

표의 순서가 곧 우선순위입니다. 락 없이 원자 연산으로 되면 그게 가장 단순하고, DB 행이 대상이면 DB에서 막는 것이 가장 정확합니다. 분산 락은 그 둘로 안 될 때 꺼내는 도구입니다.

2잡기는 한 명령으로, 풀기는 내 것인지 확인하고

락을 잡는 명령은 한 줄입니다.

락 잡기
SET lock:order:42 3f9a-서버A-요청고유값 NX PX 5000
// NX: 키가 없을 때만 저장 → 이미 누가 잡았으면 실패
// PX 5000: 5초 뒤 자동 삭제 → 잡은 서버가 죽어도 락이 영원히 남지 않음
// 값: 이 락을 누가 잡았는지 알 수 있는 고유한 값(토큰)

"없을 때만 저장"과 "만료 설정"을 한 명령으로 하는 것이 중요합니다. 28편에서 본 것처럼 명령 하나는 원자적이기 때문입니다. 두 명령으로 나누면 그 사이에 서버가 죽었을 때 만료 없는 락이 영원히 남습니다(실무 예시).

풀 때는 그냥 DEL하면 안 됩니다. 내가 잡은 락인지 확인하고 지워야 합니다. 아래 그림처럼, 내 락이 이미 만료되어 다른 서버가 새로 잡은 뒤라면 내가 남의 락을 지우게 됩니다.

✓ 내 토큰일 때만 삭제 (Lua 스크립트, 한 명령처럼 실행됨)
if redis.call("GET", KEYS[1]) == ARGV[1] then
    return redis.call("DEL", KEYS[1])
else
    return 0   -- 이미 남의 락: 건드리지 않음
end

Redis 8.4 이상에는 값이 같을 때만 지우는 명령(DELEX key IFEQ 토큰)이 생겨 Lua 없이 한 명령으로 풀 수 있습니다. 이 시리즈의 기준(Redis 7·Valkey 공통)에서는 위 Lua 방식을 씁니다. "확인하고 지우기"를 GET과 DEL 두 명령으로 나누면, 그 사이에 락이 만료되고 남이 잡을 수 있습니다. 28편의 GET→SET 경쟁과 같은 모양이라 Lua로 묶습니다.

3작업이 만료보다 길면 두 명이 동시에 잡는다

만료 시간은 양쪽으로 곤란합니다.

만료를생기는 문제
짧게 잡으면작업이 끝나기 전에 락이 풀려 다른 서버가 들어옴 (2절 그림)
길게 잡으면락을 잡은 서버가 죽었을 때, 만료될 때까지 아무도 그 일을 못 함

그래서 흔히 쓰는 방법이 작업하는 동안 만료를 계속 늘려 주는 것입니다. 자바의 Redis 클라이언트 Redisson은 이것을 watchdog이라는 이름으로 제공합니다. 락을 잡은 서버가 살아 있는 동안 주기적으로 만료를 연장하고, 서버가 죽으면 연장이 멈춰 락이 곧 만료됩니다. Redisson 기본 설정에서는 잡을 때 만료 시간(leaseTime)을 직접 주지 않았을 때만 watchdog이 동작합니다.

핵심 — watchdog이 있어도 "서버는 살아 있는데 멈춘" 경우는 남습니다. 다음 절이 그 이야기입니다.

4락이 풀린 뒤 도착한 쓰기는 락이 막지 못한다

서버 A가 락을 잡고 DB에 쓰려는 순간, JVM이 긴 GC 멈춤에 들어갔다고 합시다(02편). 멈춘 동안에는 watchdog도 멈추므로 락은 만료되고, 서버 B가 락을 잡아 먼저 DB에 씁니다. 그 뒤에 깨어난 A는 자기가 아직 락을 가졌다고 믿고 씁니다. 락은 "들어가는 문"만 지킬 뿐, 문을 통과한 뒤 늦게 도착한 쓰기는 막지 못합니다.

이 번호를 펜싱 토큰(fencing token)이라고 합니다. 백엔드에서 따로 만들 필요는 거의 없습니다. 22편의 낙관적 락(버전 컬럼)이 같은 역할을 합니다. UPDATE … SET …, version = version + 1 WHERE id = ? AND version = ?는 "내가 읽은 뒤 누가 바꿨다면 거부"이므로, 락이 풀린 뒤 늦게 도착한 A의 쓰기는 0행으로 실패합니다. 유니크 제약도 마찬가지로 마지막 방어선이 됩니다.

5장애 조치 때 락이 사라질 수 있다

29편에서 Redis 복제는 비동기라서, 장애 조치 때 이미 성공한 쓰기가 사라질 수 있다고 했습니다. 락도 쓰기입니다. A가 Primary에서 락을 잡았는데 그 쓰기가 레플리카에 복제되기 전에 Primary가 죽으면, 새 Primary에는 락이 없습니다. B가 곧바로 같은 락을 잡을 수 있습니다.

이를 줄이려고 서로 독립된 Redis 여러 대(예: 5대) 중 과반에서 락을 잡는 Redlock이라는 방법이 제안됐습니다. 다만 Redlock도 시계와 멈춤에 대한 가정에 기대고 있어서, 정확성을 보장하는지에 대해서는 전문가들 사이에 논쟁이 있습니다. 실무에서 기억할 결론은 이렇습니다.

락의 목적예충분한 것
효율 — 가끔 두 번 실행돼도 결과는 맞지만 낭비를 줄이고 싶음같은 배치·리포트 생성이 두 서버에서 도는 것 막기, 같은 캐시를 동시에 채우는 것 막기Redis 락 하나(+ Redisson)
정확성 — 두 번 실행되면 결과가 틀어짐결제, 잔액, 재고Redis 락은 앞단의 줄 세우기로 쓰고, DB의 원자 연산·버전·유니크 제약을 최종 방어선으로

6실무 예시

실수 예시

배포 중에 락이 영원히 풀리지 않았다

락을 SETNX로 잡고, 다음 줄에서 EXPIRE로 만료를 걸었습니다. 배포로 서버가 종료되는 순간 하필 두 명령 사이였고, 만료 없는 락이 남아 그 작업이 아무 서버에서도 실행되지 않았습니다.

✕ 두 명령
SETNX lock:job 1
// ← 여기서 죽으면 만료 없는 락
EXPIRE lock:job 30
✓ 한 명령
SET lock:job <토큰> NX PX 30000
실수 예시

락을 걸었는데도 쿠폰이 두 번 발급됐다

@Transactional 메서드 안에서 분산 락을 잡고, finally에서 풀었습니다. 그런데 커밋은 메서드가 끝난 뒤 프록시가 합니다(20편). 락이 풀린 순간과 커밋 사이에 다른 서버가 락을 잡고, 아직 커밋 전의 옛 데이터를 읽어 한 번 더 발급했습니다. 05편의 synchronized + @Transactional 함정과 똑같은 모양입니다.

✕ 트랜잭션 안에서 락
@Transactional
public void issue(Long couponId, Long memberId) {
    RLock lock = redisson.getLock("lock:coupon:" + couponId);
    lock.lock();
    try { … 발급 … }
    finally { lock.unlock(); }  // 커밋보다 먼저 풀림
}
✓ 락 안에서 트랜잭션
public void issue(Long couponId, Long memberId) {
    RLock lock = redisson.getLock("lock:coupon:" + couponId);
    lock.lock();
    try { couponTxService.issue(couponId, memberId); }  // 별도 빈의 @Transactional
    finally { lock.unlock(); }  // 커밋이 끝난 뒤 풂
}
좋은 패턴

Redisson으로 기다림에 상한을 둔 락

락을 기다리는 동안에도 요청 스레드는 묶입니다(16편). 무한정 기다리지 않도록 대기 시간에 상한을 두고, 못 잡으면 바로 실패를 알립니다.

✓ 대기 상한 + 내 락일 때만 해제
RLock lock = redisson.getLock("lock:report:" + date);
if (!lock.tryLock(1, TimeUnit.SECONDS)) {        // 최대 1초 기다림, leaseTime 생략 → watchdog 연장
    throw new AlreadyRunningException();
}
try {
    reportService.generate(date);
} finally {
    if (lock.isHeldByCurrentThread()) lock.unlock(); // 내 락일 때만
}

Redisson은 2절의 "토큰 확인 후 삭제"를 내부에서 처리하고, 같은 스레드가 다시 잡는 것(재진입)도 허용합니다. 직접 구현하기보다 검증된 라이브러리를 씁니다.

설계 이유

선착순 쿠폰 100장, 분산 락이 꼭 필요한가

요구선택
수량만 정확히 줄이면 됨락 없이 원자 연산: DB 조건부 UPDATE(22편) 또는 Redis DECR(28편)
1인 1장, 등급 확인 등 여러 단계 검증분산 락으로 사용자·쿠폰 단위 줄 세우기 + DB 유니크 제약(회원, 쿠폰)으로 최종 방어
순간 요청이 DB가 감당 못 할 만큼 몰림Redis DECR로 앞단에서 수량을 먼저 걸러 DB로 가는 요청 자체를 줄임

락은 "동시에 들어오지 못하게" 할 뿐, 결과가 맞다는 보장은 DB 제약이 줍니다. 5절의 표와 같은 결론입니다.

지금은 넘어가도 되는 것 · Redlock 알고리즘의 단계와 논쟁의 세부, Redisson 내부 구조(재진입 카운터, 대기자를 깨우는 방식), ZooKeeper·etcd로 만드는 락, 합의 알고리즘(Raft 등)

7설명해보기

답을 열기 전에 먼저 소리 내어 설명해 보세요.

Redis 분산 락을 잡을 때 SET NX PX를 한 명령으로 써야 하는 이유는?
"없을 때만 저장"과 "만료 설정"을 두 명령으로 나누면, 그 사이에 서버가 죽었을 때 만료 없는 락이 영원히 남습니다. 명령 하나는 원자적이므로 SET NX PX 한 번으로 둘을 함께 해야 합니다.
락을 풀 때 그냥 DEL하면 어떤 문제가 생기나요?
내 락이 이미 만료되고 다른 서버가 새로 잡은 뒤라면, DEL이 남의 락을 지웁니다. 그러면 세 번째 서버가 또 잡아 두 서버가 동시에 작업합니다. 잡을 때 고유한 토큰을 값으로 넣고, 풀 때는 값이 내 토큰일 때만 지우는 것을 Lua 스크립트로 한 번에 합니다.
분산 락을 잡았는데도 늦게 도착한 쓰기가 데이터를 덮어쓸 수 있는 이유와 대책은?
락을 잡은 서버가 GC 등으로 멈춘 사이 락이 만료되면, 다른 서버가 락을 잡고 먼저 씁니다. 깨어난 서버는 락이 있다고 믿고 늦게 씁니다. 락은 들어가는 문만 지키기 때문입니다. 쓰는 쪽에서 번호를 확인해 거부해야 하고, 백엔드에서는 낙관적 락의 버전 조건이나 유니크 제약이 그 역할을 합니다.
@Transactional 메서드 안에서 분산 락을 잡으면 왜 위험한가요?
커밋은 메서드가 끝난 뒤 프록시가 하므로, finally에서 락을 푸는 시점이 커밋보다 앞섭니다. 그 틈에 다른 서버가 락을 잡고 커밋 전의 옛 데이터를 읽습니다. 락을 트랜잭션 바깥에서 잡고, 그 안에서 트랜잭션 메서드(별도 빈)를 호출해 커밋이 끝난 뒤 풀리게 합니다.
