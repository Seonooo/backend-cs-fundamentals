쿠키·세션·토큰

HTTP는 무상태라서(12편) 서버는 방금 로그인한 사람을 다음 요청에서 기억하지 못합니다. 그래서 매 요청마다 "나 아까 로그인한 그 사람이야"를 증명할 방법이 필요합니다. 세션과 토큰은 그 증명을 어디에 보관하느냐의 차이이고, 서버가 여러 대가 되면 그 차이가 드러납니다.

1쿠키: 브라우저가 자동으로 들고 다니는 값

서버가 응답에 Set-Cookie를 보내면, 브라우저는 그 값을 저장했다가 같은 사이트로 가는 모든 요청에 자동으로 붙여 보냅니다. 세션 ID든 토큰이든 이 통로로 많이 전달됩니다.

서버 응답
Set-Cookie: SESSION=a81f…; HttpOnly; Secure; SameSite=Lax; Path=/; Max-Age=1800
속성하는 일막아 주는 것
HttpOnly자바스크립트에서 이 쿠키를 읽지 못하게 함XSS로 심어진 스크립트가 세션을 훔쳐 가는 것
SecureHTTPS 요청에만 붙여 보냄평문 HTTP에서 노출 (13편)
SameSite다른 사이트에서 시작된 요청에는 안 보내거나 제한CSRF (남의 사이트가 내 로그인으로 요청 보내기)
Max-Age유효 시간없으면 브라우저를 닫을 때 삭제

2세션 vs 토큰: 로그인 정보를 어디에 두나

세션토큰 (JWT)
로그인 정보 위치서버 (세션 저장소)토큰 자체 (클라이언트가 보관)
서버 여러 대세션 저장소를 공유해야 함서명 키만 공유하면 끝
강제 로그아웃·권한 변경세션 삭제로 즉시 반영만료 전까지 어려움 (추가 장치 필요)
요청마다 비용저장소 조회서명 검증 (조회 없음)
잘 맞는 곳일반 웹 서비스, 즉시 제어가 중요한 곳여러 서비스 간 인증, 모바일 앱 API

3서버를 늘리면 세션이 사라진다

스프링의 기본 세션은 그 서버의 JVM 메모리에 저장됩니다. 05편에서 synchronized 락이 다른 서버에 안 통했던 것과 똑같은 이유로, 세션도 다른 서버는 모릅니다.

해결 방법설명한계
스티키 세션LB가 같은 사용자를 항상 같은 서버로 보냄그 서버가 죽거나 배포되면 세션 소실, 부하 쏠림 → 임시방편
공유 세션 저장소Spring Session + Redis로 세션을 한곳에Redis가 필수 인프라가 됨 (장애 대비 필요, 28·29편)
토큰 방식서버가 세션을 저장하지 않음즉시 로그아웃 등 제어가 어려움

4실무 예시

좋은 패턴

Spring Session + Redis로 세션 공유

✓ 의존성 추가 + 설정만으로 세션 저장소 교체
// build.gradle
implementation 'org.springframework.boot:spring-boot-starter-data-redis'   // Redis 드라이버
implementation 'org.springframework.session:spring-session-data-redis'

# application.yml
spring:
  data:
    redis:
      host: redis.internal
# 세션 저장소가 Redis로 바뀜. 컨트롤러 코드(HttpSession 사용)는 그대로

세션에 큰 객체를 넣으면 요청마다 Redis와 주고받는 양이 커집니다. 세션에는 사용자 ID 등 최소한만 넣습니다.

실수 예시

JWT에 개인정보를 넣었다

JWT의 가운데 부분(payload)은 암호화가 아니라 Base64 인코딩일 뿐입니다. 누구나 jwt.io 같은 곳에 붙여 넣으면 내용을 읽을 수 있습니다. 서명은 "바뀌지 않았음"만 보장합니다.

✕ 누구나 읽을 수 있는 곳에 민감 정보
{ "sub": "7", "email": "kim@…", "phone": "010-…", "role": "USER" }

해결: 토큰에는 사용자 식별자와 권한처럼 노출돼도 괜찮은 최소 정보만 넣고, 나머지는 서버에서 조회합니다.

실수 예시

로그아웃했는데 토큰이 계속 통한다

JWT는 서버가 저장하지 않으니 "이 토큰 무효"라고 지울 곳이 없습니다. 만료 시간이 7일이면 탈취된 토큰도 7일간 유효합니다. 권한을 바꿔도 토큰 안의 옛 권한이 계속 쓰입니다.

  • 액세스 토큰은 짧게(예: 15~30분) + 리프레시 토큰으로 재발급
  • 리프레시 토큰은 서버(DB·Redis)에 저장해, 로그아웃·강제 만료 시 삭제
  • 즉시 차단이 꼭 필요하면 차단 목록을 두되, 그만큼 "조회 없음"이라는 장점은 줄어듦

결국 토큰도 실무에서는 일부 상태를 서버에 두게 됩니다. 세션과 토큰은 정답이 아니라 트레이드오프입니다.

5설명해보기

답을 열기 전에 먼저 소리 내어 설명해 보세요.

세션 방식과 토큰 방식의 차이를 "정보가 어디 있는가"로 설명해 보세요.
세션은 로그인 정보를 서버의 세션 저장소에 두고 클라이언트에는 세션 ID만 줍니다. 토큰은 로그인 정보를 서명과 함께 토큰 안에 넣어 클라이언트가 들고 다니고, 서버는 서명만 검증합니다. 그래서 세션은 즉시 제어가 쉽고, 토큰은 서버 확장이 쉽습니다.
서버를 1대에서 3대로 늘렸더니 로그인이 랜덤하게 풀린다. 원인과 해결책은?
세션이 각 서버의 JVM 메모리에 있어서, 로드밸런서가 다른 서버로 보낸 요청은 세션을 찾지 못합니다. Spring Session + Redis 같은 공유 세션 저장소로 옮기거나 토큰 방식으로 바꿉니다. 스티키 세션은 임시방편입니다.
JWT에 개인정보를 넣으면 안 되는 이유는?
JWT payload는 Base64 인코딩일 뿐 암호화가 아니라서 누구나 디코딩해 읽을 수 있습니다. 서명은 위조 여부만 확인해 줍니다.
쿠키의 HttpOnly, Secure, SameSite는 각각 무엇을 막나요?
HttpOnly는 자바스크립트가 쿠키를 읽지 못하게 해 XSS로 인한 탈취를 막고, Secure는 HTTPS에서만 전송해 평문 노출을 막고, SameSite는 다른 사이트에서 시작된 요청에 쿠키를 보내지 않게 해 CSRF를 완화합니다.
