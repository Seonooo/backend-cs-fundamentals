HTTPS와 TLS

HTTPS는 HTTP와 TCP 사이에 TLS라는 층을 하나 끼운 것입니다(09편에서 "계층을 나누면 끼워 넣을 수 있다"고 한 그 예). 암호 수학은 몰라도 됩니다. 무엇을 보장하는지, 인증서가 무엇을 증명하는지, 실무에서 어떤 에러로 만나는지만 알면 됩니다.

1TLS가 보장하는 세 가지

보장없으면
암호화 — 중간에서 내용을 못 읽음같은 와이파이에 있는 사람이 비밀번호·토큰을 그대로 봄
무결성 — 중간에서 바꾸면 들킴중간 장비가 응답에 광고나 악성 스크립트를 끼워 넣음
서버 인증 — 진짜 그 서버가 맞음가짜 서버가 진짜인 척 요청을 가로챔

2TLS 핸드셰이크: 서로 확인하고, 같은 열쇠를 만든다

TCP 연결(11편)이 맺어진 직후, 데이터를 보내기 전에 TLS 핸드셰이크를 합니다. 핵심은 두 가지입니다. ① 인증서로 서버가 진짜인지 확인하고, ② 둘만 아는 대칭키를 안전하게 만들어 냄니다.

왜 두 종류의 암호를 섞을까 — 공개키 암호는 "처음 보는 상대와 안전하게 약속"할 수 있지만 느립니다. 대칭키 암호는 빠르지만 "같은 키를 어떻게 나눠 갖나"가 문제입니다. 그래서 공개키 방식으로 대칭키를 안전하게 만들고, 그 뒤로는 대칭키로 빠르게 통신합니다.

3인증서는 "이 공개키는 이 도메인의 것"이라는 보증서

서버가 "나 api.shop.com이야"라고 말하는 것만으로는 믿을 수 없습니다. 그래서 믿을 수 있는 기관(CA)이 서명한 인증서를 보여 줍니다. 클라이언트는 서명을 거슬러 올라가 자기가 원래 믿고 있는 루트 CA에 닿으면 통과시킵니다.

4보통은 로드밸런서에서 TLS를 푼다

실무에서는 인증서 관리를 한곳에서 하기 위해 로드밸런서가 HTTPS를 받아 풀고(TLS 종료), 내부 서버와는 HTTP로 통신하는 구성이 흔합니다.

5실무 예시

실수 예시

인증서가 만료되어 서비스 전체가 접속 불가

인증서에는 유효 기간이 있습니다. 공개 인증서의 최대 유효 기간은 2026년 3월부터 200일이고, 이후 100일, 47일로 계속 줄어들 예정이라 수동 갱신은 사실상 불가능해지고 있습니다. 갱신을 잊으면 만료 순간 모든 클라이언트가 연결을 거부합니다. 코드는 아무 문제가 없는데 서비스가 멈추는 대표적인 사고입니다.

해결: 자동 갱신(AWS ACM, Let's Encrypt + certbot 등)을 쓰고, 그와 별개로 만료 30일 전 알람을 둡니다. 외부 API의 인증서가 만료되는 경우도 있으니 연동 대상도 모니터링합니다.

실수 예시

PKIX path building failed — 검증을 끄면 안 된다

사내 API 호출 시 에러
javax.net.ssl.SSLHandshakeException:
  PKIX path building failed: unable to find valid certification path to requested target

3번 그림의 사슬을 루트까지 잇지 못했다는 뜻입니다. 흔한 원인은 두 가지입니다.

  • 사내 CA·자체 서명 인증서: JVM 신뢰 저장소에 그 루트가 없음 → 루트 인증서를 신뢰 저장소에 추가(keytool -importcert)하거나 애플리케이션 전용 truststore를 지정
  • 상대 서버 설정 누락: 서버가 중간 CA 인증서를 함께 보내지 않음 → 상대 서버 설정을 고쳐야 함 (브라우저는 알아서 채워 넣기도 해서 브라우저에선 잘 되는 경우가 있음)
✕ 인터넷에 떠도는 "해결책"
// 모든 인증서를 믿는 TrustManager, 호스트 이름 검증 끄기
→ 2번 표의 "서버 인증"을 스스로 없애는 것. 가짜 서버도 통과함
실수 예시

로그인 후 리다이렉트가 http://로 간다

4번 그림처럼 TLS가 로드밸런서에서 풀리면, 스프링은 요청이 http로 왔다고 생각합니다. 그래서 스프링이 만드는 리다이렉트 URL이나 절대 URL이 http://로 나가 경고가 뜨거나 쿠키(Secure)가 전달되지 않습니다.

해결: 09편과 같은 설정(server.forward-headers-strategy)으로 X-Forwarded-Proto를 반영합니다.

설계 이유

HTTPS 호출일수록 연결 재사용이 중요하다

HTTPS는 TCP 핸드셰이크에 더해 TLS 핸드셰이크 왕복과 공개키 연산이 붙습니다. 외부 HTTPS API를 호출마다 새 연결로 부르면 이 비용을 매번 냅니다. 10편 폭포 그림의 초록 구간이 두 칸이 되는 셈이라, 15편의 커넥션 풀 효과가 HTTP보다 더 큽니다.

지금은 넘어가도 되는 것 · RSA·ECDHE 등 알고리즘의 수학, 암호 스위트 목록, 핸드셰이크 메시지 이름과 순서 암기, TLS 1.2와 1.3의 세부 차이

6설명해보기

답을 열기 전에 먼저 소리 내어 설명해 보세요.

HTTPS에서 공개키 암호와 대칭키 암호는 각각 어디에 쓰이나요?
공개키 암호는 핸드셰이크에서 인증서로 서버 신원을 확인하고, 양쪽이 같은 대칭키를 안전하게 만드는 데 씁니다. 이후 실제 HTTP 데이터는 빠른 대칭키로 암호화합니다. 공개키 연산은 느리기 때문입니다.
인증서는 무엇을 증명하고, 클라이언트는 어떻게 믿나요?
"이 공개키는 이 도메인의 것"이라는 사실을 CA가 서명으로 보증합니다. 클라이언트는 서버 인증서의 서명을 중간 CA, 루트 CA로 거슬러 올라가 자기 신뢰 저장소에 있는 루트에 닿는지, 도메인이 일치하는지, 유효 기간 안인지 확인합니다.
PKIX path building failed 에러가 났을 때 해결 방법은?
인증서 사슬을 신뢰하는 루트까지 잇지 못한 것입니다. 사내 CA라면 그 루트 인증서를 JVM 신뢰 저장소나 전용 truststore에 추가하고, 상대 서버가 중간 인증서를 빠뜨렸다면 상대 서버 설정을 고칩니다. 검증을 끄는 것은 서버 인증을 포기하는 것이라 안 됩니다.
TLS 종료를 로드밸런서에서 하면 애플리케이션에서 주의할 점은?
애플리케이션에는 요청이 HTTP로 들어오므로, 리다이렉트나 절대 URL이 http로 만들어질 수 있습니다. X-Forwarded-Proto 헤더를 반영하도록 설정해 원래 프로토콜을 인식하게 해야 합니다.
