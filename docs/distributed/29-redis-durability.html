Redis는 무엇을 보장하는가 ②: 영속성과 장애

28편이 "동시에 바꿔도 안전한가"였다면, 이 편은 "성공한 쓰기가 남는가"입니다. Redis는 데이터를 메모리에 두므로 꺼지면 사라지고, 이를 보완하는 장치로 디스크 저장과 복제가 있습니다. 결론은 둘입니다. 디스크 저장과 복제는 잃는 범위를 줄여 줄 뿐 0으로 만들지 않습니다. 레플리카와 자동 장애 조치는 서비스를 멈추지 않게 하는 장치이지, 쓰기를 지키는 장치가 아닙니다. 그래서 Redis를 원본 저장소로 쓸지가 이 편의 마지막 질문입니다.

1. 메모리는 꺼지면 사라지고, 디스크 저장은 잃는 범위를 줄일 뿐이다2. 복제는 비동기라 레플리카는 늦을 수 있다3. 장애 조치는 서비스를 살리지만, 성공한 쓰기를 잃을 수 있다4. 원본인지 사본인지에 따라 설정이 달라진다5. 구성은 데이터 크기와 멈춤 허용치로 고른다6. 실무 예시7. 설명해보기

1메모리는 꺼지면 사라지고, 디스크 저장은 잃는 범위를 줄일 뿐이다

Redis의 데이터는 메모리에 있으므로, 프로세스가 죽거나 서버가 재부팅되면 그대로 사라집니다. 이를 막기 위해 디스크에 남기는 방법이 두 가지 있습니다. 이렇게 데이터를 디스크에 남겨 재시작 후에도 되살리는 것을 영속성(persistence)이라고 합니다.

방식무엇을 남기나죽으면 잃는 범위대가
RDB (스냅샷)정해진 주기마다 메모리 전체를 사진 찍듯 파일로 저장마지막 스냅샷 이후의 쓰기 전부 (주기가 5분이면 최대 5분)저장할 때 메모리가 순간적으로 더 필요함(아래)
AOF (명령 기록)쓰기 명령을 받을 때마다 파일 끝에 덧붙임기본 설정(appendfsync everysec)에서 최대 약 1초디스크 쓰기가 계속 생기고, 파일이 커져서 주기적으로 다시 정리함

RDB 스냅샷은 Redis가 자기 자신을 복제한 자식 프로세스(fork)를 만들어, 자식이 그 순간의 메모리를 파일로 쓰는 방식입니다. 부모는 그동안 계속 명령을 받습니다. 부모와 자식은 처음에 메모리를 공유하다가, 저장 중에 바뀐 부분만 따로 복사합니다. 그래서 저장하는 동안 쓰기가 많으면 추가 메모리가 필요하고, 쓰기가 아주 많으면 거의 두 배까지 늘 수 있습니다. 서버 메모리를 Redis에 전부 내주지 않고 여유를 남겨 두는 이유입니다.

핵심 — 영속성을 켜도 "잃을 수 있는 범위"가 줄어들 뿐, 0이 되지는 않습니다. RDB는 분 단위, AOF 기본 설정은 1초 단위입니다. 1초도 잃으면 안 되는 데이터라면 Redis 하나에 맡기지 않고 DB를 원본으로 둡니다.

공식 문서 기준으로 AOF의 디스크 반영 방식(appendfsync)은 세 가지입니다. always는 쓰기마다 반영해 매우 느리지만 가장 안전하고, everysec(권장·기본)은 재해가 나면 1초 분량을 잃을 수 있으며, no는 운영체제에 맡겨 리눅스에서는 보통 30초 간격입니다. 그리고 기본 설정은 AOF가 꺼져 있고(appendonly no), RDB 스냅샷만 정해진 조건(1시간에 1번 이상, 5분에 100번 이상, 1분에 1만 번 이상 바뀌면)마다 저장합니다. 설정을 바꾸지 않았다면 "최근 몇 분"을 잃을 수 있는 상태입니다.

2복제는 비동기라 레플리카는 늦을 수 있다

Redis 한 대만 두는 구성입니다. 설정이 가장 단순하고, 개발·테스트 환경이나 잃어도 되는 캐시에는 충분합니다. 한계는 두 가지입니다.

  • 죽으면 서비스가 멈춥니다. 영속성을 켜 두었다면 재시작 후 데이터는 돌아오지만(1절), 재시작하는 동안은 쓸 수 없습니다.
  • 한 대의 한계가 곧 전체의 한계입니다. 메모리는 서버 한 대 크기까지이고, 명령은 한 스레드에서 실행되므로(28편) 처리량도 한 대 몫입니다.

이 한계를 넘으려고 Redis를 여러 대로 늘립니다. 구성은 아래 그림처럼 한 단계씩 커집니다.

25편의 DB 복제와 같은 구조입니다. 쓰기는 Primary(원본) 한 대가 받고, Replica(복사본)가 Primary의 변경을 따라 복사합니다. 읽기 요청을 레플리카로 보내면 Primary의 부하가 줄어듭니다.

Redis의 복제는 기본적으로 비동기입니다. Primary는 쓰기에 바로 응답하고, 레플리카에는 조금 뒤에 반영됩니다. 그래서 25편과 똑같은 문제가 생깁니다. 방금 쓴 값을 레플리카에서 읽으면 옛 값이 보일 수 있습니다. 쓰기 직후 그 결과를 읽어야 하는 흐름은 Primary에서 읽습니다.

레플리카만으로는 Primary가 죽었을 때 자동으로 넘어가지 않습니다. 사람이 레플리카를 Primary로 올리고, 애플리케이션의 접속 주소도 바꿔야 합니다. 이것을 자동으로 하는 것이 다음 단계입니다.

3장애 조치는 서비스를 살리지만, 성공한 쓰기를 잃을 수 있다

Sentinel은 Redis를 감시하는 별도 프로세스입니다. 보통 3대 이상을 두고, 여러 Sentinel이 "Primary가 죽었다"고 동의하면 레플리카 하나를 새 Primary로 올립니다. 이것을 장애 조치(failover)라고 합니다. 애플리케이션은 Redis 주소를 직접 적지 않고 Sentinel에게 "지금 Primary가 누구냐"를 물어서 접속합니다.

장애 조치 중에 생기는 일이유대응
쓰기가 잠시 실패함죽었다고 판단하고 새 Primary를 올리기까지 시간이 걸림 (감지 기준 시간 설정에 따라 수 초~수십 초)짧은 타임아웃과 재시도(16편), 실패해도 서비스가 버티게 설계
이미 성공한 쓰기가 사라질 수 있음비동기 복제라, 옛 Primary가 받았지만 레플리카에 아직 안 간 쓰기는 새 Primary에 없음잃으면 안 되는 데이터는 DB를 원본으로. Redis에는 쓰기를 받을 최소 레플리카 수를 거는 설정도 있음
핵심 — 레플리카와 Sentinel은 가용성(멈추지 않음)을 높여 주지만, "성공한 쓰기는 절대 사라지지 않는다"는 보장은 주지 않습니다. 30편 분산 락에서 이 점이 결정적으로 중요해집니다.

공식 문서도 이 점을 분명히 적습니다. Sentinel 문서는 비동기 복제 때문에 확인 응답을 보낸 쓰기가 장애 중에 유지된다고 보장하지 않는다고 하고, Cluster 문서는 강한 일관성을 보장하지 않으며 클라이언트에 성공을 알린 쓰기를 잃을 수 있다고 설명합니다. 쓰기가 레플리카에 복제될 때까지 기다리는 WAIT 명령(Redis 7.2부터는 디스크 반영까지 기다리는 WAITAOF)도 있지만, 공식 문서는 이 명령들도 Redis를 강한 일관성 저장소로 만들지는 않는다고 말합니다. 잃을 가능성을 줄일 뿐입니다.

AWS ElastiCache도 복제가 비동기라 장애 조치 때 복제 지연만큼 소량의 데이터를 잃을 수 있다고 안내합니다. 또 Multi-AZ(자동 장애 조치)와 AOF를 함께 쓸 수 없고 appendonly·appendfsync 설정도 지원하지 않으므로, ElastiCache에서는 디스크 기록보다 레플리카와 자동 장애 조치로 대비합니다.

4원본인지 사본인지에 따라 설정이 달라진다

영속성 설정과 메모리 설정을 정하는 기준은 하나입니다. "이 데이터를 잃으면 다시 만들 수 있는가?"

용도잃으면영속성메모리가 차면 (31편)
캐시 (26편)DB에서 다시 읽어 채우면 됨꺼도 됨 (켜 두면 재시작 후 빈 캐시를 피할 수 있음, 31편)오래 안 쓴 것부터 지워도 됨
세션 (14편)사용자가 로그아웃됨보통 켬함부로 지우면 안 됨
카운터·선착순 수량 (22편)숫자가 틀어짐켬, 그래도 최종 기록은 DB에지우면 안 됨
분산 락 (30편)락이 사라져 두 명이 동시에 진입켜도 완전하지 않음 (30편)지우면 안 됨

그래서 캐시와 원본 데이터를 같은 Redis에 섞으면 설정이 서로 부딪칩니다. 캐시에 맞춰 "아무 키나 지워도 됨"으로 두면 세션이 지워지고, 세션에 맞춰 "지우지 않음"으로 두면 캐시가 메모리를 다 채웠을 때 세션 쓰기까지 실패합니다. 규모가 커지면 용도별로 Redis를 나누는 것이 일반적입니다.

핵심 — Redis를 원본 저장소로 쓰려면 두 가지를 받아들여야 합니다. 디스크 저장을 켜도 남는 유실 범위(1절)와, 장애 조치 때 사라질 수 있는 성공한 쓰기(3절)입니다. 공식 문서도 PostgreSQL 수준의 데이터 안전이 필요하면 RDB와 AOF를 함께 쓰라고 안내하지만, 그래도 3절의 유실은 남습니다. 이것을 받아들일 수 없는 데이터(잔액, 주문 상태)는 DB가 원본이고 Redis는 사본입니다(27편 5절의 ② 질문).

5구성은 데이터 크기와 멈춤 허용치로 고른다

Sentinel까지는 모든 데이터가 Primary 한 대에 있습니다. 데이터가 한 대의 메모리를 넘거나 쓰기가 한 대로 감당이 안 되면, 데이터를 여러 Primary에 나눠야 합니다. 이렇게 나눈 한 덩어리를 샤드라고 합니다. Redis Cluster는 이 분할을 Redis가 직접 합니다. 샤드마다 Primary와 레플리카가 있고, 장애 조치도 Cluster가 스스로 합니다(Sentinel이 따로 필요 없음).

키가 어느 샤드로 갈지는 해시 슬롯으로 정합니다. 모든 키는 이름을 해시해서 0~16383 중 하나의 슬롯에 들어가고, 샤드마다 슬롯 범위를 나눠 맡습니다(2절 그림 ④).

이렇게 나누면 여러 키를 다루는 명령(MGET, MULTI, Lua 스크립트)은 키가 모두 같은 슬롯에 있어야 합니다. 함께 다룰 키를 해시 태그로 묶는 방법은 28편 6절에서 봤습니다.

애플리케이션 쪽에서도 알아야 할 것이 생깁니다. 클라이언트는 "어느 슬롯이 어느 노드에 있는지" 지도를 들고 있다가, 키에 맞는 노드로 바로 명령을 보냅니다. 장애 조치나 슬롯 이동으로 지도가 바뀌면 Redis가 "그 슬롯은 저쪽 노드로 가라"(MOVED)고 알려 주고, 클라이언트가 지도를 갱신합니다. Lettuce 같은 클라이언트가 이 일을 대신하지만, 지도를 언제 새로 받을지는 설정해야 합니다(실무 예시).

상황구성
개발·테스트, 잃어도 되는 작은 캐시단일
운영 서비스, 데이터는 한 대 메모리에 들어감Primary + 레플리카 + 자동 장애 조치 (직접 운영하면 Sentinel)
데이터가 한 대 메모리를 넘거나, 쓰기가 한 대로 부족함Cluster

AWS ElastiCache를 쓴다면 이름이 다릅니다. cluster mode 비활성은 샤드 하나에 Primary와 레플리카를 둔 구성입니다. 레플리카를 하나 이상 두고 자동 장애 조치(Multi-AZ)를 켜면 장애 조치는 AWS가 맡습니다(Sentinel 역할). cluster mode 활성은 여러 샤드로 나눈 Redis Cluster 구성입니다. 어느 쪽이냐에 따라 애플리케이션의 접속 설정과 여러 키 명령의 제약이 달라지므로, 처음에 정하고 시작하는 것이 좋습니다.

Sentinel 구성 (application.yml)
spring:
  data:
    redis:
      sentinel:
        master: mymaster          # Sentinel이 관리하는 이름
        nodes: s1:26379,s2:26379,s3:26379
      timeout: 1s                 # 실무 예시 참고
Cluster 구성 (application.yml)
spring:
  data:
    redis:
      cluster:
        nodes: r1:6379,r2:6379,r3:6379
      timeout: 1s
      lettuce:
        cluster:
          refresh:
            adaptive: true        # 실무 예시 참고

6실무 예시

장애 대응

Redis 장애 조치 동안 API가 1분씩 멈췄다

Primary가 죽고 새 Primary가 올라오기까지 몇 초가 걸렸습니다. 그런데 애플리케이션은 몇 초가 아니라 1분 가까이 멈췄습니다. spring.data.redis.timeout을 정하지 않아 기본 명령 타임아웃(스프링 부트 + Lettuce에서 60초)이 적용됐고, 요청 스레드들이 응답 없는 명령을 기다리며 묶였기 때문입니다. 16편에서 본 장애 전파 그대로입니다.

해결: spring.data.redis.timeout을 서비스에 맞게 짧게(예: 수백 ms~1초) 잡습니다. 캐시처럼 없어도 되는 호출은 실패 시 DB로 가도록(27편 실무 예시), 없으면 안 되는 호출은 재시도와 서킷 브레이커로 감쌉니다.

운영 설정

Cluster 장애 조치 뒤에도 옛 노드로 계속 요청했다

Cluster에서 한 샤드의 Primary가 바뀌었는데, 애플리케이션이 한동안 옛 노드로 명령을 보내며 에러를 냈습니다. 클라이언트가 들고 있는 슬롯 지도가 갱신되지 않았기 때문입니다.

해결: Lettuce의 토폴로지 갱신을 켭니다. spring.data.redis.lettuce.cluster.refresh.adaptive=true는 MOVED나 연결 끊김 같은 신호를 받으면 지도를 새로 받고, …refresh.period는 주기적으로 새로 받습니다. 스프링 부트 3 기본값은 둘 다 꺼져 있으므로(adaptive=false, period 미설정), Cluster를 쓴다면 직접 켭니다.

실수 예시

방금 담은 상품이 장바구니에 안 보인다

읽기 부하를 줄이려고 Lettuce의 읽기 대상을 레플리카 우선(ReadFrom.REPLICA_PREFERRED)으로 바꿨습니다. 그러자 "담기" 직후 장바구니 화면에서 방금 담은 상품이 가끔 빠져 보였습니다. 2절의 비동기 복제 지연입니다. 25편의 "회원가입 직후 404"와 같은 문제입니다.

해결: 쓰기 직후 바로 읽는 흐름은 Primary에서 읽고, 조금 늦어도 되는 조회(랭킹, 통계)만 레플리카로 보냅니다.

운영 설정

maxmemory를 서버 메모리와 똑같이 잡지 않는 이유

서버 메모리가 16GB라고 maxmemory를 16GB로 잡으면, RDB 스냅샷 중 늘어나는 메모리(1절)와 연결마다 쓰는 버퍼, 운영체제 몫이 들어갈 자리가 없습니다. 그 결과 스냅샷 도중 운영체제가 Redis를 강제 종료하기도 합니다. 서버 메모리의 일부만 상한으로 주고 여유를 남기며, 여유가 얼마나 필요한지는 쓰기 양과 스냅샷 여부에 따라 모니터링하며 정합니다.

지금은 넘어가도 되는 것 · RDB·AOF 파일 형식, AOF 재작성(rewrite) 과정과 여러 파일로 나눠 저장하는 방식, Sentinel끼리 합의하는 과정(쿼럼·리더 선출), Cluster 노드끼리 상태를 주고받는 방식(gossip), 샤드를 늘리거나 줄일 때 슬롯을 옮기는 과정(resharding), 프록시로 샤딩하는 다른 방식들, AWS ElastiCache의 선택 기능 Durability(Valkey 9.0 이상, 여러 가용 영역에 쓰기를 기록)

답을 열기 전에 먼저 소리 내어 설명해 보세요.

RDB와 AOF는 Redis가 죽었을 때 각각 무엇을 잃나요?
RDB는 주기적으로 찍는 스냅샷이라 마지막 스냅샷 이후의 쓰기를 모두 잃습니다. AOF는 쓰기 명령을 계속 파일에 덧붙이고, 기본 설정에서 1초마다 디스크에 반영하므로 최대 약 1초 분량을 잃습니다. 둘 다 잃는 범위를 줄일 뿐 0으로 만들지는 못합니다.
레플리카를 두면 무엇이 좋아지고, 어떤 새 문제가 생기나요?
읽기를 복사본으로 나눠 Primary 부하를 줄이고, 복사본이 데이터를 한 벌 더 갖게 됩니다. 대신 복제가 비동기라 방금 쓴 값이 레플리카에 아직 없을 수 있어, 쓰기 직후 읽기는 Primary에서 해야 합니다. 레플리카만으로는 Primary가 죽었을 때 자동으로 넘어가지 않습니다.
Sentinel이 장애 조치를 했는데도 데이터가 사라질 수 있는 이유는?
복제가 비동기라서, 옛 Primary가 쓰기에 성공 응답을 했지만 레플리카에 아직 전달되지 않은 데이터가 있을 수 있습니다. 그 레플리카가 새 Primary가 되면 그 쓰기는 없는 것이 됩니다. Sentinel은 멈추지 않게 해 주지만, 성공한 쓰기가 사라지지 않는다는 보장은 주지 않습니다.
Redis 장애 조치는 몇 초면 끝났는데 애플리케이션은 왜 1분씩 멈출 수 있나요?
명령 타임아웃을 정하지 않으면 기본값(스프링 부트 + Lettuce에서 60초)만큼 응답을 기다리며 요청 스레드가 묶입니다. 스레드가 묶이면 무관한 요청까지 밀려 장애가 번집니다. 타임아웃을 짧게 잡고, 실패해도 되는 호출은 우회하며, 재시도와 서킷 브레이커를 둡니다.
Redis를 원본 저장소로 써도 되는 데이터와 아닌 데이터는 어떻게 가르나요?
"잃으면 다시 만들 수 있는가"로 가릅니다. 캐시처럼 DB에서 다시 채울 수 있거나 세션처럼 잃어도 다시 로그인하면 되는 데이터는 Redis에 두어도 됩니다. 잔액이나 주문 상태처럼 잃으면 안 되는 데이터는, 디스크 저장을 켜도 남는 유실 범위와 장애 조치 때 사라질 수 있는 쓰기를 감당할 수 없으므로 DB를 원본으로 두고 Redis는 사본이나 빠른 계산용으로 씁니다.
