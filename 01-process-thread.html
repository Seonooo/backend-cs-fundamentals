프로세스와 스레드

스프링 서버 하나는 프로세스 하나이고, 요청 하나하나는 그 안의 스레드가 처리합니다. 스레드들은 메모리의 대부분을 공유합니다. 이 한 가지가 앞으로 나올 동시성 문제의 출발점입니다.

1. 개념2. 무엇을 공유하나3. 스프링 서버에서는 이렇게 생겼다4. 실무 예시5. 설명해보기

1개념

프로세스는 실행 중인 프로그램입니다. 운영체제가 프로세스마다 독립된 메모리 공간을 줍니다. 그래서 한 프로세스는 다른 프로세스의 메모리를 볼 수 없습니다.

스레드는 프로세스 안에서 실제로 코드를 실행하는 흐름입니다. 한 프로세스 안에 스레드가 여러 개 있으면, 이들은 같은 메모리 공간을 함께 씁니다.

비유 · 프로세스식당 하나. 식당마다 주방과 재료 창고가 따로 있고, 옆 식당 창고는 쓸 수 없다.
비유 · 스레드한 식당의 요리사들. 주방과 창고는 같이 쓰고, 각자 도마(작업대)만 따로 있다.

2무엇을 공유하나

프로세스의 메모리는 크게 네 영역으로 나뉩니다. 스레드끼리 코드·데이터·힙은 공유하고, 스택만 각자 가집니다.

영역들어 있는 것공유?
코드컴파일된 클래스, 메서드 코드공유
데이터static 변수공유
힙new로 만든 모든 객체 (스프링 빈 포함)공유
스택메서드 호출 정보, 지역 변수, 파라미터스레드마다 따로
핵심 — 공유되는 곳(힙, static)에 있는 값을 여러 스레드가 동시에 바꾸면 문제가 생깁니다. 스택에 있는 지역 변수는 그 스레드만 보기 때문에 안전합니다.

프로세스 vs 스레드 한눈에

프로세스스레드
메모리독립코드·데이터·힙 공유, 스택만 독립
만드는 비용큼상대적으로 작음 (그래도 공짜는 아님)
데이터 주고받기어려움 (네트워크, 파이프 등 필요)쉬움 (같은 객체를 그냥 참조)
하나가 죽으면다른 프로세스는 영향 없음OOM 등으로 프로세스 전체가 죽을 수 있음

3스프링 서버에서는 이렇게 생겼다

스프링 부트 애플리케이션을 실행하면 JVM 프로세스 하나가 뜹니다. 요청이 들어오면 내장 톰캣이 스레드 풀에서 스레드 하나를 꺼내 그 요청을 맡깁니다. 그런데 컨트롤러·서비스 같은 스프링 빈은 기본이 싱글톤이라 힙에 딱 하나만 있습니다.

여기서 두 가지를 기억하면 됩니다.

  1. 메서드 안의 지역 변수와 파라미터는 각 스레드의 스택에 있으니 안전하다.
  2. 싱글톤 빈의 필드는 힙에 있으니 모든 요청이 공유한다. 여기에 요청별 값을 저장하면 안 된다.

4실무 예시

실수 예시

싱글톤 빈 필드에 요청 값을 저장했다

로컬에서 혼자 테스트할 땐 문제가 없는데, 운영에서 가끔 다른 사람의 주문 목록이 보인다는 문의가 들어옵니다.

✕ 문제 코드
@Service
public class OrderService {
    private Long currentUserId;   // 힙에 있는 필드 → 모든 요청이 공유

    public List<Order> myOrders(Long userId) {
        this.currentUserId = userId;
        validate();
        return orderRepository.findByUserId(currentUserId);
    }
}

요청 두 개가 거의 동시에 들어오면 이런 일이 벌어집니다.

✓ 고친 코드 — 값은 파라미터와 지역 변수(스택)로만 다룬다
@Service
public class OrderService {
    private final OrderRepository orderRepository;  // 필드는 '바뀌지 않는 의존성'만

    public List<Order> myOrders(Long userId) {        // 파라미터 → 이 스레드의 스택
        validate(userId);
        return orderRepository.findByUserId(userId);
    }
}

기준: 싱글톤 빈의 필드에는 final로 주입받은 의존성처럼 요청마다 바뀌지 않는 것만 둡니다.

매일 보는 곳

로그의 스레드 이름으로 요청 하나를 따라간다

스프링 로그의 대괄호 안이 그 로그를 남긴 스레드 이름입니다.

애플리케이션 로그

10:15:03.121 INFO [http-nio-8080-exec-3] OrderController : 주문 조회 userId=2
10:15:03.188 INFO [http-nio-8080-exec-7] OrderService    : 주문 3건 조회
10:15:03.190 WARN [http-nio-8080-exec-7] PaymentClient   : 결제 조회 지연 1.2s

여러 요청의 로그가 섞여 나와도, 같은 스레드 이름(exec-7)만 모으면 사용자 1의 요청 흐름이 보입니다. 다만 @Async처럼 중간에 스레드가 바뀌면 이 방법이 끊기기 때문에, 실무에서는 요청마다 trace ID를 붙여 로그에 남깁니다.

장애 대응

서버가 멈춘 것 같을 때 스레드 덤프를 뜬다

응답이 안 올 때, 지금 각 스레드가 무엇을 하고 있는지 찍어 보는 것이 스레드 덤프입니다.

jstack <pid> 결과 일부
"http-nio-8080-exec-7" #45 daemon prio=5
   java.lang.Thread.State: RUNNABLE
        at sun.nio.ch.NioSocketImpl.read(...)       ← 소켓에서 응답을 기다리는 중
        at com.example.PaymentClient.pay(PaymentClient.java:42)
        at com.example.OrderService.order(OrderService.java:58)

톰캣 스레드 대부분이 같은 줄(PaymentClient.pay)에서 멈춰 있다면, 원인은 우리 코드가 아니라 결제 서버 응답 지연일 가능성이 높습니다. 이 내용은 07 스레드 풀과 네트워크 · 타임아웃에서 이어집니다.

설계 이유

왜 요청마다 스레드를 새로 만들지 않을까

스레드는 프로세스보다 가볍지만 공짜는 아닙니다. 스레드마다 스택 메모리가 잡히고 OS 자원도 씁니다. 요청마다 만들고 버리면 생성 비용이 계속 들고, 트래픽이 몰리면 스레드가 끝없이 늘어나 서버가 죽습니다.

✕ 요청마다 새 스레드
new Thread(() -> handle(req)).start();
// 생성 비용 매번 발생
// 개수 상한 없음 → OOM
✓ 만들어 둔 스레드 재사용
executor.submit(() -> handle(req));
// 미리 만든 스레드 재사용
// 최대 개수 제한

톰캣이 스레드 풀을 쓰는 이유가 바로 이것입니다. 풀 크기를 어떻게 정하는지는 04 컨텍스트 스위칭과 07 스레드 풀에서 다룹니다.

5설명해보기

답을 열기 전에 먼저 소리 내어 설명해 보세요.

프로세스와 스레드의 차이를 메모리 관점에서 설명해 보세요.
프로세스는 운영체제로부터 독립된 메모리 공간을 받아 서로의 메모리에 접근할 수 없습니다. 스레드는 한 프로세스 안의 실행 흐름으로, 코드·데이터·힙 영역을 공유하고 스택만 각자 가집니다. 그래서 스레드 간 데이터 공유는 쉽지만, 동시에 같은 데이터를 바꾸면 문제가 생길 수 있습니다.
스프링 싱글톤 빈에 인스턴스 필드로 요청 값을 저장하면 왜 위험한가요?
싱글톤 빈은 힙에 하나만 존재하고, 모든 요청 스레드가 같은 객체를 사용합니다. 한 요청이 필드에 쓴 값을 다른 요청이 덮어쓰거나 읽을 수 있어 데이터가 섞입니다. 요청별 값은 파라미터나 지역 변수로 다뤄 스택에 두어야 합니다.
메서드 안에서 new ArrayList<>()로 만든 리스트는 힙에 있는데, 왜 안전한가요?
객체 자체는 힙에 있지만, 그 객체를 가리키는 참조는 지역 변수로 이 스레드의 스택에만 있습니다. 다른 스레드는 이 객체에 접근할 방법이 없으니 사실상 공유되지 않습니다. 반대로 이 리스트를 필드나 static 변수에 저장하는 순간 공유되어 위험해집니다.
톰캣은 왜 요청마다 스레드를 새로 만들지 않고 스레드 풀을 쓰나요?
스레드 생성에는 스택 메모리 할당과 OS 자원이 필요해 비용이 있습니다. 요청마다 만들면 생성 비용이 반복되고, 트래픽이 몰리면 스레드 수가 무한정 늘어 메모리 부족으로 서버가 죽을 수 있습니다. 풀은 스레드를 재사용하고 최대 개수를 제한해 이 두 문제를 막습니다.
