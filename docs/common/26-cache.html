캐시

캐시는 이미 여러 번 나왔습니다. OS 페이지 캐시(03), DNS 캐시(10), JPA 영속성 컨텍스트(24). 원리는 하나입니다. 자주 쓰는 것을 가까운 곳에 복사해 둔다. 그리고 대가도 하나입니다. 복사본은 원본과 달라질 수 있다. 이 편에서는 백엔드 개발자가 직접 설계하는 애플리케이션 캐시(로컬 캐시, Redis)를 중심으로 정리합니다.

1요청 하나가 지나가는 캐시들

2가장 흔한 패턴: Cache-Aside

애플리케이션이 캐시를 먼저 보고, 없으면 DB에서 읽어 캐시에 넣는 방식입니다. 스프링의 @Cacheable이 이 동작을 해 줍니다.

무효화 방법설명감수하는 것
TTL 만료일정 시간이 지나면 자동 삭제TTL 동안은 옛 값일 수 있음 (10편 DNS와 같음)
쓰기 시 삭제데이터를 바꾸는 코드에서 캐시 키 삭제 (@CacheEvict)삭제를 빠뜨리는 코드 경로가 생기기 쉬움
둘 다쓰기 시 삭제 + 안전망으로 TTL가장 흔한 실무 조합

3로컬 캐시 vs Redis

로컬 캐시 (Caffeine)원격 캐시 (Redis)
속도가장 빠름 (메모리 접근)네트워크 왕복 1번
서버 간 일관성서버마다 다를 수 있음모두 같은 값을 봄 (Redis 한 대 기준. Replica에서 읽거나 장애 조치 중에는 잠시 달라질 수 있음, 29편)
용량JVM 힙 안 (02편 · 크기 제한 필수)별도 서버 메모리
잘 맞는 데이터거의 안 바뀌는 코드표, 설정, 카테고리세션(14편), 자주 바뀌지만 공유가 필요한 값

4실무 예시

좋은 패턴

@Cacheable + Redis + TTL

✓ 조회는 캐시, 수정은 삭제
@Cacheable(cacheNames = "product", key = "#id")
public ProductDto getProduct(Long id) { … }        // 캐시 미스일 때만 실행

@CacheEvict(cacheNames = "product", key = "#id")
@Transactional
public void changePrice(Long id, int price) { … }  // 수정 후 캐시 삭제

# application.yml
spring:
  cache:
    type: redis
    redis:
      time-to-live: 10m    # 삭제를 빠뜨려도 10분 뒤엔 새 값 (안전망)

주의: 두 어노테이션을 한 메서드에 함께 쓰면 캐시 삭제가 커밋보다 먼저 일어날 수 있습니다. 그 틈에 읽기가 들어오면 옛 값이 다시 캐시에 채워집니다. 커밋 후 삭제를 보장하려면 캐시 매니저를 transactionAware로 설정하거나, @TransactionalEventListener(AFTER_COMMIT)에서 삭제합니다 (20편).

@Cacheable도 @Transactional처럼 프록시로 동작하므로, 같은 클래스 안에서 호출하면 캐시가 적용되지 않습니다 (20편과 같은 함정). 엔티티 대신 DTO를 캐시해야 직렬화 문제와 지연 로딩 문제를 피할 수 있습니다 (24편).

실수 예시

캐시 키에 사용자 구분을 빠뜨렸다

"내 쿠폰 목록"을 캐시하면서 키를 쿠폰 타입으로만 잡았습니다. 첫 번째로 조회한 사용자의 쿠폰 목록이 캐시에 들어가고, 이후 모든 사용자가 그 사람의 목록을 봅니다. 01편의 "싱글톤 필드에 사용자 값 저장" 버그와 똑같은 결과가 캐시 레벨에서 나온 것입니다.

✕ 누구의 데이터인지 키에 없음
@Cacheable(cacheNames = "myCoupons",
           key = "#type")
public List<CouponDto> myCoupons(
    Long memberId, CouponType type)
✓ 결과를 결정하는 모든 값을 키에
@Cacheable(cacheNames = "myCoupons",
           key = "#memberId + ':' + #type")
public List<CouponDto> myCoupons(
    Long memberId, CouponType type)
실수 예시

인기 상품 캐시가 만료되는 순간 DB가 멈췄다 (캐시 스탬피드)

초당 수천 번 조회되는 메인 페이지 캐시의 TTL이 끝나는 순간, 그 사이 들어온 요청이 전부 동시에 캐시 미스를 내고 같은 무거운 쿼리를 DB에 보냅니다. 16편의 "장애 전파"가 캐시에서 시작되는 경우입니다.

  • 한 번만 읽기: 같은 키를 동시에 로딩할 때 하나만 DB에 가고 나머지는 결과를 기다리게 함. Caffeine의 get(key, loader)나 @Cacheable(sync = true)를 쓰면 JVM 안에서 합쳐지지만, 기본 @Cacheable은 합쳐 주지 않음. 분산 환경은 락 등으로 구현
  • 만료 시간 흩뿌리기: TTL에 무작위 값을 더해 여러 키가 한꺼번에 만료되지 않게 (16편 재시도의 지터와 같은 아이디어)
  • 미리 갱신: 만료 전에 백그라운드에서 새 값으로 교체
설계 이유

캐시를 붙이기 전에 먼저 묻는 것

  1. 정말 느린가? 인덱스(18편)나 N+1(24편)로 해결되는 문제를 캐시로 덮으면 원인이 숨습니다.
  2. 얼마나 늦어도 괜찮은가? 가격·재고·잔액처럼 정확해야 하는 값은 캐시를 신중히, 짧게.
  3. 무엇이 바뀌면 지워야 하는가? 그 데이터를 바꾸는 모든 코드 경로를 알고 있는가.
  4. 캐시가 죽으면? Redis 장애 시 모든 요청이 DB로 쏟아져도 버틸 수 있는가.

5캐시가 이어지는 곳

캐시는 앞에서 따로 나온 원리들이 모이는 곳입니다. OS 페이지 캐시(03편)의 "가까운 곳에 복사본", DNS TTL(10편)의 "얼마나 늦어도 괜찮은가", 인덱스(18편)의 "디스크를 덜 읽기", 영속성 컨텍스트(24편)의 "트랜잭션 안의 1차 캐시"가 이 편에서 애플리케이션 캐시로 다시 나왔습니다.

여러 원리가 편을 넘어 반복되는 흐름은 목차의 연결 키워드 지도에서 한 번에 볼 수 있습니다.

6설명해보기

답을 열기 전에 먼저 소리 내어 설명해 보세요.

Cache-Aside 패턴에서 데이터를 수정할 때 캐시를 갱신하지 않고 삭제하는 이유는?
동시에 여러 요청이 수정할 때 캐시 갱신 순서와 DB 반영 순서가 엇갈리면 옛 값이 캐시에 남을 수 있습니다. 삭제하면 다음 읽기가 DB의 최신 값을 다시 채우므로 순서 꼬임의 위험이 줄어듭니다. TTL을 함께 두면 삭제를 놓쳐도 일정 시간 뒤 바로잡힙니다.
로컬 캐시와 Redis 중 무엇을 쓸지 어떻게 판단하나요?
거의 바뀌지 않고 서버 간 약간의 불일치가 괜찮은 데이터는 가장 빠른 로컬 캐시를, 서버 간 일관성이 중요하거나 세션처럼 공유가 필요한 데이터는 Redis를 씁니다. 로컬 캐시는 JVM 힙을 쓰므로 크기 제한이 필수입니다.
캐시 스탬피드가 무엇이고, 어떻게 막나요?
자주 조회되는 키가 만료되는 순간 동시에 들어온 요청이 모두 캐시 미스를 내고 DB로 몰리는 현상입니다. 같은 키 로딩을 하나로 합치고, TTL에 무작위 값을 더해 만료를 흩뜨리고, 만료 전에 미리 갱신하는 방법으로 막습니다.
이 시리즈에서 "풀링" 패턴이 등장한 곳과 공통 질문을 설명해 보세요.
스레드 풀(07), HTTP 커넥션 풀(15), DB 커넥션 풀(23)입니다. 공통 질문은 크기를 몇으로 할지, 다 쓰고 있을 때 어떻게 기다리고 그 한도는 얼마인지, 오래된 자원을 어떻게 정리할지입니다. 대기에 한도가 없으면 고갈이 장애로 번집니다.
